## 1. 设计目标与范围

玩家面对的是“自己的游戏 Agent 和持续任务”，而不是某个必须一直打开的 AI 聊天窗口。Web/桌面客户端用于看世界、发布目标和作出关键选择；实际运行的外部 Runtime 读取目标、自主规划、汇报和求助；oasis7 使两侧共享可信的任务、权限和世界结果。

保留世界舞台的主阅读位置。协作内容在所选 Agent 的任务上下文展开，不用新增常驻管理面板取代地图。角色、消息来源和下一步清楚可读，是比布局统一更重要的设计目标。

设计假设：玩家能在不理解进程、协议或队列的情况下识别“我发出了什么、谁已收到、正在做什么、轮到谁处理”。应以真实用户完成下述流程来验证；单张界面截图或 Agent 自述不能证明成立。

## 2. 一次完整的协作经历

### 2.1 绑定任务与发布目标

玩家选中自己有权控制的 Agent，先看到世界、Agent 身份、当前任务、执行方及已有义务。没有运行中的执行方时，可以保存目标，但清楚显示“目标已保存，等待执行方接入”，提供该受支持 Runtime 的启动/恢复说明，不显示虚假的运行中状态。

目标编辑展示当前有效版本、草稿差异和将改变的游戏约束。提交成功只说明可信记录已保存。服务端生效状态与外部 Runtime 的读取/采纳确认分开，尤其不能将“Prompt 已应用到配置”解释为“模型已经采用并执行”。编辑冲突先检查控制资格；有权时可重读重编，无权时不泄露新值。

### 2.2 Runtime 领取上下文并汇报

已启动的 Runtime 或受支持薄执行器经 Game API 读取当前任务、目标版本、有效委托与未决结果，再处理增量变化。每个已采纳声明注明执行方和目标版本；后续可关联的决策、等待或阻塞结果用于表明该版本已进入执行上下文，不宣称能证明模型内部理解。

玩家读到三种不同内容：当前计划摘要、执行方报告的阶段/阻塞，以及世界确认的行动结果。计划旁注明“执行方报告”和更新时间；世界成果使用权威回执。没有可信进度分母时，不显示编造的完成百分比。计划无需公开模型内部思维、完整私有会话或凭据。

<a id="collaboration-question-delivery"></a>
### 2.3 需要澄清时的双向问答

玩家可以询问“为什么先处理能源”，Runtime 也可以问“优先保证储备，还是优先扩大产量”。同一线程保留任务、提问方、指定回答方、目标版本、原问题和已接受答案；玩家可以在另一个设备回答。服务保存、接收端报告收到、原提问方报告处理答案，以及世界结果分别呈现。

| 可显示的事实 | 中文 / English 正文 | 下一步与证明范围 |
| --- | --- | --- |
| 服务已保存问题或答案，尚无对应接收报告 | 已保存，等待接收 / Saved; awaiting receipt | 保留原线程；不将提交成功写成对方已收到 |
| 指定接收端报告收到该消息 | 接收端报告已收到 / Recipient reports receipt | 展开可见接收方、时间及保存范围；执行器报告写入本地受控 inbox，玩家表面只确认当前窗口内存收到，两者均不证明人已读或模型理解 |
| 玩家明确处理 Runtime 对其问题的回答 | 你已标为已查看 / You marked this as viewed | 使用“标为已查看 / Mark as viewed”明确操作；页面渲染、滚动或接收报告不自动代点 |
| Runtime 报告考虑了玩家对其问题的回答 | 执行方报告已考虑 / Runtime reports it has considered the answer | 只表示执行方声明完成此次处理，目标、授权与世界成果仍取原权威结果 |
| 处理后需改变目标或取得授权 | 需要明确修改目标 / Explicit goal change required；需要申请授权 / Authorization request required | 进入原目标编辑或授权申请，展示待确认内容；处理报告不自动提交这些动作 |
| 接收者报告无法采用答案 | 接收者报告无法采用 / Recipient reports it cannot use the answer | 显示有来源的原因，允许新问题或仍合法的替代；不自行扩大权限 |
| 原目标或身份关系已失效 | 已过时，需重新提问 / Out of date; ask again | 历史在当前读权内保留；新问题显式关联旧线程，不搬运旧批准或执行资格 |

已回答但尚未处理的线程仍留在任务的未完问答中，不能在问题有答案时就从离线恢复内容里消失。关闭窗口、刷新或换设备后从服务端重读当前线程；旧窗口的接收报告不证明新窗口收到或玩家已查看。Web/桌面 Viewer 不因此新增私有正文的持久缓存；切身份、失权和关闭时清除有关内存，原私有数据与历史读取边界继续有效。

同一问题只接受一份基于当前问题版本的答案。另一设备已回答时，保留本地草稿并重读原答案，不静默覆盖；更正或继续讨论通过新的关联问题，确需改目标仍走明确编辑。答案或回执响应丢失时显示“结果待确认 / Result unconfirmed”，先核对原提交，不能另造答案或把重试当作第二次处理。未完问答与申请达到服务公布的容量时，明确拒绝新增项并保留已接受内容；不能自动关闭旧问题或批准申请腾出空间。

有权玩家可明确选择“关闭此问题 / Close this question”，确认后显示“问题已关闭 / Question closed”。关闭只结束该未完问答，保留已有答案和历史，不代表已查看或已采用，也不停止委托、撤销授权或取消世界行动；仍缺必要决定的行动继续按原合同阻塞。

普通聊天不是目标修改。回答确实要改变持续目标时，展示待修改内容并转入明确的目标确认；需要扩大权限时，转入授权申请。在旧目标或身份关系仍有效时已被服务接受、失效后才交付的回复，按当前读权保留为过时历史；失效后才首次提交的旧问答或回执会被拒绝，不新增为有效历史，也不自动执行旧答案。

### 2.4 关键选择的授权交互

Runtime 需要超出已有范围的投入时，申请卡展示：关联 Agent/任务、要做的选择、原因与可核对依据、对象范围、累计资源/风险额度、有效期、已有授权和拒绝后的替代。授权界面使用现有权威授予路径，不根据模型生成的卡片自行赋权。

玩家可批准明示范围、拒绝或调整范围；调整也是新的显式决定。批准后显示“授权已生效/等待执行方”，随后行动仍可能因世界资源或条件变化被拒绝。拒绝、到期、撤销、owner 变化或目标变化使申请失去适用性时，不显示“默认继续”，也不要求玩家再次拒绝相同过时申请。

对于“减少风险但允许其他工作继续”的选择，界面分别说明受阻部分和已有合法范围内的独立任务；不能把等待审批包装为暂停整个世界。游戏授权不批准 Runtime 的本机文件操作、外部付款或额外第三方工具权限。

### 2.5 离开、返回、停止与接管

玩家关闭网页/客户端但独立执行方仍在工作时，协作继续；打开另一表面看到同一任务、未完问答（含已答待处理）、未决申请、最新目标和权威结果。用户不必找到原终端或重新输入完整目标。

停止后续委托与关闭观察窗口是不同操作。停止前说明新增工作会停止，但已受理行动仍需核对；已有结果不撤销，消息历史不删除。Runtime 会话结束或机器关闭后显示等待执行方，不假装游戏服务能远程启动其本机程序。

恢复或执行方交接先读取当前目标、有效权限和未知结果。旧执行方不再有新提交资格；历史读取与新的执行权分开。私有上下文丢失时明示，并提供依据可信世界事实重新规划，不要求保留同一个私有 session ID。

## 3. 协作信息与网络能力

### 3.1 默认层、展开层和诊断层

| 层次 | 信息 | 阅读目的 |
| --- | --- | --- |
| 默认层 | 当前 Agent/任务、有效目标、是否等待玩家或执行方、最近世界成果与主要阻塞 | 玩家立即知道发生了什么、下一步由谁处理 |
| 展开层 | 计划摘要、目标修改差异、问答线程、授权申请、旧版本与恢复结果 | 支持有依据的选择和追溯 |
| 诊断层 | Runtime/适配版本、最近通信、事件缺口、读取/采纳确认与关联请求 | 排查没有响应或状态不一致，不暴露秘密和模型内部思维 |

“在线”必须有来源和时效。API 健康、最近轮询成功、正在推理、等待玩家和等待世界不能合并为一个绿点。当前执行状态无法确认时显示未知/需检查，而不是直接宣判进程关闭或自动启动第二个执行方。

### 3.2 同一 Game API 的协作职责

| 使用方 | 需要完成的产品操作 | 不能借此获得的能力 |
| --- | --- | --- |
| 有权玩家 | 发布/修改目标、读取任务与报告、提问/回答、显式决定授权、停止委托 | 任意控制其他 Agent 或绕过世界规则 |
| 当前受权 Runtime | 读取有效任务与增量通知、确认读取/采纳版本、报告状态、问答和申请授权、提交合法世界意图 | 批准自己的申请、将任意聊天升级为 owner 指令 |
| 可信接入与世界执行方 | 验证身份与版本、保存协作结果、处理去重/缺口、执行现有权限与世界裁决 | 以保存消息或采纳声明伪造世界效果 |

这些能力可复用现有 Game API、目标和事件通道，不需要另开 OpenClaw 专用消息系统。首期以有界增量读取/轮询满足接收和恢复；SSE/WebSocket 只是可选传输。具体端点、字段、鉴权、保留周期和唤醒实现留在专业设计。

Skill 指导何时检查新目标、未完问答和权限，但不保活进程。支持矩阵必须说明实际执行器是什么、如何由用户启动、何时检查更新、怎样判断失联和恢复；不能把安装 Skill、一次 CLI 调用成功或某模型有工具能力当成常驻执行已成立。

## 4. 状态、失败与安全下一步

| 情境 | 真实解释 | 玩家或 Runtime 的下一步 |
| --- | --- | --- |
| 目标已保存，Runtime 没回应 | 内容已发布，未确认读取 | 保留任务，启动/恢复执行方；不重复发布制造新任务 |
| 新版本发布，旧确认或旧行动迟到 | 旧版本有效时已被接受的结果只属于旧版本，不代表当前目标已采纳 | 按当前读权查阅已保存历史；失效后首次提交的旧问答/回执拒绝，旧世界行动仍按其权威合同裁决 |
| 两个表面编辑同一目标 | 当前值已变化，或控制资格已丢失 | 有权时保留草稿并查看差异重编；无权时只给安全阻断原因 |
| 自报完成但世界无成果 | 只是执行方报告，不能标记世界完成 | 查询权威结果、说明证据缺失或重新规划 |
| 回答/回执重复、竞答或已过时 | 原答案与处理记录不重复生效，另一设备可能已经回答 | 先回读原线程；有权时保留草稿并另提问题，过时内容不写入新目标 |
| 审批重复或已过时 | 相同决定不应再次应用，适用条件可能已变化 | 返回原处理结果或明确失效，必要时重新确认 |
| 已回答后长期离线，增量历史已压缩 | 已保存答案可能仍未接收或处理 | 从完整当前快照恢复未完线程；不显示“没有新问题”或重新发送同一答案 |
| 拒绝/超时/撤销后申请继续 | 没有有效授权；不是普通网络失败 | 保持受限部分阻塞，选择仍合法的替代或重新申请 |
| 增量游标失效或消息内容冲突 | 历史缺口或关联冲突，不能当作无新消息 | 明示问题并重读可信当前状态与未决项目 |
| 提交超时、世界结果未知 | 未确认最终结果 | 先核对原请求，不能因重连生成第二次世界效果 |
| 执行方重启或被替换 | 世界任务不变，执行资格须重验 | 验证当前绑定、目标和未决结果后继续，旧执行方不重获权限 |
| 停止委托但仍有 pending | 不再允许新的受限工作，旧世界义务仍需处理 | 保留查询与权威回执，不用停止提示伪造取消或退款 |

软指导与硬约束分开：自然语言目标的采纳并不保证策略最优或绝对遵循；可机器校验的预算、授权和目标上下文则必须由可信边界控制，不能只靠模型“承诺听话”。世界既有最终性及待决处理合同保持不变。

## 5. 可访问性、取舍与验证

关键状态不得只靠颜色或动效表示；CJK、窄屏、低高度及桌面内嵌 Web 中保留对象、目标、成本、期限、提交状态和下一步。输入法组合文字、焦点变化和重复点击不能误发消息、目标或授权；高影响决定使用明确的目标/范围确认，普通聊天发送与批准操作不可混淆。

世界舞台保持主要观察面，任务协作按上下文展开；不因增加消息就另建覆盖游戏画面的通用项目管理平台。持久化协作优先于网页直连本机进程，代价是存在可解释的读取/采纳延迟；延迟界限由实际支持组合声明并验证，未验证前不承诺实时到达。

产品评审关注玩家能否知道“我改的目标是否被读取、执行方现在为何等待、是否该由我做决定”，并从另一表面继续。自动验证覆盖确定性身份、版本、消息、权限和恢复负例；实际 Runtime 与真实 Web/桌面样例证明协作可用，权威世界结果单独对账。示例与状态表都不是实现通过证据。
