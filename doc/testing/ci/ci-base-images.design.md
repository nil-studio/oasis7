# CI 基础镜像

- 状态：proposed
- 上游要求：[CI 分级执行 PRD](ci-tiered-execution.prd.md)
- 控制与验证：[CI 分级执行设计](ci-tiered-execution.design.md)

## 上游需求与问题

`rust.yml` 的 `custody-node` 四个分片分别在临时 Ubuntu runner 安装 13 个相同系统包（含 gdb、gcc 和 pkg-config），然后下载上游预编译产物。PR #6023 的 [custody-node (2) 原始日志](https://github.com/nil-studio/oasis7/actions/runs/44297220098/job/134807710346) 显示微软 apt 源返回 HTTP 429，分片在测试启动前即失败。同一组开发包还出现在 Rust、编译指标、缓存预热、存储验收和发布打包流程。镜像将逐任务联网安装改为按镜像版本集中安装。测试内部的计划过期等时序问题沿既有缺陷独立处理。

## 镜像结构与消费边界

| 环境 | 首选处理方式 | 验收边界 |
| --- | --- | --- |
| Ubuntu Linux 运行测试 | `runtime` 目标，以 `custody-node` 起步。按实际 ELF 动态依赖、子进程调用和 smoke 结果选运行包 | 四个分片全部执行，保留测试数、结果收集及产物身份核验 |
| Ubuntu Linux 编译 | `build` 目标复用 runtime 层，增加 Cargo 构建需要的开发包、pkg-config 和通用编译工具。覆盖 Rust、缓存预热、编译指标和适合的打包 job | 核对 target、链接器、profile、缓存隔离及真实产物消费 |
| Web、治理和轻量检查 | 先核对 runner 预装工具，按实际依赖决定是否使用镜像 | 衡量冷拉取成本，保持原验证入口和结果 |
| 存储验收、发布及平台验证 | 按 job 区分普通编译和需要宿主网络、权限、Docker、签名或交付环境的验证 | 保留实际平台和发布来源合同，验证运行库兼容、包内容和启动行为 |
| WASM、macOS、Windows | 沿用现有 WASM canonical builder 和各原生 runner，分别盘点其重复安装 | 保留 WASM recipe 与确定性合同，以及各原生系统覆盖 |

以上目标共用一份 Ubuntu 24.04 基础 Dockerfile 和可审查的软件包清单。首版保持仓库固定的 Rust 和 Node 工具链选择，语言依赖继续使用锁文件及现有安装、缓存和验证入口。遇到运行镜像中缺少的原生依赖时先查动态链接和实际消费者，再更新相应包清单。运行测试镜像还须覆盖测试工具，例如 custody shard 0 的 workerd GDB 合同。核实 gcc 的实际消费者后再决定其镜像归属。

## 构建、发布与信任决策

独立工作流从受保护的 main 构建并发布到 GHCR。基础镜像以 digest 固定，记录 Dockerfile 与清单来源提交、目标架构、实际系统包版本、产物 digest 和安全扫描结果。通过定期重建或安全更新触发候选构建，由更新 PR 审查并提升消费 digest。历史已采用 digest 至少保留到迁移验证结束并覆盖回退窗口。

发布 job 单独授予包写权限。普通 PR，包括 fork PR，只拉取已发布的可信 digest。接入前验证 fork pull_request 的无发布凭据拉取路径。若镜像可见性不满足此条件，先解决分发方案。镜像只含可公开分发的构建工具与系统包，发布工作流不使用普通 PR 产物或其缓存作为可信输入。镜像改动、digest 提升和 CI 门禁接线接受独立评审。

镜像 digest 加入依赖系统库或工具链的 native 缓存身份，防止跨环境恢复不兼容产物。镜像拉取或依赖探测失败时保持 job 失败，按已有流程退回上一已验证 digest 或回退迁移提交。禁止以自动 apt 回退掩盖镜像缺件，让安装步骤重新进入常规路径。

## 迁移与验收验证

1. 盘点每个 CI job 的平台、安装入口、编译与运行依赖、宿主能力、权限和产物消费者，记录适用目标或保留理由。首批只做 `custody-node` 四个分片及一个 Rust 编译 job。在 GitHub Actions 的 `container:` 环境验证 `setup-linux-mold`、`setup-python` 和 `setup-node`，核对 `RUNNER_TOOL_CACHE` 挂载及写权限、实际运行用户和 sudo 假设。
2. 使用同一候选源码和测试选择，分别执行原 runner 路径与镜像路径。按 job 比较冷拉取和原安装耗时、总时长与失败类型，多次采样并报告样本数、中位数及尾部耗时。记录构建、扫描、发布频率与镜像大小，判断节省能否覆盖镜像维护成本。
3. 首批验收要求宿主平台合同、测试覆盖和真实结果等价，普通路径无系统包现场安装，且镜像引入的冷启动成本有可接受的实测结果。对拉取拒绝、缺库与缓存不匹配验证可观测的失败及回退路径。
4. 普通 Linux 编译、缓存和指标采纳同一镜像后，再逐工作流迁移打包与验收。发布类任务逐一核对 SOURCEPLAN、BUILDINFO、签名边界和实际目标系统启动，保持 source HEAD 与被测产物绑定。任何依赖宿主能力的例外都记录在相应工作流设计。
