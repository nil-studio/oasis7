## 1. 玩家目的与范围

玩家预期在以后几个确定窗口取得电力，供方用自己的经营安排承担届时供给责任，买方以 Data 付费。首个检查点的价值是实际收到约定数量的 Electricity；这不保证 Agent 始终在线、工业任务完成或运行时长。玩家也可以保留资金、自己发电，或届时再寻找一次性交换；这些替代方案同样不保证未来资源或成交。

`owner_checkpoint_power_service_v1` 只支持同一 canonical world/branch 中两个不同个人当前 owner、各自控制的两个不同 Agent。双方签署 2 至 16 个有限检查点；交付时必须符合签署的接收位置、当前共址与适用权限。供方不预存未来电力，也不能把尚未收到的价款或电力当作可用余额。组织、多方联合服务、物料运输、设施维修、借贷、无限期承诺和自动续期沿原范围另行设计。

此 profile 将整段服务保留为跨时间、可失败的承诺；每一次被接受的实际交付分别原子结算。一次检查点成功不代表其余检查点必然成功，也不把已交付结果重新挂入可重复执行队列。

本文只形成 CR-001/CR-002 的有界专业承接。当前 native Service 仍明确拒绝，受保护 hold、完整履约消费者、个人服务裁决名册和可靠抽签来源尚未成为本 profile 的可用实现；实现/治理激活继续分别取证。[native 分类与冻结](../../world-runtime/prd.md#native-surface-分类与冻结规则)仍适用，本政策不选择 SC32 pilot、不扩展旧 EconomicContract 语义，也不宣称通用争端、情境声誉或整个 SC-14 完成。

## 2. 明确条款与有限时间

### 2.1 必须共同签署的内容

| 条款 | 决定与拒绝边界 |
| --- | --- |
| 主体与责任 | 世界/分支、供方和买方的个人主体、Agent、当前控制来源、固定接收位置、原合同 lineage；原主体责任不随 Agent 换 owner 自动移动。 |
| 服务单位 | 每检查点 `q_i > 0` 个 Electricity 最小整数单位；单元 Data 价款 `p_i > 0`、单元 Data collateral `c_i > 0`。检查点价款为 `q_i × p_i`，抵押为 `q_i × c_i`；不隐含兑换率或浮点四舍五入。 |
| 时间与程序 | 各检查点 `opens_at_i < due_at_i`，相邻交付窗口不重叠；第一个窗口晚于激活提交。正整数 `Q` 表示双方接受的程序时间单位，使用既有 canonical world tick。签署全文包含下表导出的全部绝对截止。 |
| 费用与资金来源 | 分别披露价款、抵押、operational fee 与 closure fee 的资源、来源、付款人、可消费命令/次数上限和余款去向；交易费按其合法来源确定付款方，Kernel/module 的实际 artifact-owner payer 必须是已签当事方。不得从价款或抵押暗扣运行费。 |
| 授权与检查点条件 | 当前所有者、适用资源/方向授权、位置、余额和受保护占用；接受与交付各自需要的条件明确分开。签署不是绕过以后提交时的授权与安全校验。 |
| 失败与处置 | 原范围修复、终止、责任认定、最小保全、有限申诉、显式继受，以及绝对截止仍无有效责任结论时的中性尾部处置。明确失败不保证全额补偿。 |
| 争端前置 | 本地 jurisdiction、服务裁决权限 artifact、名册和抽签政策；不得用组织身份、运维权限或未核实名册补齐。 |

上述字段连同政策版本必须进入同一不可变条款与可读正文。非绑定草稿、预览、offer、双方接受及接受待校验均不锁资源、不扣费、不创建服务责任。任一当事方显式激活时，runtime 重验当前条件并一次提交全部必要 hold、义务与 receipt；不完整、漂移、溢出或预算不足均原子拒绝。旧接受不能同意未显示的新条款。

### 2.2 不可重置的程序窗口

`R_i = due_at_i + 2Q` 为原范围修复截止。以下均从签署的 `due_at_i` 导出，不以开案、重连、补证、补位、继受或新请求为起点；所有窗口为左闭右开，到截止本身原窗口已结束。

| 窗口或边界 | 固定规则 |
| --- | --- |
| 正常交付 | `[opens_at_i, due_at_i)`。 |
| 原范围修复 | `[due_at_i, R_i)`；不延长服务量、不改价格、不重发已完成单元。 |
| 争端登记与证据截止 | 从 `due_at_i` 起，可提交具体争点；最迟 `R_i + 2Q` 关闭登记与普通补证。迟提交只剩原窗口余量。 |
| 初审截止 | `R_i + 4Q`；无有效初审不判任一方胜诉。 |
| 一次程序性申诉 | 有效初审发布后 `Q` 内，且最迟 `R_i + 5Q`；不能通过重复申诉续窗。 |
| 复核截止 | `R_i + 7Q`。 |
| 绝对处置上界 | `R_i + 8Q`；是否提出争议均采用相同尾部规则，不形成无限期业务保全。 |

激活前必须能说明 `Q`、当前权威 tick、窗口剩余量及当前世界时间解释的来源；未知或无法读取时不绑定。tick 不等于客户端 poll、区块 slot 或现实秒，不能用客户端时钟补算、倒退窗口或承诺墙钟 ETA。世界没有新的 canonical tick 时窗口不凭现实时间消耗；世界继续运行而玩家个人离线时，原窗口继续。任何参数或导出截止溢出都拒绝绑定。

`Q=8` 仅用于下游手算与故障样例，不是生产默认值，也未经真人或裁决者响应验证。双方在已声明的技术上限内选择并明确接受 Q；后续实际平衡以对应候选的签署理解、响应和履约证据复核，不能把测试 tick 数直接推广为可用生产时长。

## 3. 检查点、交付与责任证据

每检查点单元空间为 `[0, q_i)`。一次交付使用其中尚未处置的不重叠半开整数区间；区间不可重复、越界或借新请求重用。`fulfilled` 量只来自该合同认可的 canonical 交付 receipt，缺少 receipt、仅有在途 intent、排队或旧 action ack 均不算交付。

提交时重验供方电力、双方控制/授权、签署接收位置与当前共址、买方价款 hold、供方对应抵押 hold、当前争议限制及全部费用。一次成功同时转移实际电力、支付该区间的 Data 价款、释放对应抵押占用、处置全部费用并记录履行量与 receipt；任一前置或写入失败整次不变。已付的价款不能回头为同次原本不足的资金或费用融资。

释放 hold 只使本来属于该来源的余额重新可用，不增加 gross；消费 hold 同时减少原 gross 并转入合法收款方或 treasury。价款、抵押和两类 fee 预算分别核对，不能只看一个“总锁款”。精确余额/预算与命令上限由 [resource holds](../../world-runtime/runtime/checkpoint-power-service-fulfillment.design.md#service-resource-holds) 和 [fee budgets](../../world-runtime/runtime/checkpoint-power-service-fulfillment.design.md#service-fee-budgets)唯一维护。

适用交易费按原检查点、原 fee leg 的累计业务量计算增量，拆分交付、修复、换请求或继受不得重置累计量而少缴；同量整段与拆分的交易费一致，真实成功调用次数不同导致的 mandatory metering 可不同。抵押赔付若依法适用费用，使用单独声明的 closure 交易费预算，不能从买方应得净赔付中暗减；免收同样需要明确合法适用依据。

`due_at_i` 到达只产生 `checkpoint_due` 的可读条件；尚有单元未完成时区分已交付量与剩余量。它不自动罚没、生成债务、改变声誉或把余量判为 `defaulted`。`partial` 与到期、争议和责任是不同维度，不能用全合同一个状态位覆盖。

责任认定至少核对以下证据，不能由 LLM 推测或当前单张快照替代：

| 事实 | 认定依据与限制 |
| --- | --- |
| 已交付与余量 | 原合同单元账本、交付 receipt 和完整 canonical 结果；不能把客户端未见响应当作未交付。 |
| 接收条件 | 相关窗口内接收位置、买方当前授权/接收条件及其变化的可核验来源；单次共址或 grant 失败只说明该次不能执行。 |
| 供方责任 | 事前约定范围内的供给风险、实际可执行条件、供方确认或可审计行动/资源事实。证明买方合法接收与执行条件具备后，供方自身资源/安排不足可以构成约定缺供责任；证据不足只保留未履行事实。 |
| 系统与保全影响 | 正式执行、结果读取与救济入口的权威可用性、已确认保护范围；不可用、来源缺失或有效 stay 造成的不能交付不得直接归责供方。 |
| 已确认责任 | 有效同版责任承认/和解，或按第 5 节形成的最终裁决及其未执行量；后来的撤权、下线、重签或请求失败不清除它。 |

正式 `defaulted` 与抵押赔付只能来自双方对精确残余及处置同版明确签署的责任承认/和解，或本政策有效 panel 决定依固定程序成为 final。时间、缺供计数或通用 handler 只能生成待判断事实，不能创造罚没权限。裁决不能重写已确认交付、反向扣回已合法收到的电力/价款或改动第三方余额。

责任承认也须对应真实已发生的原约事实；修复截止前自愿终止并约定补偿，可以记为明确和解/终止，不能伪写成尚未发生的缺供 default。

请求认定供方缺供责任的一方承担证明责任，panel 只有逐项确认下列条件，才能把对应单元裁为供方违约：原条款确已生效且该净量义务仍归该供方；原修复截止已过且完整 canonical 账本证明未履行；买方在相关可履约窗口满足原约接收义务，且没有买方阻碍、有效保全或系统不可用足以解释缺供；同时存在供方对原范围的有效签署拒绝/责任承认，或能够归责供方的资源不足、主动失权/停供等具体权威事实。普通聊天、缺席、当前余额、一个失败 ack 或推测的“本来能交付”不足以独立满足这些条件。

例如，买方接收与正式执行的完整来源均成立，供方在合法交付机会提交的原请求因其 Electricity 不足而被权威拒绝，随后至原截止仍未补足且没有相反证据，可以支持该剩余范围的责任判断；若买方在该窗口主动移离接收位置、撤去必需接收授权，或正式执行可用性/相关历史覆盖未知，就不能从同一缺供量直接作此判断。反证必须进入同一证据集合和理由；不能以买方或供方没有继续回复替代证明。

<a id="service-policy-remedies"></a>
## 4. 玩家恢复选择与终态

| 选择 | 可执行条件与实际后果 |
| --- | --- |
| `repair/reperform` | 仅对原未交付且未被保护/结清的单元，在 `R_i` 前、当前交付条件满足时执行；仍用原价、原单元身份、原期限和费用限制。可分批补足，成功次数和费用受原预算约束，失败不重置额度。 |
| `terminate/settle` | 双方对具体残余的同版终止/责任处置明确同意，或原签署的到期规则已具备。未交付价款返原买方；未判罚抵押返原提供者；有效赔付按已确认处置执行。不能单方取消已成立责任或已提交但尚未知的交付。 |
| `dispute/preserve` | 符合第 5 节的具体争点和受理条件，仅保护直接相关的未交付单元、价款/抵押及不可逆动作。其他单元、检查点与无关合同按原条件继续。 |
| `replace_with_explicit_successor` | 按第 6 节由原供方、买方和接替方同意，仅转交可独立、未交付且无未决争议的范围；不是旧 Agent 控制权自动转让。 |
| 停止或重新规划 | 无安全交付/修复路径、操作费用不足或授权失效时停止新风险，保留原件查询、已确认结果和合法结清路径；不能无限静默重试。 |

费用不足不自动消费价款或抵押，也不授权第三方代扣。举证、case、投票和申诉的有限份额按原合同/检查点/阶段/actor slot 分别保护，不能被交付、重试或一方补证用尽而使另一方失去原定程序；次数与资源上界以 runtime 的签署 manifest 为准。已激活的合法退出必须由签署的 closure 预算和兼容 drain 路径支持；升级不能用新费率追补旧合同或挤占已承诺结清资金。未消费费用只按原来源解除保护，已消费合法费用不因服务失败自动退回。

全部单元有交付或合法处置结果后，服务义务可以终结；未付款的已确认赔付、原受益人无法安全收款的返还和费用结清仍分别显示，不把“服务终止”写成“资金全部已到账”。若原 Agent 已换 owner，原主体的返还权不能直接记入新 owner 可支出的余额；按 runtime 原来源返还合同保持 `return_pending`，待合法收款路径恢复。

到达绝对上界时，先查询完整 canonical 交付/案件/裁决结果，处理已提交但客户端尚未知的事实。只有可证明仍无有效责任结论的未交付单元，才能按激活时已披露且双方已签署的中性尾部规则结束：未交付价款归原买方，未判罚抵押归原提供者。是否开案、谁先开案或是否申诉不改变该规则；既有 final、final 待付款、已确认和解及其责任优先保留。结果来源 unknown 不等于“没有裁决”，也不能据此释放。

中性结束只是本有限供电 profile 对未决尾部的风险分配，避免无限期业务保全；它不证明供方没有违约或任一方清白，不删除失败事实和已确认责任，也不保证争议事实得到裁判或合作损失获得全赔。到期本身不假装已经执行资金变化：只有合法有预算的真实提交才产生结清 receipt，否则显示 `eligible_for_disposition / outcome_unknown / return_pending` 中的真实原因。

## 5. 有界本地争端程序

### 5.1 权限、名册与抽取

个人服务合同必须单独取得原世界治理程序认可的本地服务裁决授权 artifact，绑定 world/branch、jurisdiction、profile、政策版本、合法名册来源和处置资产/上限。这里的授权不从组织 charter、当前多数、名望或 API 管理员身份推导；不新增全球法院。管辖位置在签署时固定，履约者移动或接替不能改选有利辖区。

名册最多 64 个可核验 controller 主体；同一 controller 只占一个位置。排除双方、拟接替方、已确认的同控制/关联利益主体和本案直接经济受益人。缺身份、冲突范围或名册有效性证明时不把该人当作独立合格者。新合同须有至少 6 个可证明符合条件的候选，以支持初审 3 人和不重复的申诉 3 人；这不保证以后始终有足够候选。

受理 case 时固定候选名册承诺、原案身份、政策和待抽取轮次，再消费首个由获准来源产生、可验证且在该承诺提交前不可预选的随机结果。初审、补位与申诉共同消费一份固定排列；资格失效或冲突者被剔除后顺延，不重抽、不让请求者挑选随机轮次。更换请求 ID、重复提交、撤回重开、续签或继受不改变原案抽样。

当前仓库未提供可直接复用的本 profile 随机裁决名册与可靠随机 authority。实现激活必须具备对应授权、完整名册证明、可验证不可预选的抽签及消费者；public block hash、客户端随机、单节点随机或模型选择均不能代签公平抽取。依赖缺失时不得激活新合同；已激活后失效按本节原固定截止处理，不能临时任命另一种有权者。

### 5.2 受理、证据与最小保全

每 `(原合同 lineage, checkpoint)` 最多一个争端 case。申请须来自原当事方或仍有本案责任的合法主体，给出具体争点、精确未交付单元和可核验事实引用；仅说“不同意”、空白证据或把未收到客户端响应当失败，不足以受理。登记请求不产生控制权、赔付或保全；只有资格、事实和范围校验通过的权威受理 receipt 才建立 stay。

每个有责当事方在初审和程序复核各最多提交 16 个权威 receipt 引用及有界说明；阶段份额分别保护，初审用满不剥夺原定申诉。补证更新原案，不更换 case、抽样或截止。证据只能说明原签署义务、交付、接收、授权、系统可用性或程序事实；不能凭无关声望、外部声量或私有模型叙事取得权利。证据截止前双方合法精确争点合并同一 case；到原截止一次冻结受理范围及统一证据 root，之后拒绝普通扩范围/补证。公开面只披露必要范围、原因和结果，个人材料按权限读取。

stay 只覆盖与具体争点直接相关的未交付单元及其未结算价款/抵押，不冻结其他检查点。既有成功交付不转回待决；保护造成的暂停不能再作为供方缺供的单独依据。形式不完整、超窗或同事实重复请求不叠加 stay，也不阻止按已有合法证据推进。缺席、下线、撤权或拒补非必要材料不否决现有证据，不产生重新计时或中性退款资格。

### 5.3 初审、有限申诉与最终结果

初审由 3 名合格且无冲突的成员进行，只能在原证据截止之后、初审截止之前，针对已经冻结的整案受理范围和证据 root 投票。至少 2 人对同一 typed disposition、精确范围和证据依据作出有效签署才有决定；不能提前耗尽唯一轮次，遗漏仍在合法窗口提交的争点。成员无权更改单位价款/抵押、扩大责任对象、创造新债、追补收益、处置其他合同或改写世界历史。

允许的裁决只处置未交付单元：证明原约供方缺供责任的范围，退回该范围价款并将至多对应 `c_i` 的抵押给买方；责任未获证明或经证据确认不归供方的范围，终止并原路返还价款与未判罚抵押。已合法消耗的费用保持原事实，不另给 panel 奖励或按罚没分成。混合结果必须把单元范围分开，不使用全合同平均罚款。

有效初审先公开为待程序窗口结束的决定。无合格申诉时，原申诉窗口结束后成为 final；有合格申诉时，原决定继续保留，最多等到固定复核截止，由有效复核结果替代或按仍有效的原初审 final。申诉登记、补证或复核者未回复本身都不撤销原决定。

每案仅一次程序复核，限于可核验的授权错误、已提交证据遗漏、利益冲突、超范围处置或可验证错误。各方都有原独立份额在原申诉窗口内提出具体错误和证据，合法理由并入同一轮，不以第一个申请剥夺另一方陈述；不能用重复争论或新的无关诉求重审。复核在该原窗口结束、程序争点和证据 root 固定后进行，不新开窗口。原初审成员、当事方和有利益冲突者不能参与复核；从原固定排列中顺延组成另一组 3 人，仍须至少 2 人同意同一结果。

只有有权复核确认具体程序错误，才能使原决定 invalid 或作有界纠正；无有效复核结论时保留仍有效初审。已 final 的决定不因到达尾部、再次申诉或支付尚 pending 而消失。若原决定已被合法确认 invalid，而固定截止内没有替代的有效决定，才将相应未决单元交给第 4 节已签署的中性尾部。新发现且超出本程序的世界错误按原有权纠错入口处理，不通过重开此案复制抵押或改写历史。

名册不足、随机证明不可取、无人投票、无 quorum 或预算/合法提交暂不可用时，读面分别说明原因和原绝对上界。不存在“默认供方胜诉”“默认买方获赔”或永远续窗；有有效决定先尊重决定，没有有效结论的尾部才按原签署风险分配处理。

## 6. 显式继受与续期

v1 一次继受必须接替该合同全部仍可继续履约、未交付、未已判罚且无未决争议的范围；不能只选其中一部分，再让原供方并行供给余量。原供方、买方和接替方须对同一继受条款明确接受，绑定原合同/单元、原责任边界、新供方的当前自有 Agent、位置、资源、全部费用及原固定截止。接替方须是与买方不同的个人主体；不借接替创造自我交易奖励或额外额度。

一次成功交接必须同时确认新方资格与当前授权、补足其对应抵押/费用、调整旧方可解除的占用、切换这部分未来履约/收款责任，并留下原/新主体可读 receipt。旧方已履行、已发生违约或未决责任、原价款来源、原单元 identity 和累计量保持；原请求不迁移到新主体，新请求也不能继承旧队列位置或重复交付。

若旧冻结/争议范围仍可能解除保护并在原修复窗口内继续交付，而其处置尚未明确，先拒绝继受，不能借交接强制取消该义务。只剩审理、赔付/返还与结清的旧冻结、争议或已判范围继续绑定原责任和 hold；成功交接后旧供方在该合同不再取得新交付入口，解除保护也不自动恢复旧供方供给或给新方添加未签义务。本 profile 不支持同一合同并行多供方；确需独立新增供给时另行明确签署新合同，不能覆盖旧单元、责任或窗口。继受次数、provider history/程序 actor slots 均受激活时签署的有限 cap 约束，换主体或接替不重置；到达 cap 后保留原合法结清，不接受额外继受。

接替不自动转让旧 Agent、个人 credential 或情境声誉。旧 Agent 控制发生变化时，新 owner 不因持有 Agent 就接受原服务责任或取得原抵押/价款返还。组织连续性如参与外围处置，仍消费原[处置顺序与资金来源](../../world-runtime/runtime/organization-continuity-and-disposition.design.md#des-wr-oc-001)，不能替个人合同生成同意。

固定 artifact-owner payer 与真实费用来源必须在继受后仍合法。如果原供方也是 payer，而新范围无法同时满足实际付款人、已签当事方和受保护预算条件，交接拒绝并保留原状态；不能暗扣已经退出的第三方。买方为 payer 的合法继受可以保持该原来源，但新方仍须承担明确属于自己的资源和抵押。

续期是基于当前状态的新报价、新合同与明确接受，只创造新披露的服务范围。它引用原 lineage/结果，但不延长旧检查点、不释放旧责任、不重用已交付单元、旧抽样或旧费用额度。反复取消/重签、换 owner、接替或改请求 ID 不能洗掉原失败、案例和责任链。

## 7. 玩家读面与专业验收

确认前的 `service_commitment_preview` 必须让当事人比较：首检查点实际电力价值、价款与资金占用、未来供给不保证、当时全部费用与期限、供方抵押和可赔上限、修复/终止/争端/接替的真实可用条件，以及自行供电、等待或即时交换等无合同替代路径。中性尾部不保证获得责任判定或全额损失补偿，必须随签署正文显式可读；推荐动作不代替接受或激活。
