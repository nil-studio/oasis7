## 2. 接受前必须看懂并明确同意的内容

service_commitment_preview 在当前权威切点只读展示：全部相关主体与当前代表权限、服务目的、原对象/来源、各检查点的可用价值、必须完成的工作与接收条件、正常/补救窗口、第一笔不可逆成本、价款和 collateral、全部执行/程序/关闭费用、风险由谁承担、哪部分可取消、无合同的替代路径，以及推荐理由和有效边界。预览、offer、接受待校验不扣款、不建 hold、不锁工作或容量、不产生责任、排队、奖励或声誉。

同一不可变正文必须固定以下内容；任何决定性项目缺失均不提供可接受的省略版：

1. world/branch、服务实例、政策版本和 exact obligation lineage；当前各角色及其权利来源。
2. 每个检查点的正常窗口、净履行单位、允许部分履行与否、原领域执行/接收谓词、不可分共同工序、先后依赖和已发生事实的归属。
3. 每个价款单元的 payer/source、受款人、资源种类、整数金额和赚取条件；本次 collateral 与责任上限逐责任主体、受益范围、风险项及资源列明。
4. 可用的真实物料、设施/账本/位置权限、开始及完成所需容量、费用 payer、完整调用/资源上界和独立关闭资金；未预留的未来条件明示为条件风险。
5. 归责所需证据、风险分配、最小保全、合法本地 panel、一次程序复核、固定尾部、停止与继受条件。
6. source_projection_use 所允许的情境、用途、受众与披露边界；同意形成服务不自动同意公开私密原件或跨情境评分。

请求的完整 scope、effects、interval 和扣付范围必须被当前授权与接受包含；提交时不得取交集后静默缩小或更换对象。更窄方案只能单列建议，由相关主体明确重提、重新审核接受。续期、改道、换目标、加角色或新增风险同样不得借“修复”标签改写原条款。

激活由共同形成验证和本服务完整准备在同一根事务中完成。active receipt 同时建立原义务、真实占用、狭义处分授权和责任来源；缺任何必需接受、当前权限、资金、合法管辖或完整退出能力时全项不成立。接受不会预付未来服务成功，也不会把未生产的材料、预期运输到达或未来收入当当前资金。

## 3. 个人、组织与多方责任

每个义务 slot 固定责任主体、实际执行者角色、接受服务者、价款 payer、资产/材料所有人及必要配合方。一个主体可以承担多个明示角色，但角色不能相互代签；多个别名、Agent 或岗位不增加同一主体的预算或程序机会。组织依[当前业务代表 mandate](../../world-runtime/runtime/agent-mediated-contract-formation.design.md#contract-formation-principals-mandates)作自己的承诺；使用成员或第三方财产时，该财产权利人的真实授权与明确接受仍是独立前置。

责任按原义务和风险项分别成立。没有明确接受的共同责任条款，不因同组、同组织、相邻工序或同一受益人而承担他人的债。共同不可分工作必须在激活前列齐各角色、完成谓词、共同停止边界、逐方责任 cap 与资金来源；不得由事后多数投票把全部损失分给较富的一方。允许的分担向量在接受时固定，逐风险项合计不超过已接受总额；归责还须证明该方的行为/未履行与该损失的因果关系。一个损害已有实际补救/赔付的量从尚可请求量扣除，不把同一损失向多方重复全额领取。

付款或组织资产被托管不改变其原权利人。组织处置继续按[原清偿政策](gameplay-organization-continuity-policy.prd.md#oc-policy-estate)先保护既有合同、第三方托管、债权与责任，再处理业务和剩余；服务不能写“无其他责任”代替完整原清单。个人控制转让、设施出售、组织换代表、解散或资不抵债不抹去原责任，不向新 owner 或独立成员自动追缴。已发生的有权债权超过当前实际可付量时保留 confirmed_unpaid 与原主体/来源，不能用终止或中性尾部免除；本服务不产生超出已接受责任范围的新债务。

### 4.1 运输的物权、保管与有限退出

运输必须绑定当前合法路线、源/目的 ledger、实际货物所有人、沿途保管者、接收资格和有限仓储/terminal 容量。未预留的容量和未来路线可用性明示风险；不得把签约变成硬交付保证。第三方寄存货物与承运人、仓库或付款人的财产分别记账，保管转移不自动转移所有权，资金 escrow 也不替代货权证明。只有原合同明确的里程碑和当前合法接收/结算可以改变对应货权。

拒收、迟到、已确认损耗和取消分别保留原 receipt；补运、改道、返程或转交保管必须使用真实剩余货物、新的路线/容量/费用及必要接受。原货物已丢失时不能释放一份可再次运输的库存；返回也是实际物理过程，到原合法接收 receipt 才记返还。合法出发前可释放未消费预留；出发后只能走已签且当前可执行的安全处置，不因服务终止立即解锁仍承担保管/损害责任的资金。

条款允许部分履行时，只按规范化、不重叠的实际单元结算。拒绝与已完成或已处置范围相交的整项请求，不偷偷裁剪。禁止拆分交付的 whole 单元在完整谓词前不赚取该单元价款，但已经发生的工作和成本仍须保存。一个角色可已完成自己的工作而共同成果仍未完成；不能把下游失败改写为该角色从未履行。

价款赚取只能使用事前明示的 own_completion 或 joint_completion。后者明确写出依赖和退出时哪些已发生工作仍应支付、哪些价款仍是有条件；不能在失败后临时定价。每笔已赚价款、未赚价款、已支付、受争议和待付款分别保留。确认履行、消费该价格/保证范围、累计费用、实际支付或明确待结算权利及 receipt 必须关联同一原单位；不能以网络 ACK 认定收到款。物理长流程的已发生结果不能因服务结算暂时受阻被删除；合法资金结算仍需原 authority 实际提交。

已完成价款不因原窗口到期或另一单元 default 自动退回。价款、责任 collateral、执行费用、程序及关闭费用分账；抵押不是免费奖励。费用按完整合法规则、实际调用/交易和已同意 payer 结算，拆单不重置累计交易费的原基础；不把上界当实际收费。

## 5. 失败后的四条完整路径

正常窗口为各单元已签的 [opens, due)，Q 为已接受的正整数 canonical world ticks，修复终点 R = due + 2Q。Q 的实际值和绝对时界进入签署正文；本文不把测试 Q 映射成现实秒数。读取 due 仅提示到期，不自动违约、罚款、欠费或声誉变化。

| 玩家选择 | 准入与处理 | 保留的事实 |
| --- | --- | --- |
| repair/reperform | 只处理原未满足、未被不兼容保全的单元，在 [due,R) 及原权限/预算内真实补做；预声明的重运/返工引用原失败和新的实际成本 | 原完成、沉没成本、损失、顺位、deadline 和责任不清零；新损坏/改用途必须另报新工作 |
| terminate/settle | 任一方可停止自己尚未发生的新履约；合同按已接受的停止/取消 schedule 或全部受影响方的同版和解处置原范围。原领域安全停止与在途处理仍需真实完成 | 已完成应付款、合法取消成本、已确认赔付、未决货物和 original-owner 返还保留；停新不等于全退款或无责 |
| dispute/preserve | 有权入口基于具体原件建立最小 stay；只阻断与争点直接冲突的新承诺、处分和不可逆效果 | 无争议且仍安全可履行的义务继续；申请不自动获胜、不建立全合同冻结 |
| replace_with_explicit_successor | 仅对明确可分且无重叠未知执行的剩余义务，按 §7 同版接受、真实资源与唯一权限交接 | 不转走旧债、已发生损失、未决赔付或前任 credential；旧请求不作为新主体同意 |

取消 schedule 必须在接受前逐阶段给出结果：未开始且未消费的资源原路释放；已经开工的材料/能源和合法费用不退；在制品、在途、buffer/terminal-pending 按其原有限停止/完成/返程/保管方案继续；未赚价款在不承担既有权利后释放；已赚价款和预声明有上限的取消成本仍结算。取消成本只能来自真实已发生且由条款允许的成本项目，不按任意“预期利润”追偿。原受益人无法安全收款时显示 return_pending，不把退款给新 owner。

归责需要同时证明：原有效义务、完整窗口/当前条件、明确未满足单元、接收/配合条件及可用性、预声明的责任或风险触发、该方因果和精确损害。provider 在其接受范围内明确拒绝、挪用保留输入或未履行已承诺可控准备可成为证据；receiver 撤去必要准入、不可归责原领域损耗、合法保全与系统不可用必须分别考虑。缺席、未回复、当前余额不足、单次失败、低声誉、聊天指责或历史覆盖未知均不单独构成 default。

责任 cap、原接受的风险分担和实际尚未补偿损害共同限制赔付；实际付款另受对应真实受保护资金限制。不足保持已确认未付和原责任，禁止使用其他单元本金、成员个人资产或未实现收入填补。恢复/赔付本身也是新事实，既不擦除失败记录，也不让已补偿量再次获赔。

## 6. receipt-first 本地程序与固定尾部

本程序仅处理本合同已接受的义务、风险、价款、托管及责任 cap。激活前必须有治理明确认可的 local-service.review 管辖、政策、地域/事项/资产边界、完整名册和不可预选的随机来源；现有组织连续性、RD、许可、战争或社交 panel 不能代签。本文规定目标规则，不宣称这些运行前置已经具备。

一个原 agreement/checkpoint 只有一案；全部合法争点在原窗口并入。原义务 scope、当事人角色、历史责任和固定截止不因换 request、撤回重开、继受、别名或续签重置。初始/继受时必须保证全部仍有责任或资金权利的主体有独立程序份额。每主体每阶段最多 16 个必要证据引用；两个阶段分别保留。一般重复争论不获得新有损重审。

| 边界 | 统一规则 |
| --- | --- |
| 受理和初审证据 | 激活后可登记有具体事实的原范围争点；至 R+2Q 前接纳，之后冻结整案 scope/当事人/证据 root |
| 初审 | 冻结后、R+4Q 前产生；3 名无冲突者中 2 人对同一精确 typed disposition/root 一致 |
| 一次程序申诉 | 从初审决定 D 起至 min(D+Q,R+5Q) 前接纳；只能针对权限、原已交证据遗漏、冲突、越界或可验证错误；完整原申诉窗关闭后冻结复核 root |
| 复核 | 与初审不重叠的另 3 人、同样 2/3；R+7Q 前结束。申请本身不撤销有效初审；只有有权纠错能替代/撤销 |
| 程序尾部 | R+8Q 到达后核全原请求/决定/执行事实；有效 final、和解或仍有效初审保留。可证明不存在有效改变原基线的结论时，按已签中性停止/资金和物理处置规则结束程序保全 |

所有窗口为半开区间，等于截止不再接纳该阶段新输入。处分只有在该决定已 executable_final 时执行：原申诉窗已闭且无有效待决复核，或有效复核已完成，或原复核截止后原仍有效初审依法终局；不能在初审发布时抢先划款。相同 tick 按 canonical 顺序核当前时界，不以客户端收到时刻插队。中性尾部也须实际合法提交；unknown 不等于无案/无债权。

名册最多 64 个不同 controller，自激活就须至少 6 名有资格且无冲突的候选。排除全部当事方、相关组织代表/控制人、原/新继受方、直接经济受益人及相关批准者；资格未知不得计入。先固定原 case/名册承诺，再消费既有获准随机源的首个合格后续结果形成一次排列；补位和复核沿原排列，不重抽。资格后来失效只能按排列补位；候选、随机或 quorum 不足不产生默认胜者或无限延长。

只允许确认完成/未满足、按原条款修复或停止、确认逐方责任、在已接受 cap 内结算、原路返还和解除精确保全。不得新建权限、分配 R&D 份额、改声誉评分、没收第三方资产或重写既成世界历史。无证据的部分不判罚；确认的赔付未到账不被“程序关闭”擦除。

程序受理不自动获保全。保全申请须同时有申请人的直接原权利、具体原争点、准确原资产/单位和原件证明的冲突不可逆效果，经受权服务规则核验后才在原受理/证据/申诉迁移同根成立；不新增无上限独立保全调用。缩小/解除随原和解、终局或有权履约/关闭处理，源更正须在效果前重验，不为投影刷新延长程序。程序保护以具体原资产/单元及冲突效果为依据。共同不可分工序若不能安全拆开，说明必须保护的最小整组及其因果；其他工序和合同继续。程序到界停止新争点，原物理在途、真实有效权利和提交未知按原恢复继续，不能为了显示有界而伪造物品返还或资金结清。

<a id="continuing-service-succession"></a>
## 7. 显式继受、控制变化与续期

继受先列完整受影响 scope：未满足单位、必须共同交接的工序/托管物、未来价款、真实资金、物理/执行权限和被改变的接收条件。原履行方、新履行方，以及付款、受益、财产或风险被该交接改变的每个主体均须经共同形成接口明确接受同一内容；不得用“多数已同意”代替必要权利人。已存在且足以覆盖本次范围的真实来源授权可以引用，不重复索要一份无新增用途的第三方同意。

可分单元允许部分交接；不可分工作、尚可恢复原履约的争议范围、未确认的在途效果不得切开或并行交给两人。先对原未知结果查询或完成原安全处置，再交接真正剩余。新方先具备自己的当前 mandate、执行能力、真实输入/容量、责任抵押和完整费用；同根终止旧范围的新执行权、建立新范围、调整相应 hold 并留唯一 receipt。旧方已发生的责任、程序份额、待付款和原材料/托管权益单独保留。

原 deadline、unit identity、已完成数量、已用预算、case/随机、累计交易费和反重放边界全部延续。继受次数与历史主体槽在初次接受时有界保护，耗尽不得通过新别名或改组织重置；必要的新同意只承担明确新增的后续范围，不对旧未知付款补签。普通 owner 或组织代表替换只改变当前可执行资格，不自动改变合同责任主体或收款权。

续期是一份当前报价、全部必需接受与新 receipt 的新披露范围，引用原 agreement/obligation 关系，不继承旧顺位。旧合同的完成、未付、争点与已发生费用继续可查；新合同不能再次消费原完成 receipt、把旧成本包装成新投入或洗掉责任。无安全能力时可停止新增承诺并重规划，不能强制选择外援或签新约才能取回原权利。

## 8. 费用、范围上限和关闭

原[真实 hold](../../world-runtime/runtime/checkpoint-power-service-fulfillment.design.md#service-resource-holds)与[共同累计暴露](../../world-runtime/runtime/agent-mediated-contract-formation.design.md#contract-formation-cumulative-exposure)分别约束资产和授权。每原 payer/source/resource 都要独立足额；hold 不是第二份余额，退款也不重置已经实际使用的授权额度。没有合法 fee authority 的零费同样不能默认为允许。

当前合同最多 16 个参与主体、16 个检查点、64 个固定义务 slot；历史与后继责任主体合计最多 32 个。允许的继受/物理工作/修复次数、原程序机会和完整关闭次数在接受前定额，不能先激活再发现最后一次返还无预算。数量和时期可在这些工程上限内选择，规则不宣称生产价格、费率或玩家负担已经平衡。

普通工作费用、每主体两阶段程序费用及安全关闭资金分别保护。普通次数或资金耗尽停止新工作，仍须保留所有既有角色的原件查询、停止新增权限、完整安全处置、最终决定/支付和原路释放。精确重放不再收费。未绑定提议/接受、静态准入拒绝和整项 activation 拒绝均无新业务扣费；激活可真实执行受控 L2 sandbox 并暂存计量，只在完整成功提交时扣实际费用，不能为零扣费把服务规则移入 native 旁路。active 后，只有已签明示允许计费、确实计算且以原 attempt 结果同根提交的业务尝试可保留其实际计算费；这不把旧供能 v1 的确定拒绝改成收费，也不允许普通权限/预算拒绝、无结果、模块 trap 或重复请求收费。未发生的调用不能收费，unknown 不猜为零、不重调。

停用/升级不得使旧合同无法读取、履行已成立的狭义处分、结清或恢复。改费用或执行来源须有当前合法兼容 drain 或必要的新同意；不能事后涨价耗尽已保护的出口。责任、真实物理结果和资金是否到账分别关闭，不通过删记录、TTL 或回滚快照获得结案。
