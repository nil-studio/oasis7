# 开发流程规范

本文定义 oasis7 日常开发、验证、评审、合入和交付的通用规则。目标是让修改容易完成、结果可以核实，并把保护措施放在实际需要它们的操作边界。

## 1. 适用范围与规则边界

本文是通用开发流程的唯一规范。脚本、CI、AGENTS 和 skills 负责执行或说明这些规则，不得另设任务准入、审批、状态、证据材料或完成条件。发现不一致时，应修正对应实现和入口，不得用额外证明补偿规则冲突。

每项工作有一个明确负责人，可以是人或主 Agent，直接负责本项分析、设计、实现、自测和组织适用评审。专业角色提供按需参考的关注点，不构成固定交接链。

Git、PR、实际 CI 结果和评审记录承载代码交付事实。未拆分的简单修改可以只有 PR；拆出的独立开发任务使用[原生 sub-issue](#code-task-sub-issues)，Project 按需使用。本地开发、测试和 PR 验证不依赖 Project 可用性，不要求额外任务标识或工作区登记。

按用户选择的工作类型交付：分析和方案请求交付结论或方案；实施授权覆盖同一目标和范围内的修改、测试及修复。提交更新、测试失败或 main 前进不要求重复确认。扩大目标或范围、增加尚未授权的外部影响、改变交付对象时，才确认新增部分；已经明确授权的动作不重复申请。

修改必需检查或合入策略时，必须同步规范、实现、执行入口和适用的 GitHub 保护设置，并核实它们一致。当前生效的保护规则始终约束实际合入；只修改文档不能解除已有强制检查或代替设置变更。

### 1.1 语言与写作要求

Trace ID: O7-REQ-45815c91-fc25-43b0-b91b-e0ec221b6a20

适用于仓库内的说明、规范、产品、设计、测试和交付文档，以及 Issue、PR 的描述、评论、评审意见和交接记录。

以读者能够正确理解、实施和验收为准。准确、完整优先于简练。

- **简练：** 在信息完整、表意清楚的前提下精简文字，删除套话、重复解释和无关背景。
- **准确：** 写清必要的条件、对象、动作和结果；统一术语，按需注明数量、单位、版本和适用范围。区分事实、推断和计划。
- **直接：** 用具体名词和动词描述事实与要求，少用抽象词、口号和未经说明的缩写。
- **克制：** 减少无关免责声明、反复否定和防御性强调。必要的边界、风险和状态在相关位置明确说明，避免无必要的重复。
- **完整：** 保留影响理解、实施和验收的信息，包括必要的依据、限制和验证结果。精简表达时保持原意，如实说明尚未确认的事项。
- **自然：** 使用日常工作语言和必要的专业术语，避免模板腔、空泛总结和刻意强调。

同一规则只维护一处，其他位置引用；为便于独立阅读，可以保留与来源一致的必要摘要。

评审针对本次新增或修改的文字：冗余则删，含糊则改，缺少必要信息则补。评审意见应指出具体问题；同样清楚、准确的不同写法均可接受。本节通过现有自检和评审执行，不新增字数、词语或文风评分门禁。

## 2. 日常开发

开始时明确问题、预期结果、必要的范围边界和验收方式。未拆分的简单修改写在 PR 描述即可；复杂设计使用已有设计文档。只读查询和分析无需创建流程任务、分支、工作区或远程证据评论。

接手已有 Issue 开始实施时，代码、文档和测试任务均须先检查 Issue 正文、评论、已有执行会话及同目标 PR，确认同一范围没有其他执行者正在处理或有效暂停；再在原 Issue 留下开工 comment，说明本次工作、范围和负责人或可识别的当前会话关联，并回读确认发布成功后再开始相应实施或测试。发现同范围已有有效认领、并发留言或执行状态不明时，先核对并明确交接，不重复认领。评论发布失败或结果不明时先查询、重试或报告，不能假称已认领；只读分析可继续。同一会话续做同一范围复用已有开工记录，接管时补充交接说明；协调者已发布且关联实际执行会话的领取记录可直接复用。拆出的独立开发任务按[原生 sub-issue](#code-task-sub-issues)在各自子 Issue 留存并核实认领，不重复认领父 Issue；任务内部步骤可复用本项认领和分工。开工评论用于协作去重，不是原子锁，也不扩大任务授权；不因此要求未拆分的简单修改新建 Issue。测试认领与原开发关联按[测试任务的接收与完成](#test-task-acceptance)区分。

代码修改在独立分支进行，不直接修改 main。需要并行隔离时使用 worktree；工作区路径不是开发许可。保留用户已有改动，不擅自覆盖他人工作，并遵守明确的只读目录和资源边界。

本地编译优先复用少量固定路径的开发 worktree：串行任务在干净、未被其他执行者占用的开发工作区切换独立分支；并行任务才新增隔离工作区，不在 main 或主工作区修改。切换前保留未提交和未推送工作；不强制重置或替他人切换分支。固定路径复用该工作区的 Cargo target，跨工作区由 sccache 复用支持的编译结果。日常命令按受影响 crate、测试或 binary 执行，完整 launcher/playtest 和预热仅按需启动。操作及磁盘回收见 [testing-manual.md](../../../testing-manual.md)。

工作区入口统一使用仓库脚本和 Git 配置：先用 `git worktree list --porcelain` 检查已有工作区、分支和使用情况；当前聊天的附件列表不能代替仓库工作区清单。确需新增时使用 `./scripts/new-task-worktree.sh <module> <task> --base <ref>`，根目录取 `git config --local --get oasis7.task-worktrees-root`，未配置时按脚本默认值解析。Agent 不用 Codex App 的 `create_worktree`、worktree fork 或 handoff 代替该入口；用户明确指定时遵从用户要求。Cargo 默认使用工作区内的 `target/`，不预建缓存链接；已有 target 不自动删除，保留占用中和身份不明确的资源。日常反馈使用开发 wrapper，正式验收保留 canonical 命令和参数。

<a id="small-complete-pr"></a>
**优先小而完整的 PR。** 开发默认按可独立交付的结果组织小 PR，以缩短分支存活和依赖等待、减少并行修改冲突。每个 PR 聚焦一个清楚结果，包含本次所需实现、调用方、测试和文档，能在目标分支独立构建、验证并保持已有行为与合同。准备性切片可以尚未开放完整功能，但不能依赖未来 PR 才能让当前代码正确。大小以职责、审阅负担和可独立交付性判断，不设统一行数、文件数或 PR 数量门禁。必须同时修改才能保持正确性的强耦合改动可原子跨多个 crate，在 PR 中说明合在一起的原因。

公共接口、基础能力及其他能解除下游阻塞的前置，具备独立交付条件后优先提交评审并在已有授权内推进合入，使依赖方尽早复用；不等整个父任务或其他并行分支完成后再集中交付。小 PR 仍保留本次完整验证，父目标的剩余工作和最终集成验收继续跟踪。

**最小完整改动**

修改前读取相关实现，沿实际调用和数据流确认消费者、状态、错误处理及适用约定。以本次验收和合同确定完整范围，包含必要的调用方、测试、配置和文档；同一根因在所属职责内修复，必要时跨模块联动。

先查仓库已有能力，再查标准库或平台能力、已采用依赖；行为、错误处理和状态约束相容时优先复用。新增抽象、依赖、配置、缓存或包装层应服务本次验收或已确认的职责与边界，不为未确认的未来用途预留机制。复用须遵守现有分层，不因代码表面相似合并不同职责，也不因实现数量少删除必要接口。

在满足上述要求的方案中，选择容易理解和维护的最小实现。精简保留必要的边界校验、错误传播、恢复、安全、兼容和可访问性，不以本次增删行数或文件数代替质量判断。性能和容量取舍依据适用的负载、设计目标或可核实的瓶颈，不要求每次修改另做基准测试。

在已有 PR 或设计说明中按需解释新增机制的具体用途、复用取舍和仍适用的限制，不另建统一说明表、债务账本或审批步骤。无关清理不自动纳入本次修改；验收、必要验证和适用评审满足后按既有流程交付。实施方法见 [executing-project-tasks](../../../.agents/skills/executing-project-tasks/SKILL.md)。

负责人可连续完成复现、实现和局部验证，无需逐步发布计划字段或等待机械状态转换。可稳定自动复现的行为缺陷，应有能检出该缺陷的回归测试；已有测试能够检出时直接复用，覆盖不足时增加或修正。机械修改不强制增加与实现重复的测试。

代码任务由负责会话连续完成实现、自测、PR/CI 跟进及同范围修复，设计充分时直接实施；发现设计缺口按[设计检查与修复](#root-cause-design-check)处理，必要文档可随同一 PR 完成。并行开发按[独立开发会话](#independent-development-sessions)组织；交接复用 Issue/PR 的已有内容，补充必要上下文即可，不要求角色接力、模型证明或额外回执。

修改影响对外行为、接口、部署方式或使用方法时，同步维护相关文档。文档长度是编辑参考，不能作为是否允许提交的门禁，也不能通过压成长行掩盖过量内容。

涉及当前目标、阶段进展、重要设计决定或部署边界的工作，负责人在收尾时按[指挥面板持续更新流程](../command-center/command-center.manual.md)维护受影响的[项目状态](../command-center/README.md)和[架构索引](../command-center/architecture/README.md)；开始相关工作或项目回顾时核对旧摘要。先更新已授权的主责条款，再同步带来源、时间和未知项的派生内容；尚未发生的合入、部署和验收不能预写。无实质变化不制造提交，合入事实可在下一次刷新批量补齐，不为每个 PR 新建状态 PR。摘要维护不增加任务准入、审批、完成证明或合入门禁，读取失败只影响有关信息的时效。

<a id="information-record-placement"></a>
### 2.1 长期文档与过程记录的归属

“同步相关文档”指维护受影响的长期要求、设计决定及理由、接口/安全/兼容合同、使用/验证方法和真实能力边界；它不要求把本次执行、评审或 CI 流水写回 PRD、design、manual、runbook 或 README。按信息职责决定位置，不按日期、目录、文件名或是否出现 SHA 判断去留。

| 信息 | 主记录位置 | 仓库保留内容 |
| --- | --- | --- |
| 短期目标、排期、负责人、依赖、阻塞、剩余项与下一轮安排 | 对应 Task Issue；未拆分的简单修改可由当前 PR 承接 | 必要的来源/任务导航，不镜像可变任务状态 |
| 候选/合入 SHA、测试数、CI 等待与重跑、逐轮评审修复、清理与交接经过 | 同一 Task/PR 时间线，链接真实提交、检查与原始证据 | 合同所需固定版本身份及当前已验证范围；不追加逐 PR 交付日记 |
| 稳定产品要求、技术合同、已采用设计决定及理由、操作/恢复/测试方法 | 对应产品或专业 authority | 正文、可复用模板、输出字段及方法；任务不成为第二份规范 |
| 一次运行的原始事件、world/oracle、截图、fixture、manifest、hash 与不可重复事实 | 按证据生命周期保存的原始材料；Task/PR 定位该运行，本地验收输出按第 5 节清理 | 被消费者使用或需要长期审计的原件、固定 source/build/Skill/环境/窗口、原判定与必要解释；历史 run README 不继续追加后续 CI/收尾义务 |
| 当前方向、能力、风险与待决定事项的派生摘要 | 现有指挥面板索引，回链主责来源 | 来源、核验时间、覆盖范围与 unknown；替换同主题过期摘要，不复制逐候选尝试或测试计数流水 |

不因存放过程记录额外创建 Issue、Project、任务标识或本地 ledger；拆出的开发任务仍按[原生 sub-issue](#code-task-sub-issues)管理，未拆分的简单修改可由当前 PR 承载。已有 Task 只承接其真实范围，不能将 PR 编号冒写为另一个 Task Issue 的身份或捏造归属。已关闭或 `not_planned` 的任务只能标为历史来源，不恢复其义务。仍有效的暂停、部署/发布限制、未结发放义务与能力缺口须在当前 PR/操作入口或适用合同中继续可见，不能仅放进历史时间线。

长期合同不依赖阅读任务时间线才能理解接口、权限、失败/恢复或怎么使用。实填过程记录需要迁出时，先核准确接收方并保全独有历史，再精简源与修复引用/机器消费者；接收方未核实、原件不可取回或存在冻结/保留合同时，保留固定来源与原语义并注明限制，不批量建 Issue、不猜 Task，也不只留可能过期的 CI artifact 链接。后来的 PASS、合入或关闭不改写旧失败、旧候选或未验证范围；必要校验和更新只反映实际编辑，不能变成新的运行/审批证据。发行资产、许可/来源和版本身份按其原职责保留。

负责人在通常的自检与评审中核对上述分工：长期文档是否新增可变进度副本，运行记录是否混入后续收尾，摘要是否仍有决策价值；发现问题修在本次受影响范围。这是内容维护方法，不新增统一放行材料、每 PR 状态同步、固定数量指标或仅靠日期/SHA/Task 关键词阻断的门禁。

<a id="root-cause-design-check"></a>
### 2.2 根因确认后的设计检查与修复

开发、测试、CI 或实际试玩中确认问题根因后，负责人必须在修复实现前检查受影响的产品设计文档和系统设计文档。产品层检查要求、用户流程、体验、边界和验收标准是否遗漏、错误或冲突；系统层检查职责、接口、状态、失败/恢复与兼容合同是否正确且足以支持预期行为。不能仅因定位到某行代码就认定为纯实现 bug。

| 判断 | 处理顺序 |
| --- | --- |
| 产品或系统设计存在缺陷，包括同时存在实现 bug | 先修订受影响的产品要求/体验与验收标准，再修订受影响的系统设计，然后按正确约定补回归测试、修复实现并验证。只修改有缺陷或受联动影响的层级；系统设计有误不要求改动正确的产品文档。 |
| 设计正确且足以指导实现，问题只是实现偏离约定 | 直接复用或补充能检出问题的回归测试，修复实现并验证；不为走流程而修改正确设计或另造设计文档。 |

先补文档是工作顺序，不要求文档单独提交或先合入；同一 PR 可以连续完成文档、测试和实现。复现与诊断实验可以先行，可自动复现的行为仍须先观察回归失败再修复。若实现已经符合正确约定而只有文档失实，只修正文档并核验，不制造无必要的代码改动。不能通过改写正确设计或放宽测试来迁就错误实现。

缺少必要文档、约定含糊或无法确认设计正确时，不得默认归为纯实现 bug；先查主责文档和既有决定，确认属于设计缺口后在相应文档补齐。仅测试、环境或执行入口问题同样检查适用设计，无设计缺陷时修复对应对象，不强行引入产品设计。必要产品取舍超出已有授权时只暂停依赖该决定的动作，其他诊断与已授权工作继续。

在当前 PR 或已有 Task 中简述根因、设计判断及依据、受影响文档或无需修改理由、修复与验证结果即可；不为这项说明新增固定表单、审批、Issue、状态或 CI 门禁。长期文档只保留正确约定和可复用方法，过程记录仍按第 2.1 节归属；新建或实质修改的跨层要求沿用既有追踪规则。

<a id="issue-lifecycle"></a>
### 2.3 Issue 五类与转换

Trace ID: O7-REQ-1a003dc5-18f2-4cd3-adbb-d1b95316086e

拆出的独立开发任务按[原生 sub-issue](#code-task-sub-issues)管理，其他工作按跟踪需要使用 Issue，不要求每个 PR 单独建单。新建或转换的 Issue 只允许以下五类，且每项恰有一个 `type:*` 分类标签。类型描述当前主交付物，不是执行状态；优先级、模块、`implementation:*`、阻塞或暂停不构成第六类。分类与正文必须一致，标题前缀仅用于阅读。

| 类型 / 唯一标签 | 准入与必要内容 | 完成或转换依据 |
| --- | --- | --- |
| 缺陷 / `type:defect` | 内外部测试发现的实际问题，待 Triage；记录预期/实际、影响、版本/环境、复现或观察证据、已知与未知。根因可未知，不把推测当事实 | 经查重与设计/实现判断，转文档、代码、测试或决策；证据不足保留缺陷并写清补证条件 |
| 文档 / `type:document` | 明确的产品/系统设计补充或其他文档改动；写清主责文件、内容缺口、范围和核验方式 | 文档改动按交付约定完成；仍需实现且满足代码准入时可转代码，否则按全部义务决定关闭或保留 |
| 代码 / `type:code` | 新功能/设计实施须引用完善、足以指导本次范围的产品文档和系统设计及版本；明确实现 bug 可引用正确既有约定、实际偏差和复现证据直接修复，不为形式补写正确设计 | 开发角色完成实现及本项测试，所需 PR 合入后按剩余复杂测试决定转类或结项，见下述分工；设计缺口先按第 2.2 节处理，未决产品取舍不得假定为明确 bug |
| 测试 / `type:test` | 独立测试需求，或开发 PR 合入后的剩余复杂测试；写清对象、版本/环境、范围、方法、预期结果、执行权限及退出条件 | 交付实际覆盖、结果、未测范围和缺陷承接，按原目标及退出条件结项；测试完成不等于所有发现已修复，也不以 CI 代签真实体验 |
| 决策 / `type:decision` | 需要项目 owner 决定的具体问题；写清选项、取舍、推荐、影响和等待决定期间可继续的工作 | 记录有权决定者的真实结论及来源；需要落实设计时转文档，不能由 Agent 猜测决定或把沉默当批准 |

五份表单位于 `.github/ISSUE_TEMPLATE/`，创建者（包括 API/Agent）必须提供等价内容：类型、目标、来源与范围、验收、依赖、交付终点，以及该类型的专属依据。未知字段明确写未知与补证动作；代码准入所需设计或明确 bug 证据不能用“待补”代替。模板不默认添加 `implementation:ready`，类型也不授予模型、执行、合入或部署权限。

复杂代码 Issue 可以承载父目标，由负责人先拆分和协调；实际实施前须形成[可验证的代码任务](#verifiable-code-task)。设计完整、类型正确或列有几个阶段，不等于父项全部范围已可直接派发。简单任务可由已有目标、范围、依赖和验收表达，不重复填写拆分材料。

**转换沿用原 Issue ID。** 更新当前唯一类型和当前交付目标，保留原问题、讨论、来源、已完成成果及全部未完义务；以一条有实质变化的 comment 记录旧类型 → 新类型、证据/决定、已完成验收、剩余验收/依赖及下一责任人（无人承接如实写待承接）。先回读当前状态、认领和暂停；不能靠换类覆盖人工新要求、取消暂停或重复派工。多次 API 写入并非原子事务，结果未知先协调已有写入；正文与标签尚未一致时不得领取。

**开发测试与合入后复杂测试。** 本项适用的单元测试，以及不依赖外部条件、可在开发环境自行准备和运行的集成测试，由开发角色随开发 PR 完成。按实际执行条件判断；本地夹具或可自行启动的测试依赖不构成后移理由，也不因名称含“集成”就交给测试角色。已有合入前必要检查、适用评审及独立验证仍须满足，不能用转测试推迟开发应完成的验证。

只有本项约定实现、开发测试和适用评审完成，所需开发 PR 均已实际合入，且仍有需正式部署、真实外部系统、专门测试资源或持续观测等条件的复杂测试时，才沿用原 Issue ID 转为 `type:test`，明确剩余验证及其具体条件。合入前可准备后续测试计划和环境，原项保持 `type:code`；一个阶段 PR 合入不能代替本项全部实现交付。仍有计划内实现（包括测试框架、用例或 CI 接线开发）未完成时继续由开发角色承接。无剩余复杂测试时，原代码 Issue 在合入及全部原交付义务满足后按授权直接关闭，无需为证据核对先转测试。

交接复杂测试时按上述转换记录保留已合入 PR、实际合入提交/构建版本、开发测试证据和原验收标准；当前正文列明剩余复杂测试的对象、版本、环境及依赖、范围、方法、预期结果、权限/预算、退出条件和下一责任人。已有证据核对其对合入版本和待测环境的适用范围，只补缺项；进入测试阶段后，即使无需重跑也记录验收结论。接收、阻塞和结项按[测试任务的接收与完成](#test-task-acceptance)处理。移除可消费的 `implementation:ready`，保留真实会话与暂停事实；测试通过且全部原义务满足后，才按授权关闭。

允许的转换还包括缺陷 → 其他四类、文档 → 代码、决策 → 文档；其他类型 → 测试须以当前剩余主目标确实是测试验收且对象/范围/环境/退出条件明确为依据，代码转入还须满足上述分工和合入条件。实现中的普通自测、一次 CI 失败、未解决的代码/设计/决策本身不是转测试的理由。测试发现问题按[测试任务的接收与完成](#test-task-acceptance)确定原项返修或关联承接，保留未完成覆盖。已关闭项真实复发按问题承接规则新建关联缺陷，不擅自重开或恢复已取消目标。其他逆向纠错按真实主目标和准入证据记录，不机械沿流水线走完五类。

转换前核实执行者交接：代码转其他类不删除在途会话或暂停事实，先确认旧执行停止或交接；非代码不保留可消费的 ready，历史实现记录留在评论。转代码也不自动 ready，须另满足第 2.4 节的授权与依赖。拆出的独立代码结果按[原生 sub-issue](#code-task-sub-issues)承接，原项明确每项义务的归属；不为一次类型转换新建整条 Issue 链。全部义务满足后才按授权关闭；重复、误报或决定不做按相应理由与证据关闭，不伪称已修复，也不为完成 Triage 强造下游任务。

**入口与实际约束。** 表单必填及 `blank_issues_enabled: false` 收窄普通网页入口，不是 GitHub API、特权空白入口或评论的硬校验；本仓不声称已部署服务端 Issue 格式拦截。创建者写后回读，dot Triage 在整理时、实际领取者在接手前检查唯一类型、正文和依赖；实际领取者可以是直接开发会话或已选协调者。缺类、多类或内容不完整是待修正输入，不是第六业务类型，不自动关闭；在核实前不得加入开发队列。评论是证据增量，不要求重复整套建单表单。没有新建单的普通 PR 不受此分类要求影响。

**采用与存量。** 采用本规范前，在授权范围核实五个分类标签存在且模板能正确应用；GitHub 不保证自动创建模板引用的标签。保留 `code-development` 作为旧搜索兼容提示，不能代替 `type:code`。先只读盘点旧项的目标、状态、认领与设计依据，再在已批准范围渐进补类；不根据标题猜类别、不全库覆盖正文、不重开已关闭项。活跃项先与原执行者对齐，原义务及暂停优先。模板、消费者规则、标签配置和实际调度分别记录采用状态；本 PR 不代表线上标签、旧 Issue 迁移或 20 分钟运行器已经启用。

<a id="test-task-acceptance"></a>
#### 测试任务的接收与完成

测试执行者可由用户直接指定，或由已有负责人在授权范围内安排；原负责人在接收确认前继续跟进待承接事项。每项明确一名当前测试负责人，操作入口见[测试 Issue 接收与验收](../../../testing-manual.md#test-issue-acceptance)。QA 角色提供专业方法，普通证据核对可由原负责人承担；适用的独立评审、自主试玩和真实环境验证要求仍须满足。

**确认接收与认领。** 执行者先读取原目标、全部未完义务、候选和环境、已有测试认领及暂停；代码转入时还须核实开发测试已完成、所需 PR 已实际合入及剩余复杂测试范围。核实本轮范围可执行，再按第 2 节留下并回读测试认领，明确执行者、测试范围、source/build 和环境。协调者已有领取记录经执行者确认本轮范围后可复用。被写为下一责任人不等于已接收；尚无环境或接收者时记录具体阻塞、解除条件及待承接状态。原开发会话保留实现问题承接及后续修复 PR/CI 跟进责任，本轮测试认领单独说明；`implementation:active` 不代表测试已领取，测试任务不加入代码 ready 队列。

同范围已有测试执行或认领结果未知时，先查证并协调，不能因新一轮巡检或会话中断重复启动。续做保留原认领及已完成范围；换人前确认旧测试已停止、在途操作和自有资源状态可核实，并交接剩余覆盖与证据。暂停按原指令的动作范围执行，恢复须有有效恢复依据；测试并发和环境使用沿用既有权限、预算及资源隔离要求。

**验证与反馈。** 逐项核对原验收与已有证据的版本、环境、范围及判定依据，只执行尚缺或受影响的验证。候选或相关环境变化时保留旧结论的实际身份，重新核对受影响证据并复测，不能把旧结果改写成新候选通过。反馈记录失败版本、环境、复现、预期/实际及证据；设计问题先按第 2.2 节处理，环境缺口记录解除动作，剩余可独立执行的覆盖继续推进。

代码转入验收的同源实现缺陷，按代码准入将原项转回 `type:code` 并续接原开发执行者；开发者完成修复及相应单元、可自行执行的集成回归，修复 PR 实际合入后再转测试，由测试负责人接收新的合入候选并复测原复杂测试的失败及受影响范围。独立测试发现的问题优先补回同源且仍开放有效的实现项，独立问题另建关联缺陷；测试项保留剩余覆盖。只有当前主交付物确实转为实现且满足代码准入时，才转换测试项，不因发现一个需代码修复的问题把整项测试改为开发任务。

**结论与关闭。** 测试负责人在原 Issue 留下准确版本、环境、实际覆盖、结果、未测范围、缺陷承接和下一步，区分本轮测试结束与原目标完成。代码转入的验收须满足原代码目标及全部交付义务后关闭；独立测试按原定覆盖、结果和缺陷承接等退出条件结项，不机械等待全部发现修复，原任务明确要求的修复后复测仍须完成。已处于测试阶段且当前有效证据覆盖全部验收、所有义务满足时，有权限的当前负责人可在同一轮记录验收结论并关闭，接收与结论可合并在同一条记录，无需等待另一接收者或下一轮调度；必要独立验证不能由自身结论代替。

<a id="coding-agent-issue-handoff"></a>
### 2.4 可选的 dot 与 Coding Agent Issue 交接

Trace ID: O7-REQ-59e8a26e-0c16-4a0b-b449-ce94601ebf2d

用户采用此方式时，dot 把已授权的 Rust/JS 开发目标、范围、来源、验收、依赖和交付终点写入 GitHub Issue，交给独立 Coding Agent 会话实现。用户可直接打开开发会话领取具体任务；需要集中协调时，再选择 [TPM 会话](../../../.agents/roles/tpm.md#手动启动的-tpm-会话)，使用当前工具实际提供的会话管理能力去重派发。两种入口均遵守原任务认领、暂停及执行预算，dot 不直接启动开发执行。开发工具或服务沿用用户选择和授权，后续修复优先续接原开发会话；dot 接续具体环境授权内的部署、测试和反馈。此入口不为普通开发增加必经协调会话、Issue 或审批，产品层不适用。

只有满足[五类合同](#issue-lifecycle)的唯一 `type:code`、正文完整且本次派发范围的依赖/授权具备的 Issue 才可进入 ready；缺陷、文档、测试和决策不由代码队列误领。复杂父项须通过[原生 sub-issue](#code-task-sub-issues)指明本轮可启动的[具体代码任务](#verifiable-code-task)及各自验收；ready 和派工定位到具体子 Issue，父项 ready/active 不代替子项自己的准入与领取，不能用“完成父项剩余工作”代替。协调者可先接手父项整理拆分，实际实现按已就绪子任务推进；全局设计前置、权限或暂停仍约束所有受影响任务。

以下标签描述代码实现任务的状态，不绑定具体开发工具，也不授予执行权限：

| 标签 | 协作含义 |
| --- | --- |
| `implementation:ready` | 代码实现条件已具备，尚未确认领取 |
| `implementation:active` | 代码实现任务已被接手；实际执行、等待 CI 或等待验收状态以会话和 PR 为准 |
| `implementation:blocked` | 存在明确依赖或执行障碍，记录原因及解除条件 |
| `implementation:paused` | 暂停相应派工和执行；有权解除该暂停的后续指令到来后才能继续 |

<a id="coding-agent-task-claim"></a>
**领取与状态维护。** 采用本节代码队列时，实际领取者（直接开发会话或已选 TPM）按[日常开发](#2-日常开发)核实具体执行 Issue 的认领、会话及暂停。确认开工记录后，为本项添加 `implementation:active`、移除 `implementation:ready`，回读标签和实际会话关联；保留其他类型、阻塞、暂停及无关标签。续做已有认领直接复用记录，由已承担状态维护的一方完成更新。

标签缺失时，在已有管理权限内补齐。写入失败、权限不足或结果不明时先回读，在原认领记录中说明待同步项；没有评论权限时向用户报告。已确认的认领仍作为去重依据，具备原执行权限且不受暂停影响的工作可以继续，不因标签未同步重复领取或重开会话。未确认的写入不能报告为成功。`blocked`、`paused` 可以与 `active` 并存以保留原关联；解除阻塞后先核对原会话，暂停按有效恢复指令处理，不把原任务重新标为未领取。

授权与交付仍遵守本规范：同目标修复不重复确认，新增范围才核对新增授权；PR、当前 source HEAD 的检查和评审以 GitHub 实际结果为准。Issue 留存真实会话关联与待办，创建或执行结果不明确时先核对，不重复派工；原会话不可恢复时，确认旧执行停止并保全已有工作后再交接。Coding Agent 按任务的实际合入授权执行，PR 使用 `Refs #<issue>` 关联；dot 核实整体义务，包括适用部署和真实验收后，才在已有权限内关闭 Issue。有效暂停必须阻止相应后续执行，不能靠下一轮检查或重开会话自行解除。约五分钟的检查是 TPM 活跃期间的工作节奏，实际持续能力以客户端为准，文档不保证会话结束后仍在后台执行。

<a id="parallel-task-development"></a>
### 2.5 任务拆分与并行开发

Trace ID: O7-REQ-f1388c2b-6f64-4ebd-886e-0b741bfe176c

<a id="independent-development-sessions"></a>
**默认使用独立开发会话。** 简单任务由当前会话直接完成；多个已就绪代码任务默认由可单独查看、直接交互和续接的开发会话分别领取，不以父会话内的 subagent 树作为默认开发编排。每个会话负责本项实现、自测、PR/CI 跟进及范围内修复；任务及成果由对应 Issue/PR 承接。用户可直接开启会话，整体负责人也可承担实现；需要集中协调时才采用 TPM。缺少多会话能力时按同一任务分解顺序推进。独立评审、Agent 试玩和 dot 时间表任务分别遵循其适用规则。

**先判断拆分。** 具有多项交付结果的跨模块任务、需要多个执行者或跨会话持续推进的任务，负责人须在实施前梳理子任务、依赖和整体验收。实施或验证持续未能缩小关键未知，或阶段 PR 增加却仍重复卡在同一边界时，先诊断实际阻塞，再重划受影响范围、补必要前置或最小验证；不能靠扩大任务或放宽正确验收标准收尾。简单修改直接完成；强耦合的原子改动可以串行，说明具体依赖即可，不按 crate、文件数或固定人数强拆。

**从完整结果拆任务。** 先核对当前源码、已有成果、在途 PR、认领和暂停，再把每项父目标验收对应到实现任务及最终集成。一个子任务交付可检查的行为或产物，包含其必要消费者、测试和文档；不把每次编辑或 helper 单独算作交付。写出前置关系，消除循环，识别阻塞整体结果的关键路径。公共类型、协议、错误/恢复语义和共享资源规则不明确时，先完成必要的合同或最小集成骨架，再派发依赖它们的实现；无关调研、测试设计和已独立就绪的工作可以继续。

<a id="verifiable-code-task"></a>
**代码任务须能单独验证。** 父项保留总体目标、依赖关系和最终集成验收；直接交给开发者的任务聚焦一个可验收行为或接口合同，明确以下内容，已有等价说明直接复用：

- 本项可观察结果及对应的父项验收，不能仅用模块名、阶段名或文件清单代替。
- 本次范围与非目标、实际消费者和接口边界。影响本项工作量或完成条件的 profile、消费入口、版本、预算等，写明具体范围或取值，或能唯一确定它们的固定来源；未定部分注明补齐动作、负责人和影响范围。必要的跨文件或跨 crate 修改可以属于同一任务。
- 依据的设计或正确既有约定、实际输入和依赖版本，区分已具备与尚缺的前置。
- 验证入口、输入及独立预期结果，覆盖适用的成功、拒绝或恢复行为；复用能检出问题的已有测试，不按任务数量机械增加测试。
- 本项完成与交接终点、仍由父项或后继任务承担的组合和环境验收。独立验证在声明的实际依赖上进行，不要求零依赖，也不以未来才成立的调用方或测试代替本项交付。

编写验收时，对照主责要求或设计中涉及计量、权限、状态转换、终态和恢复的关键条款，保留其对象、适用条件和副作用边界；任务摘要不能改变原合同。确需改变约定时，按[设计检查与修复](#root-cause-design-check)修订主责文档，再更新任务验收。

派发前检查子项内部是否仍含多个可独立消费和验收的结果，并从完成条件反查边界：若一个结果在固定前置上可以完整交付、由实际消费者使用并完成必要验收，却仅因另一独立结果或父项组合未完成而无法结束，应继续拆分，明确剩余结果和组合验收的归属。必须共同修改才能保持接口、状态、权限或事务正确性的部分保留原子性，说明拆开会破坏的具体合同。一个子 Issue 或接口名称不能代替这项判断；保证本项行为正确、安全所必需的拒绝与恢复随本项交付，不能通过转移本项必需验收制造独立完成。

<a id="code-task-acceptance-readiness"></a>
**派工前核对验收条件。** 核对声明依赖、权限和环境上的验证入口、输入/夹具及结果观察点；已有路径先做最小启动或基线核验，不要求尚未实现的新行为已经通过。缺入口、夹具或环境时，把补齐工作列为本项明确的先行步骤或最小独立前置，说明产出、负责人和解除条件；不因此停止可执行的诊断及独立已就绪范围。核对和补齐沿用已有授权。必需验收未能执行时如实保留该阻塞，不能把“测试待补”当作完成。

实施中发现必要前置缺失、关键合同未定、约束前提失效或新增可独立交付结果时，先更新受影响任务的依赖和拆分，再继续相应实现；本项同目标修复及必要联动沿原授权推进。按行为与接口划分任务，不为了数量把同一完整结果拆成 helper，也不把新增独立能力持续吸收到原任务。

<a id="delivery-feasibility"></a>
**先验证关键交付路径。** 对含未验证关键约束的跨组件新能力，先选定一条最小完整路径，明确真实入口、消费者可观察结果及本任务必需的结束或恢复行为。把决定方案是否可行的预算、时效、容量或权限约束放到这条路径上共同核对，设计内容见[约束组合与可行性](../doc-governance/system-design-writing-standard.design.md#constraint-feasibility)。优先用已有实现分析、成本计算或最小验证消除关键不确定性，再扩展依赖该结论的实现；需要实测的接口、时序和运行行为通过真实消费者与相关适配器验证。前置或环境缺失时列明具体缺口和解除动作，独立就绪的工作仍可按自身范围交付。

设计或验收调整新增必要前置，或改变跨边界调用、校验、终态、持久化或恢复义务并影响关键路径时，重新核对受影响的约束组合、消费者和最终结果，更新原安排的依赖、实现范围及验证，并说明对原交付范围和验收的影响。原预算、时序或容量结论仅在前提仍成立时复用，复核限于实际受影响部分。

<a id="code-task-sub-issues"></a>
**拆出的开发任务使用原生 sub-issue。** 拆出的每个独立开发任务，在派发前必须创建或复用符合[五类合同](#issue-lifecycle)的 `type:code` Issue，并通过 GitHub 原生 parent/sub-issue 关系挂到承载父目标的 Issue。父目标尚无 Issue 时按五类合同补建；同范围已有父子 Issue 优先复用。同一会话、短任务或临时执行会话不豁免已拆出的独立开发任务；父正文 checkbox、普通链接和 PR 不能代替子 Issue 或原生层级关系。单个任务内部的机械步骤、测试用例可以使用清单；未拆分的简单修改仍可直接使用 PR，不新增 Issue 类型或要求子任务与 PR 一一对应。

派发前回读子 Issue 的正文、类型及 GitHub 实际父子关系，确认归属与范围正确；创建或挂接结果未确认时先核实、修复，不按已建立的子任务派发。父子关系表示目标归属，前置依赖另记所需产物、可用输入版本及解除条件；同属父项不表示前置已满足。子项沿用父目标适用的用户授权、范围限制与暂停，建单或挂接不扩大权限。

**保留一份可交接的安排。** 父 Issue 保留总体范围、子项关系、依赖、整体集成负责人和最终验收；子 Issue 独立承载本项范围、负责人/实际会话、认领与实现状态、PR、验收结果及剩余义务。交接应能核对本项验收、前置与可用输入版本、允许写入的文件/目录和接口边界、验证方法及集成去向。完整派工文本可留在执行会话，公开记录只放必要且可公开的关联；局部步骤编号不是新的任务身份或 Trace ID。

父项简述已可验证的完整结果、阻断整体验收的关键条件及依据、下一步解除动作；子项维护自己的实施事实，父项不复制子项逐轮记录。事实变化时更新对应摘要并保留历史记录。

<a id="task-decomposition-delivery"></a>
**仅拆分时的交付。** 本次范围仅为任务拆分时，交付子任务及父目标验收归属、已有成果和在途执行的承接、建议优先推进的范围，以及实施条件已核对与尚待核对的部分。整体集成或执行责任尚未承接、前置尚未核实时，明确下一步承接或核实动作。拆分交付、具备派发条件、实际认领和已执行验证分别按事实说明；拆分完成不代替父目标完成。后续实施沿用已有授权，派发前核对相应范围，不要求所有子项同时就绪。

**只并行派发已就绪的范围。** 当前批次的任务须有可核对输出、已满足的前置、可用的共同接口与输入，以及能隔离的写入和运行资源；负责人在这些条件成立且有实际执行容量时并行分派。准备测试夹具可以先行，依赖未完成实现的最终行为验证仍须等待，mock 或临时接口不得被当成真实集成完成。若需要串行，记录实际原因；没有并行工具时保留分解并顺序推进，不虚报多个执行者。

**明确一个写入负责人。** 每个子任务有一个有效执行者，父任务有一个整合负责人；负责人可兼做边界清楚的实现。父 Issue 已 active 不代替子 Issue 的领取；由现任负责人协调分派并核对重叠，各子 Issue 按自身认领和实现状态推进，不允许其他会话重复领取。共享协议、`Cargo.toml`、`Cargo.lock`、`lib.rs`/`mod.rs`、生成产物及全局索引按实际影响指定单一写入者，其他任务提供所需接口变化。发现新增读写冲突或契约变化时，先调整受影响任务的依赖和所有权，再继续相应写入。

**按真实能力隔离。** 并行实现优先使用独立分支和 worktree，沿用第 2 节的仓库脚本入口，固定各自起始版本；新会话不自动提供工作区隔离。共享工作区只用于文件及生成/运行输出确实不重叠的任务，Git 暂存、提交、切分支、变基、清理和全局生成操作由负责人串行执行，各开发会话不做全仓格式化或提交他人文件。会改变其他任务工作基础的切换、变基、清理或生成，须先确认受影响执行者停写并保全成果，再执行和通知恢复；仅让 Git 命令串行不够。独立 worktree 仍需协调公共接口、端口、测试数据和外部环境，不能只凭目录不同判断互不影响。

**按容量调度并及时整合。** 在已有用户授权、工具能力、CPU/内存、构建/CI 容量和可审阅工作量内确定并发；所有相关开发和评审会话共享同一执行与预算上限，另开会话不提高约定上限或扩大授权。等待依赖且已停写的任务可让出执行名额；待 CI、评审、集成或验收仍属在制品，仍可能写入的会话仍计入执行并发。优先收尾并解除关键路径阻塞，保留整合与验收容量；反复冲突、等待、重复验证或返工超过收益时减少并发、合并过细任务或重新划分边界。新的付费、部署或其他外部影响仍遵守已有授权；不是每次分派都重新申请许可。

**收回真实产物。** 执行者返回实际提交/补丁范围、受测版本、已执行命令与结果、未完成项和接口偏差。负责人读 diff，按依赖顺序及时整合，核对消费者和共享文件；相关结果形成后执行阶段组合验收，不把已可执行的验收攒到父项最后。父项最终仍核对完整目标、实际组合所需的跨边界验证与现有必要检查。局部验证按职责分配，不让每个开发会话重复全仓测试；各分支绿色不能相加成集成绿色。记录“已返回、待集成”与“已集成”的实际区别，实际合入和整体完成仍按第 5 节核实。会话停止、子任务自报完成或已有阶段 PR 均不代替验收。

**按依赖持续交付小 PR。** 按[小而完整的 PR](#small-complete-pr)规划交付边界、依赖 PR/版本及先后顺序，优先释放阻塞其他任务的前置代码。同一父目标可由多个小 PR 逐步完成；任务数与 PR 数不要求一一对应，多个执行者也可共同完成一个小 PR。强耦合部分保留原子性，不因父目标相同而长期堆积成一个大 PR。

前置尚未合入时，依赖方可基于接口稳定且已有适用验证的固定提交开展堆叠开发，注明依赖 PR、提交、未合入状态和目标分支；可独立交付的前置仍优先评审及按授权合入。前置合入后核对实际合入版本，更新必要的依赖引用和分支关系，让依赖方复用同一成果，避免重复引入改动或各自复制实现。后继 PR 的验收覆盖实际目标分支组合，不把旧父分支结果改写为新组合证据，也不因无关 main 前进重跑全部工作。

<a id="interface-prerequisite-delivery"></a>
**接口前置交付。** 当跨模块任务需要让消费方在真实适配器完成前开发时，先盘点已有公共接口、错误类型和测试支撑，再选择能独立正确、可编译且可被实际消费者使用的前置产物。接口已经足够时直接复用；简单修改或不可拆的原子变更不必补一套 fake、额外 trait 或专用 PR。接口语义仍由原领域设计拥有，本节只规定交接方式，不借用并行开发改变权限、兼容性或恢复承诺。

前置产物在同一 Issue/PR 的已有安排中说明以下适用内容，不要求固定文件清单或另建台账：

| 交付内容 | 消费方需要能核对的事实 |
| --- | --- |
| 权威与输入 | 原设计锚点、实际 trait/DTO/错误类型位置、输入提交或依赖 PR；区分已实现能力与待实现适配器，说明允许的依赖方向 |
| 行为与错误 | 正常输入/输出、相关错误类别及调用方的重试/停止含义；只列该接口已有的身份、顺序、拒绝无副作用、重复或恢复规则，不统一新增 TTL 或 exactly-once |
| fake 与共用断言 | 可确定控制的结果/故障、每例的隔离及观察点；同一组公共行为断言如何接入 fake 和真实实现，预期值来自合同而非被测转换函数 |
| 最小消费与真实接入 | 一个能编译并执行所选行为的真实消费入口；真实适配器的构造/依赖接缝、需要的环境、未被 fake 证明的部分 |
| 交付关系 | 公共类型、共享测试支撑、生成产物的单一写入者；实现方和消费方各自写入范围、所依赖的实际版本、最终组合验收及整体集成负责人 |

可控 fake 与共用断言是供消费者实际复用的测试支撑，不复制另一套业务 DTO，也不把生产适配器依赖带回纯协议层。前置 PR 须在当时可用的代码上通过自身必要验证并有实际消费示例；只有声明、未来才成立的编译状态或空壳 adapter 不能算完成。已存在真实实现时，优先同时接入以检验前置抽象；尚不存在时，把真实接入和组合验证继续保留在父项，消费方仅对已就绪的接口范围开展工作。

实现和消费 PR 使用同一前置版本；接口有变化时由共享写入者先更新前置和受影响安排，再同步消费方。整合时至少核对选定范围的 fake 通过、真实实现通过，以及故意破坏合同后的同一断言失败，并保留领域要求的真实集成验收。fake 或本地传输夹具不证明外部服务、世界写入授权、持久化或重启恢复。具体试点、用例和这些证据的界限见[测试手册的接口共用契约验证](../../../testing-manual.md#shared-interface-conformance)。文档方案通过不表示支撑代码已可用；需要后续实现的 Issue 沿五类合同转为代码任务，保留实施和最终集成义务，不以设计 PR 关闭。

**恢复与关闭。** 中断或接管时核对每项实际会话、分支/补丁、已整合结果及剩余依赖；结果不明先查证，确认旧执行停止并保全成果后才能换人。父项暂停约束全部受影响子项，局部阻塞只阻塞其依赖链。子任务 PR 关联对应子 Issue，对父项使用 `Refs`，不由子 PR 自动关闭父 Issue。只有原目标及适用真实环境义务全部满足才关闭父项；缩减目标须有相应用户决定，不能通过拆单丢掉难做的验收。

本节通过现有派工、自检和评审执行，不增加固定角色链、全仓必填计划、每任务 PR、调度服务或 CI 门禁。具体操作和模板见 [parallel-development](../../../.agents/skills/parallel-development/SKILL.md)。

## 3. 验证与评审

开发者负责本项完整的局部验证，按[测试分工](#issue-lifecycle)随 PR 完成适用单元测试及不依赖外部条件的集成测试。先用最小有效验证获得反馈，按行为与风险选择单元、合同、故障或最小真实场景，覆盖适用的成功、拒绝和恢复；不要求每项遍历所有测试层次。预期结果来自需求、合同或独立基线，用该行为的权威状态或结果判定，不能由被测实现生成同源预期或仅凭成功日志判定。复用现有测试和入口，CI 执行完整的必要检查，独立评审不代替开发者自测。具体命令和环境准备见 [testing-manual.md](../../../testing-manual.md)。验证记录应能说明执行了什么、针对哪个版本、结果如何及未覆盖的部分，按[信息归属](#information-record-placement)放在实际 PR/Task 及适用原始证据中；长期文档维护验证方法与证明边界，不另造通用放行回执。

CI 按普通 PR 快速反馈、关键改动按实际风险定向加测、main 每四小时完整回归分层；十分钟/P95 目标、统计口径、覆盖与发布版本要求由 [CI 专业要求](../../testing/ci/ci-tiered-execution.prd.md#ci-fast-pr-periodic-full)拥有。当前候选已接入选择、执行、汇总及发布结果消费，hosted 时延、完整覆盖和周期容量仍待实测。定向加测属于普通 CI，不自动增加环境专项或重复全仓验证。必要检查按可信 BASE 能力和已生效入口执行；旧 BASE 不支持新 profile 时保留旧完整必要范围，首次候选 bootstrap 不取得发布资格。切换仍须核实适用保护与实际汇总一致，文档不能解除已有门禁。普通 PR 不等待下一轮完整回归，发布消费实际已验证的固定候选版本。

CI 按实际改动及受影响消费者选择测试。选择范围必须考虑新增、删除、重命名两端、依赖关系、features、生成输入、共享配置及锁文件变化；无法可靠解析 Git/依赖输入时扩大覆盖；已确认未匹配任何包归属、显式范围或共享控制规则的路径，按[未登记路径门禁](../../testing/ci/ci-tiered-execution.prd.md#ci-unknown-inputs)使规划和最终 required check 失败，不以全量回退掩盖规则缺口。包关系用于选择测试，不用于禁止合理修改。

最终 required check 必须在所有选中的必要任务结束后汇总，并以 `always` 等可靠机制在失败或取消路径仍执行。只有预期任务全部真实成功才能通过；失败、取消、缺失、未知结果，或应执行却跳过的任务均不得算成功。未被计划选中的任务可以不执行。

CI 结果必须对应实际 source HEAD 和测试对象。测试合并树时还应能识别真实 base、event commit 和 tested tree；不得把只测试过源分支的结果宣称为最新 main 组合验证，也不得将旧结果改写成新版本证据。

普通 PR CI 的 GitHub 权限只读，不授予生产凭据或部署身份。需要特殊权限的验证使用受控入口，固定已批准的待测版本并授予最小权限。PR 缓存和产物不得直接成为特权入口的可执行输入。

改变 CI workflow、测试入口或选择规则的 PR，必须接受独立评审，并验证测试确实按既定保护要求执行。候选代码不能通过删减必要任务、改变汇总条件或伪造同名成功状态为自己放行。

评审按复杂度和风险选择，可由独立评审会话或其他合适的审阅者完成。普通变更由负责人自检并按需安排独立评审；机械文档不强制领域角色或 QA。权限、凭据、共识、持久化兼容、不可逆迁移、关键安全边界和开发门禁变更必须有对应能力的独立评审，评审者不得批准自己编写的部分。

<a id="evidence-based-review"></a>
评审先读适用要求和 diff，再沿调用、状态变换核对受影响消费者。先检查正确性、安全、数据保护及实际负载下的行为，再评估验证、性能和简化。缺陷结论应给出具体位置、可核对的触发条件或可达路径、影响及依据；代码能够确认的风险无需等到事故或运行复现，尚未确认的疑点则说明待核查条件。

评审记录说明所审阅的版本、结论、阻断问题及处置即可。真实的正确性、安全性或数据丢失风险必须修复或以事实证明不适用。简化建议应指出具体冗余或复用入口，并保留所需行为与边界；不影响本次验收且未揭示实际风险的纯简化或风格建议按非阻断处理，可以说明理由后不改，不自动创建后续任务。已有取舍记录或临时注释不豁免当前要求和风险检查。修改后的复审针对实际变化及受影响部分，不强制所有角色重复全量审阅。具体方法见 [requesting-repo-owned-review](../../../.agents/skills/requesting-repo-owned-review/SKILL.md)。

CI 和独立评审可以并行，合入时汇总两者。一般情况下，当前 PR 的 source HEAD 已通过全部必需 CI 即满足 CI 合入条件；main 前进或分支显示 `BEHIND` 本身不使该结果失效，不要求因此 rebase、合并 main 或重新运行 CI，也不要求重做设计、开发或全部评审。GitHub 的必需状态检查保留，但关闭“合入前分支必须跟上 base”的要求。存在合并冲突，或 main 的相关变化带来明确的集成风险时，才按需要更新分支并验证实际合并组合；必须说明具体冲突或风险，不能仅以 main 前进要求重测。source HEAD 变化后，重新运行必要的普通 CI，并复审实际变化及受影响部分；已有 CI 结果仍只代表实际测试过的版本和组合。

修改 UI 时，须在 PR 或交付说明中附上实际运行界面的验证截图，标明受测版本、界面状态和视口尺寸，并覆盖本次受影响的桌面、窄屏或关键交互状态；截图不能代替功能验证，模拟或组件预览须明确说明其范围。

普通 CI 是默认验证方式。缺测试先补 CI；只有明确需要普通 CI 难以提供的环境、跨系统状态或部署恢复过程时，才增加专项集成验证。专项验证必须说明具体环境缺口、验证目标、执行版本、实际结果和剩余限制。高风险本身不等于需要重复执行另一套相同 CI。

已有绿色结果后追加阻塞验证时，先暂停合入并触发包含该项的 PR 验证；当前版本通过后才解除相应暂停。删除标签或修改描述不能自动取消尚未满足的验证要求。

<a id="agent-gameplay-selftest"></a>
### 3.1 Agent 游戏功能的开发自测

验证 Agent 通过正式游戏 Skill/API 自主游玩及相关玩家协作功能时，负责人必须按[开发 Agent 自测操作手册](../../testing/manual/agent-runtime-self-playtest.manual.md)组织自测，不以普通 CI 通过或源码审阅代替实际游玩。命中本条范围时主动执行，不以用户另行提醒或再次点名手册为前提；具体步骤和模板只在手册维护。

**触发范围**：本次交付或验收涉及 Agent 的游戏接入、正式玩家 Skill 使用方式、能力发现与行动、实际 Runtime/worker、目标/问答/审批、预算/停止/恢复、Agent 可玩的生产或其他玩法，以及与这些能力关联的 Web/桌面观察和高层指导。按行为与受影响消费者判断，不仅按文件扩展名或目录；改变玩家 Skill 的指令或上手路径即使只改 Markdown 也属于此范围。

先执行适用的普通单元/合同/故障回归，再按手册选择能覆盖本次行为的最小实际场景。开发主 Agent 读取手册、固定候选及获准私有测试环境，派出真实独立试玩 subagent 读取同一候选的正式游戏 Skill，自主启动或接入、游玩并反馈；负责人核对原世界操作/回执，确认缺陷及根因后先按[设计检查与修复](#root-cause-design-check)分流，再补普通回归、修复并用新候选复测。试玩者不得获得源码答案或测试侧世界写权限。Runtime/profile、冷启动/准备态与 Web/桌面按实际受影响范围分别验证，不要求每次遍历全部七组场景或所有平台。

**完成判据**：在当前 PR 或已有测试记录中说明受测 source/build/Skill、实际 Runtime/profile、选中场景、真实子会话和操作结果、缺陷处置、复测及未覆盖项；复用现有记录，不新增通用证书。固定动作脚本、mock、模型自报、健康检查、截图存在或世界自然活动不能代签自主试玩；API 结果不能代签图形交互。新候选的结论不得直接沿用旧构建的实玩结果，失败尝试不能被一次重跑成功覆盖。

**缺前置与阻断**：缺游戏 Skill/API、适用 Runtime、独立派工/GUI 工具、有效权限、隔离环境或预算时，先完成可执行的预检和普通测试，并把受影响场景如实标为 blocked/inconclusive。降级的主 Agent/脚本测试只证明其实际范围，不能将未执行场景改为 not_applicable 或通过。属于本次功能交付的必需场景未满足时，不得宣称验证完成，相关合入按本节和第 4 节的必要验证要求处理；缺口不阻止诊断、修复和无关已授权工作。

**范围与授权边界**：仅分析/设计、文档排版或经核实不影响上述行为的重构，不强制模型试玩，须说明不适用理由。原本独立交付且尚不开放完整玩法的前置切片，只验收其真实范围并明确后续实玩缺口；不能在失败后改名为前置切片以规避验收。执行必须遵守已有用户授权、私有环境和有限总预算，读取本规范不新增付费、部署、生产访问或无限重试许可；授权已覆盖的范围不重复确认。

本条规定有条件的开发验收义务，不新增所有 PR 必跑的付费 CI check，不改变现有 GitHub required checks、权限或保护设置。确定性缺口先补普通 CI；真实自主行为和实际图形体验按手册补证，不因使用 subagent 自动升级为另一套重复的严格集成验证。此类测试选择规则的修改仍须接受本节要求的独立评审。

<a id="pr-description"></a>
### 4.1 PR 描述

Trace refs: O7-REQ-45815c91-fc25-43b0-b91b-e0ec221b6a20；本节落实[语言与写作要求](#language-and-writing)。

正文应让未参与执行的读者无需翻查聊天记录、提交列表或 diff，就能理解本次交付。以[默认 PR 模板](../../../.github/pull_request_template.md)为起点，先说明问题和目的，再组织以下内容：

- **问题与目的：** 原来的问题或能力缺口、影响及本次目标，按实际任务关系链接 Issue。
- **本次改动与结果：** 按行为、能力或规则说明具体变化及修改后的结果；文件路径用于定位，不能代替变化说明。文档 PR 写清确定或修订了什么设计、合同或操作方法，并区分设计、实现和实际验证状态。
- **验证结果：** 说明验证对象、方法、实际结果和重要未覆盖项；受测版本与详细证据可通过准确链接定位，不能仅写“CI 通过”或堆叠测试数量。
- **重要风险与剩余事项：** 写出影响审阅、使用或交付判断的兼容、发布影响和未完成事项；没有适用内容时省略。

简单变更可以合并相邻栏目，等价且清楚的结构同样有效；要求追踪和奖励申请按各自适用范围保留，不重复填写正文已有信息。网页、CLI、API 和 Agent 创建或更新 PR 都遵循本节；直接传入正文或从 commit 自动填充后，仍须核对这些信息。

正文维护当前候选相对目标分支的整体改动。创建、实质变更后及请求评审前核对正文与实际 diff、验证结论及剩余范围一致；草稿中的计划与已完成结果分开说明。收尾时修正过期的当前状态表述，GitHub 已显示的 Draft、合入状态无需另建一份副本。

详细命令输出、逐轮修复、旧候选失败和重复版本信息按[信息归属](#information-record-placement)保留在评论、原始证据或折叠附录，正文提供必要结论和入口。有效暂停、关键风险和影响交付的未验证范围仍在正文可见；更新当前摘要不改写历史候选的原始结果。

自检和评审核对读者能否回答“为什么改、实际改变什么、验证覆盖什么、还缺什么”，并指出影响理解的具体缺项。不新增字数、固定标题、关键词或文风评分门禁。

### 4.2 评审与合入

可以提前创建草稿获取反馈，也可以在完成实现后创建；草稿不是强制生命周期阶段。已有同一交付范围的 PR 应继续更新，不因修复或重新验证创建重复 PR。

用户要求暂停合入、发布或部署时，将限制记录在对应 PR 或操作入口可见的位置，并确保自动执行路径遵守。限制绑定实际动作，不阻止无冲突的开发和测试；只有来自用户或已授权主体的后续指令才能解除。

合入前检查当前 PR 和 source HEAD、全部必需检查、适用评审及阻断问题、冲突、权限和用户限制。必要检查未成功、真实阻断问题未解决、身份不明确或存在有效暂停指令时，不得合入。

默认使用正常受保护的合入路径，不以 `--admin`、关闭保护或伪造成功绕过门禁。确需调整规则或执行管理员操作时，应已有覆盖该动作的明确授权；管理员权限不代替真实验证和必要评审。

合入操作必须绑定已检查的预期 source HEAD，防止新 push 在检查后替换候选内容。源版本变化后重新检查受影响的验证和评审。自动合入仅在实际配置支持且其保护条件满足时使用，不假设存在 merge queue 或已启用 auto-merge。

## 5. 交付、状态与清理

代码任务在验收满足且实际 PR 已合入后完成代码交付。确认真实 merge 状态和对应提交，向用户报告结果及重要限制；不要求另建准备完成、任务完成和终态完成的证明链。

若用户目标还包含部署、数据迁移、真实环境验收、多个 PR 的整体结果或其他明确义务，继续完成这些工作后才能宣称整个请求完成。交付说明区分局部代码验证、实际组合验证和目标环境验收，注明各自版本及未完成范围；一种结果不代签另一种，单个 PR 合入不自动满足整体目标。长时运行或观测可在原 Task/PR 中单列，写明对象、固定版本与运行条件、观测窗口、负责人及退出条件，保留父项义务；不能将本次合入前必需的验收移到合入后。

Issue 和 Project 用于展示和管理。同步失败不改变代码已经合入的事实，但用户明确要求的管理动作仍需完成。协调多个交付项的 Issue 必须等所需义务完成后再关闭，不能由其中一个 PR 自动关闭。

工作区、分支清理和本地 main 更新独立于代码交付。清理失败或暂缓不使已合入任务退回未交付，也不阻塞无关工作。main 更新按本地需要进行，不作为完成前提。

任务验收完成且相关 PR 实际合入后，收尾时必须删除本任务产生的本地验收输出（包括临时日志、截图、fixture、运行目录和验收回执）及分支备份（包括备份分支、Git bundle 和补丁归档）。同一材料位于工作树外、临时目录或另建归档目录时，也属于清理范围；不得以迁移目录、压缩归档或创建备份代替删除。PR/Task 保留受测版本、验证结果及未覆盖范围，不要求为此继续保留本地副本。

清理范围还包括本任务的 Cargo target、增量编译和构建中间产物。默认目录位于工作区内；显式配置到外部的任务专属产物也须核对实际目标、归属、可复用性和进程占用后处理。仍在使用、可供其他 worktree 复用或归属不明的缓存不得随本任务清空，不能递归删除全局 Cargo 或 sccache 缓存。

只有用户明确要求保留，或适用的发行、审计、证据保留合同明确要求保留的材料，才按指定范围和期限保留；在 PR/Task 说明依据、位置和到期清理条件，不因“可能复核或恢复”默认留存。尚未完成验收、仍用于排障或被其他任务使用的资源，待用途结束后再清理；本条不授权删除正式发行资产、仓库内受版本管理的证据或其他任务的材料。

清理前确认准确仓库、路径、分支、预期提交和使用情况。保留有未提交或较新改动、仍在使用、被其他任务共享或身份不明确的资源；不删除 main，不以强制删除绕过资料、身份、交付或占用检查，不递归清空未知目录。删除引用须匹配预期 tip，执行后检查实际结果。只有确认可重建的缓存可以随清理丢弃。

<a id="submodule-worktree-cleanup"></a>
### 5.1 含子模块工作区的有条件清理

Git 对含子模块的 worktree 要求使用 `--force`，即使文件干净且已反初始化。仅在目标已交付、独立且未锁定，path/branch/expected HEAD 精确匹配，主工作树与子模块均无未提交、未跟踪、未知 ignored 资料及未推送工作，并已核对没有使用者时，允许通过[资源清理入口](../../../scripts/resource-cleanup-executor.py)显式传入 `--allow-submodules --execute`，先非强制反初始化，再对该精确路径执行一次 `git worktree remove --force`。此授权不允许双重 `--force`、删除锁定或脏工作区，或绕过其他保护。

检查必须覆盖已初始化和反初始化后留存的子模块 Git 数据及递归子模块；HEAD 必须匹配父仓库 gitlink，暂存区必须与 HEAD 一致，本地 refs/reflog 中存在未被已知远端引用覆盖的提交或不可达本地对象时保留。自定义 config/hooks、改动的默认模板、未知 Git 元数据及未完成操作同样保留。Git 数据外置、共享、额外 linked worktree、无法归属的残留模块数据或检查失败时保留；过程不自动 fetch。占用检查同时覆盖工作目录及将随 worktree 删除的子模块 Git 目录，有限观察域与并发限制沿用[清理接口](../../scripts/prd.md#资源清理接口)。执行前重查身份、材料与子模块状态，成功后读回工作树、注册和分支结果；预览或任何检查失败不得反初始化或执行强制删除。

## 6. 异常处理与操作保护

异常只阻塞依赖该信息或结果的动作。测试失败阻止合入，但允许在原范围内诊断、修复和重测，根因确认后按[设计检查与修复](#root-cause-design-check)处理；Project 不可用不停止普通开发；发布权限不足只阻止对应发布。说明具体失败、受影响动作和下一步，不把局部异常扩展为整个任务失效。

执行远程写入或破坏性操作前，确认目标仓库、环境、资源和当前状态，检查所需权限及用户限制。只读取当前动作需要的信息；执行后核实真实结果，不以本地日志、返回成功文本或生成文件代替服务器事实。

远程创建、更新或删除的结果不确定时，先查询并协调已有结果，再决定是否重试。不得盲目重复非幂等操作、覆盖用户内容或修改日志伪造成功。push、合入和删除引用使用准确目标及预期版本保护，避免影响并发的新工作。

部署、迁移和生产操作必须在已授权的目标、影响范围和限制内进行，并具备与风险相称的恢复办法。具体命令、环境参数和恢复步骤沿用适用环境的现有 runbook，例如[公开测试网部署与恢复](../../p2p/blockchain/public-testnet-governed-bootstrap.runbook.md)。遵守其中的技术安全约束，但不得借操作文档增加普通 PR 的通用审批或证据义务。

凭据和敏感运行数据不得写入仓库、公共日志或 PR 内容。权限不足、目标冲突或关键操作结果无法核实时，保留已有工作并停止依赖该条件的动作；其他已授权且不受影响的工作可以继续。
