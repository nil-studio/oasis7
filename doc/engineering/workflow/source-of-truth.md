# 开发流程规范

本文定义 oasis7 日常开发、验证、评审、合入和交付的通用规则。目标是让修改容易完成、结果可以核实，并把保护措施放在实际需要它们的操作边界。

## 1. 适用范围与规则边界

本文是通用开发流程的唯一规范。脚本、CI、AGENTS 和 skills 负责执行或说明这些规则，不得另设任务准入、审批、状态、证据材料或完成条件。发现不一致时，应修正对应实现和入口，不得用额外证明补偿规则冲突。

每项工作有一个明确负责人。负责人可以是人或主 Agent，可直接分析、设计、实现、自测和组织评审；专业角色和 subagent 按任务需要使用，不构成所有修改的必经环节。

Git、PR、实际 CI 结果和评审记录承载代码交付事实。Issue 和 Project 按跟踪需要使用；普通修改可以只有 PR。本地开发、测试和 PR 验证不依赖 Project 可用性，不要求额外任务标识或工作区登记。

按用户选择的工作类型交付：分析和方案请求交付结论或方案；实施授权覆盖同一目标和范围内的修改、测试及修复。提交更新、测试失败或 main 前进不要求重复确认。扩大目标或范围、增加尚未授权的外部影响、改变交付对象时，才确认新增部分；已经明确授权的动作不重复申请。

修改必需检查或合入策略时，必须同步规范、实现、执行入口和适用的 GitHub 保护设置，并核实它们一致。当前生效的保护规则始终约束实际合入；只修改文档不能解除已有强制检查或代替设置变更。

## 2. 日常开发

开始时明确问题、预期结果、必要的范围边界和验收方式。简单修改写在 PR 描述即可；复杂设计使用已有设计文档。只读查询和分析无需创建流程任务、分支、工作区或远程证据评论。

接手已有 Issue 开始实施时，代码和文档任务均须先检查 Issue 正文、评论、已有执行会话及同目标 PR，确认没有其他执行者正在处理或有效暂停；再在原 Issue 留下开工 comment，说明已开始实施、本次范围和负责人或可识别的当前会话关联，并回读确认发布成功后再开始修改。发现已有有效认领、并发留言或执行状态不明时，先核对并明确交接，不重复认领。评论发布失败或结果不明时先查询、重试或报告，不能假称已认领；只读分析可继续。同一会话续做同一范围复用已有开工记录，接管时补充交接说明；TPM 已发布且关联实际执行会话的领取记录可直接复用。开工评论用于协作去重，不是原子锁，也不扩大任务授权；不因此要求原本没有 Issue 的修改新建 Issue。

代码修改在独立分支进行，不直接修改 main。需要并行隔离时使用 worktree；工作区路径不是开发许可。保留用户已有改动，不擅自覆盖他人工作，并遵守明确的只读目录和资源边界。

本地编译优先复用少量固定路径的开发 worktree：串行任务在干净、未被其他执行者占用的开发工作区切换独立分支；并行任务才新增隔离工作区，不在 main 或主工作区修改。切换前保留未提交和未推送工作；不强制重置或替他人切换分支。固定路径复用该工作区的 Cargo target，跨工作区由 sccache 复用支持的编译结果。日常命令按受影响 crate、测试或 binary 执行，完整 launcher/playtest 和预热仅按需启动。操作及磁盘回收见 [testing-manual.md](../../../testing-manual.md)。

工作区入口统一使用仓库脚本和 Git 配置：先用 `git worktree list --porcelain` 检查已有工作区、分支和使用情况；当前聊天的附件列表不能代替仓库工作区清单。确需新增时使用 `./scripts/new-task-worktree.sh <module> <task> --base <ref>`，根目录取 `git config --local --get oasis7.task-worktrees-root`，未配置时按脚本默认值解析。Agent 不用 Codex App 的 `create_worktree`、worktree fork 或 handoff 代替该入口；用户明确指定时遵从用户要求。Cargo 默认使用工作区内的 `target/`，不预建缓存链接；已有 target 不自动删除，保留占用中和身份不明确的资源。日常反馈使用开发 wrapper，正式验收保留 canonical 命令和参数。

一个 PR 围绕一个清楚的交付目的，可以同时修改多个 crate、测试、配置和相关文档。原子修复不按包数量强行拆分；确有独立目的或独立交付价值时再拆 PR。

**最小完整改动**

修改前读取相关实现，沿实际调用和数据流确认消费者、状态、错误处理及适用约定。以本次验收和合同确定完整范围，包含必要的调用方、测试、配置和文档；同一根因在所属职责内修复，必要时跨模块联动。

先查仓库已有能力，再查标准库或平台能力、已采用依赖；行为、错误处理和状态约束相容时优先复用。新增抽象、依赖、配置、缓存或包装层应服务本次验收或已确认的职责与边界，不为未确认的未来用途预留机制。复用须遵守现有分层，不因代码表面相似合并不同职责，也不因实现数量少删除必要接口。

在满足上述要求的方案中，选择容易理解和维护的最小实现。精简保留必要的边界校验、错误传播、恢复、安全、兼容和可访问性，不以本次增删行数或文件数代替质量判断。性能和容量取舍依据适用的负载、设计目标或可核实的瓶颈，不要求每次修改另做基准测试。

在已有 PR 或设计说明中按需解释新增机制的具体用途、复用取舍和仍适用的限制，不另建统一说明表、债务账本或审批步骤。无关清理不自动纳入本次修改；验收、必要验证和适用评审满足后按既有流程交付。实施方法见 [executing-project-tasks](../../../.agents/skills/executing-project-tasks/SKILL.md)。

负责人可连续完成复现、实现和局部验证，无需逐步发布计划字段或等待机械状态转换。可稳定自动复现的行为缺陷，应有能检出该缺陷的回归测试；已有测试能够检出时直接复用，覆盖不足时增加或修正。机械修改不强制增加与实现重复的测试。

采用 subagent 时，说明具体问题、必要上下文、允许的写入范围和期望结果。并行编辑应避免重叠，由负责人合并结果；不要求固定角色组合、模型证明、派工回执或额外评审文件链。

修改影响对外行为、接口、部署方式或使用方法时，同步维护相关文档。文档长度是编辑参考，不能作为是否允许提交的门禁，也不能通过压成长行掩盖过量内容。

涉及当前目标、阶段进展、重要设计决定或部署边界的工作，负责人在收尾时按[指挥面板持续更新流程](../command-center/command-center.manual.md)维护受影响的[项目状态](../command-center/README.md)和[架构索引](../command-center/architecture/README.md)；开始相关工作或项目回顾时核对旧摘要。先更新已授权的主责条款，再同步带来源、时间和未知项的派生内容；尚未发生的合入、部署和验收不能预写。无实质变化不制造提交，合入事实可在下一次刷新批量补齐，不为每个 PR 新建状态 PR。摘要维护不增加任务准入、审批、完成证明或合入门禁，读取失败只影响有关信息的时效。

<a id="information-record-placement"></a>
### 2.1 长期文档与过程记录的归属

“同步相关文档”指维护受影响的长期要求、设计决定及理由、接口/安全/兼容合同、使用/验证方法和真实能力边界；它不要求把本次执行、评审或 CI 流水写回 PRD、design、manual、runbook 或 README。按信息职责决定位置，不按日期、目录、文件名或是否出现 SHA 判断去留。

| 信息 | 主记录位置 | 仓库保留内容 |
| --- | --- | --- |
| 短期目标、排期、负责人、依赖、阻塞、剩余项与下一轮安排 | 已使用的 Task Issue；普通变更可由当前 PR 承接 | 必要的来源/任务导航，不镜像可变任务状态 |
| 候选/合入 SHA、测试数、CI 等待与重跑、逐轮评审修复、清理与交接经过 | 同一 Task/PR 时间线，链接真实提交、检查与原始证据 | 合同所需固定版本身份及当前已验证范围；不追加逐 PR 交付日记 |
| 稳定产品要求、技术合同、已采用设计决定及理由、操作/恢复/测试方法 | 对应产品或专业 authority | 正文、可复用模板、输出字段及方法；任务不成为第二份规范 |
| 一次运行的原始事件、world/oracle、截图、fixture、manifest、hash 与不可重复事实 | 按证据生命周期保存的原始材料；Task/PR 定位该运行，本地验收输出按第 5 节清理 | 被消费者使用或需要长期审计的原件、固定 source/build/Skill/环境/窗口、原判定与必要解释；历史 run README 不继续追加后续 CI/收尾义务 |
| 当前方向、能力、风险与待决定事项的派生摘要 | 现有指挥面板索引，回链主责来源 | 来源、核验时间、覆盖范围与 unknown；替换同主题过期摘要，不复制逐候选尝试或测试计数流水 |

普通变更不因此强制创建 Issue、Project、任务标识或新的本地 ledger；已有 Task 只承接其真实范围，不能将 PR 编号冒写为另一个 Task Issue 的身份或捏造归属；没有独立 Issue 时，当前 PR 可以直接承载本次任务说明。已关闭或 `not_planned` 的任务只能标为历史来源，不恢复其义务。仍有效的暂停、部署/发布限制、未结发放义务与能力缺口须在当前 PR/操作入口或适用合同中继续可见，不能仅放进历史时间线。

长期合同不依赖阅读任务时间线才能理解接口、权限、失败/恢复或怎么使用。实填过程记录需要迁出时，先核准确接收方并保全独有历史，再精简源与修复引用/机器消费者；接收方未核实、原件不可取回或存在冻结/保留合同时，保留固定来源与原语义并注明限制，不批量建 Issue、不猜 Task，也不只留可能过期的 CI artifact 链接。后来的 PASS、合入或关闭不改写旧失败、旧候选或未验证范围；必要校验和更新只反映实际编辑，不能变成新的运行/审批证据。发行资产、许可/来源和版本身份按其原职责保留。

负责人在通常的自检与评审中核对上述分工：长期文档是否新增可变进度副本，运行记录是否混入后续收尾，摘要是否仍有决策价值；发现问题修在本次受影响范围。这是内容维护方法，不新增统一放行材料、每 PR 状态同步、固定数量指标或仅靠日期/SHA/Task 关键词阻断的门禁。

<a id="root-cause-design-check"></a>
### 2.2 根因确认后的设计检查与修复

开发、测试、CI 或实际试玩中确认问题根因后，负责人必须在修复实现前检查受影响的产品设计文档和系统设计文档。产品层检查要求、用户流程、体验、边界和验收标准是否遗漏、错误或冲突；系统层检查职责、接口、状态、失败/恢复与兼容合同是否正确且足以支持预期行为。不能仅因定位到某行代码就认定为纯实现 bug。

| 判断 | 处理顺序 |
| --- | --- |
| 产品或系统设计存在缺陷，包括同时存在实现 bug | 先修订受影响的产品要求/体验与验收标准，再修订受影响的系统设计，然后按正确约定补回归测试、修复实现并验证。只修改有缺陷或受联动影响的层级；系统设计有误不要求改动正确的产品文档。 |
| 设计正确且足以指导实现，问题只是实现偏离约定 | 直接复用或补充能检出问题的回归测试，修复实现并验证；不为走流程而修改正确设计或另造设计文档。 |

先补文档是工作顺序，不要求文档单独提交或先合入；同一 PR 可以连续完成文档、测试和实现。复现与诊断实验可以先行，可自动复现的行为仍须先观察回归失败再修复。若实现已经符合正确约定而只有文档失实，只修正文档并核验，不制造无必要的代码改动。不能通过改写正确设计或放宽测试来迁就错误实现。

缺少必要文档、约定含糊或无法确认设计正确时，不得默认归为纯实现 bug；先查主责文档和既有决定，确认属于设计缺口后在相应文档补齐。仅测试、环境或执行入口问题同样检查适用设计，无设计缺陷时修复对应对象，不强行引入产品设计。必要产品取舍超出已有授权时只暂停依赖该决定的动作，其他诊断与已授权工作继续。

在当前 PR 或已有 Task 中简述根因、设计判断及依据、受影响文档或无需修改理由、修复与验证结果即可；不新增固定表单、审批、Issue、状态或 CI 门禁。长期文档只保留正确约定和可复用方法，过程记录仍按第 2.1 节归属；新建或实质修改的跨层要求沿用既有追踪规则。

<a id="issue-lifecycle"></a>
### 2.3 Issue 五类与转换

Trace ID: O7-REQ-1a003dc5-18f2-4cd3-adbb-d1b95316086e

Issue 按跟踪需要使用，不要求每个 PR 建单；但新建或转换的 Issue 只允许以下五类，且每项恰有一个 `type:*` 分类标签。类型描述当前主交付物，不是执行状态；优先级、模块、`implementation:*`、阻塞或暂停不构成第六类。分类与正文必须一致，标题前缀仅用于阅读。

| 类型 / 唯一标签 | 准入与必要内容 | 完成或转换依据 |
| --- | --- | --- |
| 缺陷 / `type:defect` | 内外部测试发现的实际问题，待 Triage；记录预期/实际、影响、版本/环境、复现或观察证据、已知与未知。根因可未知，不把推测当事实 | 经查重与设计/实现判断，转文档、代码、测试或决策；证据不足保留缺陷并写清补证条件 |
| 文档 / `type:document` | 明确的产品/系统设计补充或其他文档改动；写清主责文件、内容缺口、范围和核验方式 | 文档改动按交付约定完成；仍需实现且满足代码准入时可转代码，否则按全部义务决定关闭或保留 |
| 代码 / `type:code` | 新功能/设计实施须引用完善、足以指导本次范围的产品文档和系统设计及版本；明确实现 bug 可引用正确既有约定、实际偏差和复现证据直接修复，不为形式补写正确设计 | 代码、回归及适用部署/真实验收均有准确版本证据；设计缺口先按第 2.2 节处理，未决产品取舍不得假定为明确 bug |
| 测试 / `type:test` | 对局部或全量功能的独立测试需求；写清对象、版本/环境、范围、方法、预期结果、执行权限及退出条件 | 交付实际覆盖、结果、未测范围和缺陷承接；测试完成不等于所有发现已修复，也不以 CI 代签真实体验 |
| 决策 / `type:decision` | 需要项目 owner 决定的具体问题；写清选项、取舍、推荐、影响和等待决定期间可继续的工作 | 记录有权决定者的真实结论及来源；需要落实设计时转文档，不能由 Agent 猜测决定或把沉默当批准 |

五份表单位于 `.github/ISSUE_TEMPLATE/`，创建者（包括 API/Agent）必须提供等价内容：类型、目标、来源与范围、验收、依赖、交付终点，以及该类型的专属依据。未知字段明确写未知与补证动作；代码准入所需设计或明确 bug 证据不能用“待补”代替。模板不默认添加 `implementation:ready`，类型也不授予模型、执行、合入或部署权限。

**转换沿用原 Issue ID。** 更新当前唯一类型和当前交付目标，保留原问题、讨论、来源、已完成成果及全部未完义务；以一条有实质变化的 comment 记录旧类型 → 新类型、证据/决定、已完成验收、剩余验收/依赖及下一责任人（无人承接如实写待承接）。先回读当前状态、认领和暂停；不能靠换类覆盖人工新要求、取消暂停或重复派工。多次 API 写入并非原子事务，结果未知先协调已有写入；正文与标签尚未一致时不得领取。

允许的转换包括缺陷 → 其他四类、文档 → 代码、决策 → 文档。任意类型 → 测试只在当前剩余主目标确实是独立测试任务、对象/范围/环境/退出条件明确时采用；实现中的普通自测、一次 CI 失败、未解决的代码/设计/决策不应换成测试来掩盖未完义务。测试发现新问题时优先补回同源且仍开放有效的原项，独立问题才另建关联缺陷；已关闭项真实复发按问题承接规则新建关联缺陷，不擅自重开或恢复已取消目标；原测试保留未完成覆盖。其他逆向纠错按真实主目标和准入证据记录，不机械沿流水线走完五类。

转换前核实执行者交接：代码转其他类不删除在途会话或暂停事实，先确认旧执行停止或交接；非代码不保留可消费的 ready，历史实现记录留在评论。转代码也不自动 ready，须另满足第 2.4 节的授权与依赖。独立交付确需拆分时才建关联项，原项明确每项义务的承接，不为一次类型转换新建整条 Issue 链。全部义务满足后才按授权关闭；重复、误报或决定不做按相应理由与证据关闭，不伪称已修复，也不为完成 Triage 强造下游任务。

**入口与实际约束。** 表单必填及 `blank_issues_enabled: false` 收窄普通网页入口，不是 GitHub API、特权空白入口或评论的硬校验；本仓不声称已部署服务端 Issue 格式拦截。创建者写后回读，dot Triage 和 TPM 领取前检查唯一类型、正文和依赖。缺类、多类或内容不完整是待修正输入，不是第六业务类型，不自动关闭；在核实前不得加入开发队列。评论是证据增量，不要求重复整套建单表单。没有新建单的普通 PR 不受此分类要求影响。

**采用与存量。** 采用本规范前，在授权范围核实五个分类标签存在且模板能正确应用；GitHub 不保证自动创建模板引用的标签。保留 `code-development` 作为旧搜索兼容提示，不能代替 `type:code`。先只读盘点旧项的目标、状态、认领与设计依据，再在已批准范围渐进补类；不根据标题猜类别、不全库覆盖正文、不重开已关闭项。活跃项先与原执行者对齐，原义务及暂停优先。模板、消费者规则、标签配置和实际调度分别记录采用状态；本 PR 不代表线上标签、旧 Issue 迁移或 20 分钟运行器已经启用。

### 2.4 可选的 dot 与 Coding Agent Issue 交接

用户采用此方式时，dot 把已授权的 Rust/JS 开发目标、范围、来源、验收、依赖和交付终点写入 GitHub Issue，交给 Coding Agent（代码开发执行者）实现。Coding Agent 使用用户选定且获准的开发工具或服务；用户手动启动 TPM 会话，由 TPM 使用当前工具实际提供的会话能力领取并派发任务，dot 不直接启动开发执行。TPM 在已批准的仓库、发布者、执行与预算范围内去重领取，默认一个有效 TPM 和一个开发执行并发；同一 Issue 的后续修复优先续接原 Coding Agent 会话，dot 接续具体环境授权内的部署、测试和反馈。操作与启动提示词见 [TPM 会话工作约定](../../../.agents/roles/tpm.md#手动启动的-tpm-会话)。这是可选工程协作入口，产品层不适用，不为普通 PR 增加 Issue、审批或角色链，也不依赖专用调度代码。

只有满足[五类合同](#issue-lifecycle)的唯一 `type:code`、正文完整且依赖/授权具备的 Issue 才可进入 ready；缺陷、文档、测试和决策不由代码队列误领。

以下标签描述代码实现任务的状态，不绑定具体开发工具，也不授予执行权限：

| 标签 | 协作含义 |
| --- | --- |
| `implementation:ready` | 代码实现条件已具备，尚未确认领取 |
| `implementation:active` | 代码实现任务已被接手；实际执行、等待 CI 或等待验收状态以会话和 PR 为准 |
| `implementation:blocked` | 存在明确依赖或执行障碍，记录原因及解除条件 |
| `implementation:paused` | 暂停相应派工和执行；有权解除该暂停的后续指令到来后才能继续 |

授权与交付仍遵守本规范：同目标修复不重复确认，新增范围才核对新增授权；PR、当前 source HEAD 的检查和评审以 GitHub 实际结果为准。Issue 留存真实会话关联与待办，创建或执行结果不明确时先核对，不重复派工；原会话不可恢复时，确认旧执行停止并保全已有工作后再交接。Coding Agent 按任务的实际合入授权执行，PR 使用 `Refs #<issue>` 关联；dot 核实整体义务，包括适用部署和真实验收后，才在已有权限内关闭 Issue。有效暂停必须阻止相应后续执行，不能靠下一轮检查或重开会话自行解除。约五分钟的检查是 TPM 活跃期间的工作节奏，实际持续能力以客户端为准，文档不保证会话结束后仍在后台执行。

## 3. 验证与评审

先用最小有效验证获得反馈，再由 CI 执行完整的必要检查。具体命令和环境准备见 [testing-manual.md](../../../testing-manual.md)。验证记录应能说明执行了什么、针对哪个版本、结果如何及未覆盖的部分，按[信息归属](#information-record-placement)放在实际 PR/Task 及适用原始证据中；长期文档维护验证方法与证明边界，不另造通用放行回执。

CI 按实际改动及受影响消费者选择测试。选择范围必须考虑新增、删除、重命名两端、依赖关系、features、生成输入、共享配置及锁文件变化；无法可靠解析 Git/依赖输入时扩大覆盖；已确认未匹配任何包归属、显式范围或共享控制规则的路径，按[未登记路径门禁](../../testing/ci/ci-tiered-execution.prd.md#ci-unknown-inputs)使规划和最终 required check 失败，不以全量回退掩盖规则缺口。包关系用于选择测试，不用于禁止合理修改。

最终 required check 必须在所有选中的必要任务结束后汇总，并以 `always` 等可靠机制在失败或取消路径仍执行。只有预期任务全部真实成功才能通过；失败、取消、缺失、未知结果，或应执行却跳过的任务均不得算成功。未被计划选中的任务可以不执行。

CI 结果必须对应实际 source HEAD 和测试对象。测试合并树时还应能识别真实 base、event commit 和 tested tree；不得把只测试过源分支的结果宣称为最新 main 组合验证，也不得将旧结果改写成新版本证据。

普通 PR CI 的 GitHub 权限只读，不授予生产凭据或部署身份。需要特殊权限的验证使用受控入口，固定已批准的待测版本并授予最小权限。PR 缓存和产物不得直接成为特权入口的可执行输入。

改变 CI workflow、测试入口或选择规则的 PR，必须接受独立评审，并验证测试确实按既定保护要求执行。候选代码不能通过删减必要任务、改变汇总条件或伪造同名成功状态为自己放行。

评审按复杂度和风险选择。普通变更由负责人自检并按需安排独立评审；机械文档不强制领域角色或 QA。权限、凭据、共识、持久化兼容、不可逆迁移、关键安全边界和开发门禁变更必须有对应能力的独立评审，评审者不得批准自己编写的部分。

<a id="evidence-based-review"></a>
评审先读适用要求和 diff，再沿调用、状态变换核对受影响消费者。先检查正确性、安全、数据保护及实际负载下的行为，再评估验证、性能和简化。缺陷结论应给出具体位置、可核对的触发条件或可达路径、影响及依据；代码能够确认的风险无需等到事故或运行复现，尚未确认的疑点则说明待核查条件。

评审记录说明所审阅的版本、结论、阻断问题及处置即可。真实的正确性、安全性或数据丢失风险必须修复或以事实证明不适用。简化建议应指出具体冗余或复用入口，并保留所需行为与边界；不影响本次验收且未揭示实际风险的纯简化或风格建议按非阻断处理，可以说明理由后不改，不自动创建后续任务。已有取舍记录或临时注释不豁免当前要求和风险检查。修改后的复审针对实际变化及受影响部分，不强制所有角色重复全量审阅。具体方法见 [requesting-repo-owned-review](../../../.agents/skills/requesting-repo-owned-review/SKILL.md)。

CI 和独立评审可以并行，合入时汇总两者。一般情况下，当前 PR 的 source HEAD 已通过全部必需 CI 即满足 CI 合入条件；main 前进或分支显示 `BEHIND` 本身不使该结果失效，不要求因此 rebase、合并 main 或重新运行 CI，也不要求重做设计、开发或全部评审。GitHub 的必需状态检查保留，但关闭“合入前分支必须跟上 base”的要求。存在合并冲突，或 main 的相关变化带来明确的集成风险时，才按需要更新分支并验证实际合并组合；必须说明具体冲突或风险，不能仅以 main 前进要求重测。source HEAD 变化后，重新运行必要的普通 CI，并复审实际变化及受影响部分；已有 CI 结果仍只代表实际测试过的版本和组合。

修改 UI 时，须在 PR 或交付说明中附上实际运行界面的验证截图，标明受测版本、界面状态和视口尺寸，并覆盖本次受影响的桌面、窄屏或关键交互状态；截图不能代替功能验证，模拟或组件预览须明确说明其范围。

普通 CI 是默认验证方式。缺测试先补 CI；只有明确需要普通 CI 难以提供的环境、跨系统状态或部署恢复过程时，才增加专项集成验证。专项验证必须说明具体环境缺口、验证目标、执行版本、实际结果和剩余限制。高风险本身不等于需要重复执行另一套相同 CI。

已有绿色结果后追加阻塞验证时，先暂停合入并触发包含该项的 PR 验证；当前版本通过后才解除相应暂停。删除标签或修改描述不能自动取消尚未满足的验证要求。

<a id="agent-gameplay-selftest"></a>
### 3.1 Agent 游戏功能的开发自测

验证 Agent 通过正式游戏 Skill/API 自主游玩及相关玩家协作功能时，负责人必须按[开发 Agent 自测操作手册](../../testing/manual/agent-runtime-self-playtest.manual.md)组织自测，不以普通 CI 通过或源码审阅代替实际游玩。命中本条范围时主动执行，不以用户另行提醒或再次点名手册为前提；具体步骤和模板只在手册维护。

**触发范围**：本次交付或验收涉及 Agent 的游戏接入、正式玩家 Skill 使用方式、能力发现与行动、实际 Runtime/worker、目标/问答/审批、预算/停止/恢复、Agent 可玩的生产或其他玩法，以及与这些能力关联的 Web/桌面观察和高层指导。按行为与受影响消费者判断，不仅按文件扩展名或目录；改变玩家 Skill 的指令或上手路径即使只改 Markdown 也属于此范围。

先执行适用的普通单元/合同/故障回归，再按手册选择能覆盖本次行为的最小实际场景。开发主 Agent 读取手册、固定候选及获准私有测试环境，派出真实独立试玩 subagent 读取同一候选的正式游戏 Skill，自主启动或接入、游玩并反馈；负责人核对原世界操作/回执，确认缺陷及根因后先按[设计检查与修复](#root-cause-design-check)分流，再补普通回归、修复并用新候选复测。试玩者不得获得源码答案或测试侧世界写权限。Runtime/profile、冷启动/准备态与 Web/桌面按实际受影响范围分别验证，不要求每次遍历全部七组场景或所有平台。

**完成判据**：在当前 PR 或已有测试记录中说明受测 source/build/Skill、实际 Runtime/profile、选中场景、真实子会话和操作结果、缺陷处置、复测及未覆盖项；复用现有记录，不新增通用证书。固定动作脚本、mock、模型自报、健康检查、截图存在或世界自然活动不能代签自主试玩；API 结果不能代签图形交互。新候选的结论不得直接沿用旧构建的实玩结果，失败尝试不能被一次重跑成功覆盖。

**缺前置与阻断**：缺游戏 Skill/API、适用 Runtime、独立派工/GUI 工具、有效权限、隔离环境或预算时，先完成可执行的预检和普通测试，并把受影响场景如实标为 blocked/inconclusive。降级的主 Agent/脚本测试只证明其实际范围，不能将未执行场景改为 not_applicable 或通过。属于本次功能交付的必需场景未满足时，不得宣称验证完成，相关合入按本节和第 4 节的必要验证要求处理；缺口不阻止诊断、修复和无关已授权工作。

**范围与授权边界**：仅分析/设计、文档排版或经核实不影响上述行为的重构，不强制模型试玩，须说明不适用理由。原本独立交付且尚不开放完整玩法的前置切片，只验收其真实范围并明确后续实玩缺口；不能在失败后改名为前置切片以规避验收。执行必须遵守已有用户授权、私有环境和有限总预算，读取本规范不新增付费、部署、生产访问或无限重试许可；授权已覆盖的范围不重复确认。

本条规定有条件的开发验收义务，不新增所有 PR 必跑的付费 CI check，不改变现有 GitHub required checks、权限或保护设置。确定性缺口先补普通 CI；真实自主行为和实际图形体验按手册补证，不因使用 subagent 自动升级为另一套重复的严格集成验证。此类测试选择规则的修改仍须接受本节要求的独立评审。

## 4. PR 与合入

PR 标题和完整 commit message 使用英文。

PR 描述具体问题、主要改动、验证结果和重要风险，按需链接 Issue。可以提前创建草稿获取反馈，也可以在完成实现后创建；草稿不是强制生命周期阶段。已有同一目的的 PR 应继续更新，不因修复或重新验证创建重复 PR。

用户要求暂停合入、发布或部署时，将限制记录在对应 PR 或操作入口可见的位置，并确保自动执行路径遵守。限制绑定实际动作，不阻止无冲突的开发和测试；只有来自用户或已授权主体的后续指令才能解除。

合入前检查当前 PR 和 source HEAD、全部必需检查、适用评审及阻断问题、冲突、权限和用户限制。必要检查未成功、真实阻断问题未解决、身份不明确或存在有效暂停指令时，不得合入。

默认使用正常受保护的合入路径，不以 `--admin`、关闭保护或伪造成功绕过门禁。确需调整规则或执行管理员操作时，应已有覆盖该动作的明确授权；管理员权限不代替真实验证和必要评审。

合入操作必须绑定已检查的预期 source HEAD，防止新 push 在检查后替换候选内容。源版本变化后重新检查受影响的验证和评审。自动合入仅在实际配置支持且其保护条件满足时使用，不假设存在 merge queue 或已启用 auto-merge。

## 5. 交付、状态与清理

代码任务在验收满足且实际 PR 已合入后完成代码交付。确认真实 merge 状态和对应提交，向用户报告结果及重要限制；不要求另建准备完成、任务完成和终态完成的证明链。

若用户目标还包含部署、数据迁移、真实环境验收、多个 PR 的整体结果或其他明确义务，继续完成这些工作后才能宣称整个请求完成。尚未完成的部分应清楚列出；单个 PR 合入不自动满足整体目标。

Issue 和 Project 用于展示和管理。同步失败不改变代码已经合入的事实，但用户明确要求的管理动作仍需完成。协调多个交付项的 Issue 必须等所需义务完成后再关闭，不能由其中一个 PR 自动关闭。

工作区、分支清理和本地 main 更新独立于代码交付。清理失败或暂缓不使已合入任务退回未交付，也不阻塞无关工作。main 更新按本地需要进行，不作为完成前提。

任务验收完成且相关 PR 实际合入后，收尾时必须删除本任务产生的本地验收输出（包括临时日志、截图、fixture、运行目录和验收回执）及分支备份（包括备份分支、Git bundle 和补丁归档）。同一材料位于工作树外、临时目录或另建归档目录时，也属于清理范围；不得以迁移目录、压缩归档或创建备份代替删除。PR/Task 保留受测版本、验证结果及未覆盖范围，不要求为此继续保留本地副本。

清理范围还包括本任务的 Cargo target、增量编译和构建中间产物。默认目录位于工作区内；显式配置到外部的任务专属产物也须核对实际目标、归属、可复用性和进程占用后处理。仍在使用、可供其他 worktree 复用或归属不明的缓存不得随本任务清空，不能递归删除全局 Cargo 或 sccache 缓存。

只有用户明确要求保留，或适用的发行、审计、证据保留合同明确要求保留的材料，才按指定范围和期限保留；在 PR/Task 说明依据、位置和到期清理条件，不因“可能复核或恢复”默认留存。尚未完成验收、仍用于排障或被其他任务使用的资源，待用途结束后再清理；本条不授权删除正式发行资产、仓库内受版本管理的证据或其他任务的材料。

清理前确认准确仓库、路径、分支、预期提交和使用情况。保留有未提交或较新改动、仍在使用、被其他任务共享或身份不明确的资源；不删除 main，不以强制删除绕过资料、身份、交付或占用检查，不递归清空未知目录。删除引用须匹配预期 tip，执行后检查实际结果。只有确认可重建的缓存可以随清理丢弃。

## 6. 异常处理与操作保护

异常只阻塞依赖该信息或结果的动作。测试失败阻止合入，但允许在原范围内诊断、修复和重测，根因确认后按[设计检查与修复](#root-cause-design-check)处理；Project 不可用不停止普通开发；发布权限不足只阻止对应发布。说明具体失败、受影响动作和下一步，不把局部异常扩展为整个任务失效。

执行远程写入或破坏性操作前，确认目标仓库、环境、资源和当前状态，检查所需权限及用户限制。只读取当前动作需要的信息；执行后核实真实结果，不以本地日志、返回成功文本或生成文件代替服务器事实。

远程创建、更新或删除的结果不确定时，先查询并协调已有结果，再决定是否重试。不得盲目重复非幂等操作、覆盖用户内容或修改日志伪造成功。push、合入和删除引用使用准确目标及预期版本保护，避免影响并发的新工作。

部署、迁移和生产操作必须在已授权的目标、影响范围和限制内进行，并具备与风险相称的恢复办法。具体命令、环境参数和恢复步骤沿用适用环境的现有 runbook，例如[公开测试网部署与恢复](../../p2p/blockchain/public-testnet-governed-bootstrap.runbook.md)。遵守其中的技术安全约束，但不得借操作文档增加普通 PR 的通用审批或证据义务。

凭据和敏感运行数据不得写入仓库、公共日志或 PR 内容。权限不足、目标冲突或关键操作结果无法核实时，保留已有工作并停止依赖该条件的动作；其他已授权且不受影响的工作可以继续。
