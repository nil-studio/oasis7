# Package source and archive security

Testnet 在同一个不可变 source plan 后并行启动 Web 构建与原生编译，各用独立 runner。原生编译仍只有一个互斥的可信/只读入口；安装包组装等待 Web 成功、且两个原生入口恰有一个成功另一个 skipped，失败、取消或未知状态不能进入组装。原生中间归档只从同一 run 下载，组装前核对 source SHA、platform、target、profile、ops 范围及每个固定二进制的 SHA-256/权限，缺失、symlink 或篡改拒绝；组装不再调用 Cargo。所选 source 必须包含支持 native stage 的构建脚本与 `package-native-stage.py`，旧 source 缺少该支持时在编译前拒绝。最终 SOURCEPLAN/BUILDINFO、入口验证和校验和合同不变。并行收益以实际 hosted 耗时为准，原生 runner 的 Cargo 并发固定为 1，避免多个重型 Thin LTO 构建同时占满内存；这不影响 Web/native 跨 runner 并行。

Ordinary Rust CI and Release/Mainnet runtime core, support, sync and soak gates restore `ci-shared-native-trusted-v3`. Only the main scheduled/manual-full regression produces this dependency union, including explicit build-only variants absent from its normal test target; it saves only after the complete job succeeds. Gate consumers have read-only cache tokens and disable saves. The effective pinned toolchain set, Cargo/WASM environment and archive paths must agree. The cache preparation helper removes unrelated preinstalled toolchains only on ephemeral GitHub-hosted Linux runners, after validating every required pinned toolchain and the active compiler. It does not disable Rust environment hashing. Changes to production coverage require a cache generation change; source/run IDs do not create fresh large archives on every run. The two NewAPI entrypoints preserve their existing paired identity.

Formal workspace storage uses a separate [post-save retention policy](../../testing/ci/ci-tiered-execution.design.md#ci-cache-budget-design). Only the successful trusted main producer activates the isolated maintenance job with `contents: read`, `actions: write` and `cache-mode: none`; compilation and candidate jobs do not inherit its deletion token. The helper verifies the current run and complete saved cache, retains the current compatibility group and protected recovery points, and retires only explicitly enumerated migrated native, Release gate, Web and ECS namespaces with a confirmed complete main replacement. Two complete cache and active-run inventories protect observed concurrent use, recent accesses and unfinished uploads; deletion requires stable immutable identities and the intersection of both plans. Unknown namespaces and other refs are retained. Query or deletion failures do not change required build/test outcomes, and this policy does not promise that the repository total immediately falls below its quota.

Package workflows resolve source identity once in `scripts/package-source-plan.py` from the workflow revision. Release and Mainnet accept the existing semver or daily tag families, peel annotated tags, and require the commit to belong to the default branch history. Testnet accepts explicit branch/tag refs or full commit OIDs and rejects ambiguous bare names. Candidate jobs check out the plan commit without persisted credentials and verify HEAD before executing source. Native artifacts must include a platform `SOURCEPLAN.json`; its `checkoutSha` corresponds to BUILDINFO's `commit`. The launcher freshness manifest records source fingerprints, asset hashes, and build profile/target; it currently has no Git commit field and does not replace `SOURCEPLAN.json`. Publishing compares the current release tag against the planned commit without moving it.

All workflow actions use immutable official repository commits with their existing major version comments. Candidate packaging and ordinary Rust jobs have scoped read-only cache tokens and disable normal Rust cache saves. Testnet native steps run exactly once: a write-scoped job is selected only for a Linux-only packaging-profile main workflow dispatch whose planned source and workflow revision both equal the event commit; every other ref/SHA uses the read-only job. The shared steps verify the actual checkout again before restoring/saving, and only a successful Linux job in the trusted lane may save its profile-specific cache. Non-Linux Testnet consumers remain restore-only. Release `build-web-dist` is the sole `release-packages-web-wasm-trusted-v3` writer, only after a successful main build whose planned source and workflow SHA equal the event commit. Release Web gate, Mainnet, Testnet and ECS Web restore only. Planned historical sources without the new toolchain helper skip these Rust caches and retain their normal cold build. Linux packaging keeps its separate target/profile identity and existing trusted writer predicates. ECS retains the successful main-only native lane with `oasis7-ecs-native-linux-ecs-v2`. No restore key reaches an older generation. Release/Mainnet core and support gates use full source history and a planned-commit parent/head documentation range; gate pipelines propagate upstream failures through `pipefail`.

Trunk uses the existing `trunk-archive` identity shared with ordinary Rust CI, including OS, architecture, version and the verified source's installer hash. The main scheduled/manual-full regression is its writer; Release and Testnet restore the same archive with a pinned restore-only action and always invokes `scripts/install-ci-trunk.sh`, including on a cache hit. That installer verifies the pinned official archive digest before extraction and checks the binary version. Release and Testnet reject a missing, empty or symlink installer in the planned source before restoring this cache; older tags without that helper are not supported by the new workflow. A cache miss downloads the same verified archive, without a source-build or alternate-source fallback. Other Release cache write policies remain unchanged. Cross-tag restoration and cold/warm costs require actual writer/reader observations; the [CI dependency design](../../testing/ci/ci-tiered-execution.design.md#ci-install-cache-design) defines those boundaries.

The existing workflow governance job runs `.github/actions/cache-permission-probe`, which attempts to reserve a unique empty cache entry with its read-only scoped token and requires denial. It never uploads data or logs bearer tokens or signed URLs. The existing main full-regression job saves a small new-generation sentinel. Candidate governance restores and verifies it when seeded; an initial unseeded result is explicit. Hosted execution is needed to establish token enforcement and the first writer/read restoration sequence. Restore, build and save times remain available in the existing action logs; the first generation switch incurs a separate cold-cache cost.

`scripts/safe_git_archive.py` supplies a bounded archive policy to current operator extraction, checkpoint validation and external WASM summary imports. It bounds compressed input, disk-spooled decompression, physical headers, extended metadata, member count, individual and total file bytes, and elapsed time before `tarfile` interprets PAX or GNU metadata. XZ is rejected because current consumers use plain or gzip tar and an XZ dictionary would require a separate decoder memory policy. Authority extraction rejects links and special files; the optional Cargo snapshot policy preserves safe relative final symlinks. Validation and extraction failures remove the created tree, and Git capture returns a tree only inside its temporary context. The defaults are 512 MiB archive input, 100,000 physical members, 128 MiB per member, 1 GiB expanded file bytes, 4 MiB extended metadata, and 120 seconds. Tests use smaller budgets for boundaries; these values are local policy and cannot be raised by archive content.

The older `scripts/pm` Cargo snapshot consumers, receipt closures and nested dependency-line lock regex from the October 8 proposal no longer exist in the current baseline. The current repository does not restore these deleted governance tools. The remaining remote rollout helper closure carries the new archive policy file with the same mode and checksum validation as the operator extractor. External archive imports load the helper from the trusted script file path under Python isolated mode.

Local regressions cover source resolution, input control characters, ambiguous refs, annotated tags, all current workflow pins and SHA consumers, cache generation, archive traversal and links, extended-header budgets, decompression budgets, executable modes, truncated input, and extraction cleanup. Actual hosted cache permissions, publication tag drift, and platform package execution remain subject to ordinary GitHub workflow validation.

<a id="final-artifact-freshness"></a>
## Final artifact identity and freshness

The following contracts refine the [player-entry and distribution product boundary](../../product/player-entry-distribution/prd.md). They are requirements for the named producer/consumer paths, not assertions that every platform package or upgrade scenario has passed. Packaging owns artifact identity and installed layout; release helpers own version publication and retention; runtime authority and world recovery remain outside software delivery.

Provenance and freshness are separate checks. A source plan identifies the intended checkout; a freshness result establishes that the chosen binary and generated assets correspond to their actual relevant inputs, profile and target. Matching a filename, mtime, version string or a partial source fingerprint cannot replace the input closure. That closure covers the executable's relevant sources, local dependencies, dependency locks, build scripts, generators, asset inputs and configuration affecting the build. Changing a relevant input must invalidate the old selection. The normal build-and-package entry rebuilds as needed; a low-level entry that cannot rebuild rejects stale material instead of publishing it. This does not add a Git commit field to the existing freshness schema or replace SOURCEPLAN with a second identity format.

Validate the final downloadable artifact, not just a build directory or CI intermediate. Every applicable native Testnet artifact must carry its own SOURCEPLAN and BUILDINFO with matching checkout identity and the required checksum coverage. Evidence from ordinary Release does not stand in for Testnet. Tests trace fixture source change through invalidation, binary/asset selection and the final package manifest; offline mock selection proves the selection contract only, not a real platform build or publication.

Generated Web aliases must match the expected generated content or its recomputed exact digest. Finding an expected import substring is insufficient: appended JavaScript, extra content or mismatched generated WASM/glue must be rejected even when the expected import remains present. Hash, alias and manifest validation apply to the bytes actually delivered. These checks do not authenticate a distributor or replace the existing signing policy.

<a id="installed-package-boundary"></a>
## Installed package boundary

An installed package must run without the source checkout, build working directory or mounted distribution image. Debian acceptance invokes all four published PATH wrappers from an unrelated directory and checks argv/environment forwarding. macOS acceptance copies only the `.app`, unmounts the DMG, uses a path containing spaces and exercises the application's actual bundle-relative assets and app-only replacement. Copying extra unlisted files beside the app cannot make an otherwise incomplete bundle pass.

Generated shell wrappers are tested with the supported macOS Bash 3.2 path as well as their ordinary supported environments. An unset or empty profile omits the profile flag and leaves the binary's default authoritative; wrappers do not hard-code a competing preset to make a fixture pass. A `--version` result proves only that entrypoint's version behavior, not all commands, environment forwarding, assets or install/upgrade compatibility. Previously completed platform subitems are not reopened merely to satisfy this broader contract.

The download page must retain its existing public contract independently of JavaScript: applicable download actions are real anchors, supported language selection is keyboard-operable, and narrow/desktop layouts preserve usable targets. Platform descriptions, including Windows entrypoint behavior, match the actual package rather than another platform's launch semantics. Site layout tests and installed-package tests are separate evidence.

<a id="release-upgrade-retention"></a>
## Upgrade commit and post-success retention

Version staging, upgrade commitment and old-version cleanup are different phases. Resolve and validate the candidate -> stage it without deleting prior releases -> perform the existing start/health/status acceptance -> commit the successful current-version selection and release metadata -> apply retention. An existing helper may use a reversible provisional selection during probing, but a failed pre-commit attempt must preserve or restore the prior current pointer and release metadata, and must not prune old release directories.

For example, with A/B/C already present and C current, a failed attempt to install D must leave A/B/C and the original current/metadata intact whether failure occurs at start, health or status. Only a successful D may trigger the configured retention policy. Retention preserves the current and required previous release even when the configured count is zero or smaller than that protected set; the helper must explain the resulting protected exception rather than delete an active recovery target. This requirement does not change the existing meaning of the configured retention count.

Cleanup failure after a committed upgrade is reported as successful upgrade with incomplete cleanup, with safe diagnostic/retry information. It is not an atomic upgrade rollback: already-deleted versions cannot be promised back. Repeated cleanup uses current filesystem facts and protected identities, excludes unrelated directories, and is limited to eligible release artifacts. It never treats world state, configuration, backups, journals or logs as old binaries eligible for retention deletion.

Binary/version rollback does not roll back world history. Preserve the product distinction between a compatible continuation, a failure proven not to have modified state, and an unknown or possibly modified state requiring the authoritative recovery path. This document adds neither automatic schema migration nor cross-directory player-state preservation to the existing manual-upgrade product. It does not authorize a host upgrade, service stop, destructive cleanup or public release.

<a id="distribution-acceptance-boundaries"></a>
## Verification and signing boundaries

| Contract | Required observation | Does not prove |
| --- | --- | --- |
| Relevant-input freshness | Change relevant source/dependency/generator/config; normal entry rebuilds, low-level stale selection rejects | Correctness of unexecuted native binaries or all platforms |
| Final artifact identity | Extract each applicable final native Testnet download; check SOURCEPLAN, BUILDINFO and checksummed bytes together | Ordinary Release equivalence, signing or a deployed world |
| Web generated alias | Recompute exact expected content/hash; reject appended or altered code | General site security or distributor authenticity |
| Installed layout | Real supported package entrypoints outside checkout/DMG, with spaces, argv/env and profile boundary | Real gameplay, all operating-system combinations or automatic state migration |
| Failed upgrade | Start/health/status failures separately preserve A/B/C, current and metadata | Rollback of potentially changed authoritative world data |
| Successful retention | Cleanup only after success; protected current/previous, zero count and cleanup failure remain distinguishable | Recovery of already deleted artifacts or permission to touch non-release data |

Signing and notarization remain the separately triggered broad-distribution requirement. Until the applicable evidence and product decision exist, preserve technical-preview/restricted-use wording; artifact checksums or these documentation changes cannot turn an unsigned build into a broadly released product. No signing, credentials or platform administration is part of this design change.

## ECS 服务端目录包

`ecs-packages.yml` 的手动入口只打包所选 workflow ref 对应的 `github.sha`，无第二个可变源码 ref；三个 job checkout 同一 SHA。Web 与原生独立并行，同 run 的 artifact 在汇合 job 组装，组装不执行 Cargo。原生仅选择 chain runtime、game launcher、viewer live 三个 bin / 对应 package，不包含桌面 client、独立 web launcher、安装器和 ops 工具。Viewer Web 使用既有 split delivery 构建器，把可选 payload 一并放入可发布目录。

ECS 使用独立 `ecs` profile（继承 release、opt-level 3、关闭跨 crate LTO、codegen-units 16），Linux x64。Cargo jobs 默认 2，手动入口允许选择 1 做同 SHA 对照；并发值仅传给编译步骤，不参与缓存身份。完整发行包的 `packaging` profile 不变。原生缓存使用独立 ecs-profile 命名空间，不把旧 packaging 缓存命中宣称为新 profile 复用。构建保留 GNU time 的耗时 / CPU / 最大单进程 RSS，以及每秒采样的主机内存余量、swap 和可读取的当前 cgroup 内存 / OOM 计数；资源记录与 Cargo timing 报告随 run 保存。最大单进程 RSS 不是并行构建的总内存峰值，cgroup 历史峰值也不是本次构建独占用量；缺失指标标记为未知。对照结果记录源码 SHA、runner、缓存恢复身份和 Cargo fresh / dirty 数量，单次测量不宣称为稳定收益。优化参数变化后的实际吞吐和包体积需重新实测，不能沿用旧 packaging 构建的性能结论。原生 stage 记录 source/profile/platform、固定 binary 集合、字节 SHA256 和执行权限；组装匹配实际 checkout 身份并校验后输出 `bin/`、`web-dist/`、BUILDINFO、manifest 和完整 SHA256SUMS，归档另有外部校验和。不得把这个目录包称为已安装 `.deb` 或绕过既有安装器的校验入口；它通过单机手册的独立版本目录部署，仍需保持世界、私有配置及回滚版本。

ECS 组装同时从固定 source 的 Git 对象发布正式 `skills/oasis7-play/`，不能混入 dirty checkout、未跟踪文件或旧 Bridge Skill。源 Markdown、引用、版本清单与发现页一同进入 `web-dist/skills/`，受整包校验和约束。随包发布工具在部署侧核对实际 launcher 与所选 release、清单 source 和文件字节，生成仅含精确 GET / HEAD 路径的 Nginx include；公网逐字节校验失败恢复旧 include。每次升级 / 回滚均随游戏版本发布，操作见下述单机手册；这不新增部署凭据或 CI 自动安装权限。

候选 ref 的工作流和原生 job 仅只读缓存。仅 main 且 workflow SHA 等于 source/event SHA 的原生 job 有缓存写权限，保存到独立 ECS 命名空间；失败不写缓存。Web 仅恢复既有可信缓存。汇合要求 Web 成功且恰好一个原生 lane 成功、另一个预期跳过；失败、取消或缺失不能生成最终包。入口只有内容读取和 artifact 上传，不含部署凭据、自动发布或自动安装。操作方法见[单机 ECS 手册](../../testing/manual/single-ecs-preview-deploy.manual.md)。
