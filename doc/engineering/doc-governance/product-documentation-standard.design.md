# 产品文档内容规范正文

- 配对需求文档：[`product-documentation-standard.prd.md`](product-documentation-standard.prd.md)
- 可复用模板：[`product-documentation-standard.templates.md`](product-documentation-standard.templates.md)
- 适用产品入口：[`doc/product/README.md`](../../product/README.md)
- 状态：`active`（本仓库已采纳的内容规范）

本文是产品文档内容的 canonical 规范。`必须（MUST）`、`不得（MUST NOT）`、`应该（SHOULD）`、`可以（MAY）`分别表达适用范围内的要求强度；强度不等于优先级、实现状态或发行结论。

## 1. 产品树与权威边界

`doc/product/README.md` 仍是唯一产品总入口，并且只列出四个模块：世界规则与玩法系统、权威世界基础设施、智能体、世界模拟与交互、玩家接入与发行。不得创建第五个模块、平行产品总入口或形式对称的空 `design.md` / `prd.index.md`。

根 PRD 拥有产品目标、玩家价值、范围、跨域组合、Non-Goals 和端到端成功标准。长期专题从所属模块导航显式可达并回链根 PRD；“活跃产品专题”是常用标题，不限定章节名称。根身份字段和 Product PRD-ID 只属于四个模块根 PRD；专题只能声明所属模块、上位 PRD、生命周期、owner、专业权威和复核信息。

产品文档按语义归属：

| 语义 | 主责权威 | 产品层做法 |
| --- | --- | --- |
| 玩家价值、产品范围、端到端结果 | 产品根 PRD / 专题 PRD | 汇总并细化玩家可理解的结果 |
| 玩家决策、流程、信息和体验状态 | 配对产品 design | 说明玩家如何经历机制，不复制实现 |
| 专业玩法、数值、结算和专业验收 | `doc/game/` 等专业权威 | 保留产品含义，链接正式规则 |
| runtime、共识、WASM、Agent 技术合同 | 对应专业域 PRD/design | 只引用支持或限制产品承诺的边界 |
| API、schema、组件、算法和详细测试步骤 | 专业 design/manual | 产品层写要证明的结果，不写执行细节 |
| 任务、排期、review 和执行状态 | Git、PR、实际 CI 和评审记录；Issue/Project 按需使用 | 功能点保留有来源的设计/实现状态摘要，详细过程只引用，不复制可变台账 |
| 当前公开能力和 claim envelope | 根 `README.md` 与发行权威 | 产品目标不得自动升级公开承诺 |

世界不变量、资源路径、结算规则和其他当前事实必须链接现行专业 authority。旧的 `world-rule.md`、附件、历史快照或旧资源表只能作为背景或迁移线索；未经现行 authority 核对，不得把其中的旧名称、路径、数值或规则措辞写成当前事实。迁移时须在语义迁移账目中记录其分类、当前 authority、未迁移部分和删除条件。

冲突必须显式记录决策、owner 和受影响条目。产品层拥有玩家价值与端到端结果；专业域拥有其规则、技术合同和验证机制。任何一方不得以“产品优先”或“代码已如此”静默覆盖另一方。

## 2. 文档身份与语义状态

根 PRD 保持稳定产品身份、Product PRD-ID、实际生命周期与已声明 authority；维护主责、复核时间和后继关系按真实情况表达。章节前缀和元数据写法是阅读约定，不单独作为失败条件。专题不得复制这些根保留字段。生命周期沿用 `proposed`、`draft`、`active`、`superseded`、`retired`；新候选不因写了 `draft` 就自动进入 active 专题清单。

同一文档须显式区分三种内容：

- **目标要求**：在明确范围内写“必须”，说明适用条件、玩家意义、权威来源和验收入口；未实现目标不能写成当前事实。
- **已验证事实**：写明入口、版本/范围、证据窗口和支持结论的权威记录；不能以旧样本扩大范围。
- **设计假设**：写明假设、反证信号、验证方法和决策 owner；未决问题不能伪装成默认值。

`active` 只表示当前文档是产品语义权威，不表示实现、试玩、发行或公开能力已通过。

## 3. 根 PRD 内容合同

根 PRD 推荐用以下内容视图组织，允许调整标题、次序或合并章节；既有身份、SC 和实际引用关系仍须保持：

```text
## 文档身份
### 活跃产品专题
## 1. 产品承诺
## 2. 范围
## 3. 权威与冲突处理
## 4. 路线图
## 5. Done：成功标准与验收
### 5.1 验收追踪
## 6. Non-Goals
```

根文档应说明目标玩家、核心问题、目标体验、模块贡献、适用阶段/入口、模块组合和能力阶段。根 SC 保留稳定 ID 与汇总语义；复杂 SC 的可独立失败义务下钻到长期专题，并在追踪路径中保留原限定词、专业边界和验收层级。验收关系应能定位成功标准、相应专业要求和验证方法；专业 owner、范围与证据按实际需要说明。原六列表格继续兼容，固定列数不作门禁。

## 4. 专题 PRD 与产品 design

专题应说明不依赖内部代码词汇的具体玩家/使用者情境，以及问题、目标、事实与假设；不限定在开头或特定标题下。专题至少覆盖：范围与 Non-Goals、正常路径、核心选择、成本/机会成本/风险、主要失败与恢复、系统承诺、上位与专业依赖、验收场景、证据范围和未决问题。

核心决策应回答：玩家知道什么和不知道什么；有哪些真实选项；每项成本、授权、锁定和机会成本是什么；权威结果如何定义；玩家怎样知道结果/阻塞；下一步是继续、等待、改道、恢复还是退出。没有取舍的流水操作不能写成策略深度。

存在非平凡流程、跨状态/入口体验、信息架构、恢复交互或机制取舍时，应由配对产品 design 或明确引用的既有设计承接；同名 `*.design.md` 是推荐组织方式。design 说明方案理由、阶段信息、成本和反馈、异常恢复、失败信号；不复制 API、组件、数据库、算法和详细执行步骤。内容很小时可在 PRD 保留简短设计说明或链接到现有 active design。

<a id="product-feature-catalog-principles"></a>
### 4.1 功能清单（Feature Catalog）的编写与维护原则

功能清单位于**有稳定产品主题的专题 PRD 内**，用于回答“这一产品体验由哪些可交付、可验证的能力组成”，是目标与叶子 REQ/AC 之间的范围索引。简单专题可直接用需求章节表达，不强制新增表格；涉及多入口、多阶段或多类使用者的主题应该建立功能清单。清单不是新产品入口，也不替代专业系统设计、玩法权威或 GitHub 任务管理。

- **定义粒度**：一条功能是玩家或外部使用者（包括调用游戏能力的 Agent Runtime）能够感知、调用或核对的独立能力及结果；按用户任务、能力边界和失败恢复分组。不要把一个 API endpoint、字段、脚本、CLI 参数、组件、部署步骤、单个测试用例或待办任务冒充独立产品功能。
- **完整性**：从目标用户的正常路径和主要反例逆向枚举，不只列 happy path。至少考虑接入/资格、观察/可用能力、行动/反馈、目标与委托、持续运行/恢复、成本/风险及端到端完成边界；不适用者明确标注，不为追求表格对称增加功能。
- **稳定身份与最低信息**：每项应有不重复、永不重用的稳定功能 ID、所属能力组、可观察的功能结果、阶段/适用范围和上位产品要求/验收引用。功能仍未被正式采纳时标为候选，并指向相邻权威或待决条件，不得用候选条目伪造已确定的 REQ/AC。
- **阶段不是状态**：区分“首期闭环”“后续扩面”“长期候选”（或该专题定义的等价阶段）；阶段仅表达产品范围和顺序，不表示已实现、正在开发、自动化通过或对外可用。设计与实现状态按 §4.2 分别表达，并链接 Task/PR 和验证证据；不在目录维护任务分派、百分比、ETA 或执行日志。执行事实查询 GitHub Issue/PR/Project，支持与证据查询专业 QA 和公开 authority。
- **追踪与判定**：已承诺的功能必须指向真实的局部 REQ/AC 或上位稳定条款，并由该要求定义适用条件、反例与验收；一个功能可对应多项要求，多个功能也可共同满足一条体验要求。功能条目与 REQ/AC 保持可追踪关系，不重复规范正文；若缺少独立可判定的验收，应先补齐要求或注明暂不具备完成判定。
- **更新触发**：目标、用户场景、阶段/Non-Goals、受支持入口、授权/成本、可用能力或失败恢复语义变化时，同批审视清单和相关 REQ/AC、配对 design、专业主责及根 SC 组合验收。新增功能时检查完整用户链路与其依赖；拆分、合并、改名、范围升降或退役时保留旧 ID 的去向/映射，不重排或复用 ID，避免历史链接与证据失效。
- **单一语义主责**：跨模块功能只在拥有玩家承诺的专题清单中定义组合结果，其他模块链接消费；资源数值、世界执行、权限机制、provider 协议、指标阈值和验证方法仍由专业 authority 定义。不能因为列了功能就声称实现已经存在、某 Runtime 受支持或发行已获批准。
- **评审检查**：读者应能从产品目标逐层找到每个首期能力及其验收，也能从每个首期 REQ/AC 反查对应功能。候选范围、未覆盖的主要失败路径及不受支持入口要如实表达。机械链接/结构检查不代表目录完整、游戏有趣或真实体验已验证。

不创建第二套 Feature 状态数据库或实施看板；规范检查复用现有 CI 入口；目录维护产品范围和可回溯的状态摘要，详细交付进展使用正式 GitHub 任务真值和专业验证记录。

### 4.2 每功能点的设计与实现状态摘要

Trace ID: O7-REQ-d0107161-28a7-4274-8273-ff6ea720737f

这是产品文档的工程治理要求，产品功能层不适用；它规范功能点的状态表达，不新增游戏能力。产品功能点应区分设计覆盖与实际实现/验证，让读者知道已知结论和缺口。可以在功能条目、要求正文或简短状态卡中表达，不要求每项补齐六个固定字段。简单专题沿用要求块，不强制新增 Feature Catalog 或文件。未触达的存量按触达式迁移，不要求一次性全仓回填。

- **身份与范围**：保留稳定功能 ID、局部 REQ/AC/SC 和适用入口/阶段。功能本身就是独立要求时，在该语义唯一声明处使用 `Trace ID`；承接已有要求或组合多个要求时，功能条目使用 `Trace refs` 并逐项链接声明，不为目录项重复发号。每个功能点都可追到其适用 Trace ID，组合功能不得用一项子要求的完成掩盖其他义务。
- **系统设计状态**仅使用 `未核实`、`未设计`、`部分覆盖`、`已覆盖`、`不适用`。`未核实`表示尚无充分核对依据；`未设计`表示已核对本功能适用范围且尚无承接设计；`部分覆盖`须列出已覆盖与剩余义务；`已覆盖`须由准确的系统设计 `path#fragment` 逐项承接本范围的要求及主要失败边界。设计文件存在、产品体验 design 存在或文档 `active` 都不能单独证明系统设计已覆盖。`不适用`仅用于经核对确实无独立技术义务的范围，必须在系统设计依据中写明具体理由与适用范围；存在技术义务但尚无承接设计时只能如实写“未设计”或“未核实”，不得借“不适用”掩盖缺失，也不冒填“已覆盖”。
- **实现状态**仅使用 `未核实`、`未实现`、`部分实现`、`已实现待验证`、`已验证`。`未核实`表示当前实现证据未核清；`未实现`须有本范围核对依据，不能由搜索零结果推出；`部分实现`须列出已交付和剩余范围；`已实现待验证`表示适用实现义务有交付依据，但验收证据不足、未执行或尚未通过；`已验证`须有支持本功能全部适用验收义务的实际证据。
- **证据最小信息**：系统设计状态链接准确承接条款；实现状态链接实际 Task/PR 与验证记录，写明核对日期、需求/实现基线（固定版本或提交）、环境、入口及验收范围。尚未形成的 Task/设计或缺失证据直接说明，未核实、未设计和未实现不要求填证据占位。只有“已验证”才必须具备足以定位实际验证范围的这些信息。PR merged、Issue closed、CI green 或文档 active 不能自动推出实现或验证状态，也不推出部署、发行或其他入口可用。
- **维护触发**：要求、验收范围、入口或技术边界实质变化时，在同次变更中重核两项状态和证据适用性；旧证据不能证明新范围时标为 `未核实`，或明确保留有证据的部分及剩余范围，不沿用旧“已覆盖/已验证”。设计承接、实现交付或验收证据改变时，同步更新受影响摘要和来源链接。
- **存放边界**：产品文档只保存当前证据化摘要；负责人分派、排期、百分比、ETA、尝试过程、失败日志和详细执行进展仍在既有 Task/PR/Project 与专业验证记录。Task 可直接是 PR，不强制新建 Issue、状态数据库、追踪文件或额外审批流程。

功能与专业系统设计按适用义务及 Trace ID 建立多对多关系：一项功能可由多个设计承接，一个设计可服务多项功能，不以 PRD/design 文件数量或同名文件配对判定覆盖。产品适用的专业专题应回链真实产品功能/要求及相应 Trace ID；工程-only 设计说明产品不适用的理由、范围并保留专业要求，不编造产品功能。具体关系合同见[系统设计关系边界](system-design-writing-standard.design.md#product-system-design-relations)。

“未设计”和“部分覆盖”是合法且应如实使用的状态，不要求为了补齐关系而伪造设计。“已覆盖”的依据必须定位到实际承接本功能的专业设计条款，并能与对应上游要求核对；产品体验 design、根架构总览或无关 fragment 不能单凭存在作为充分依据。“部分覆盖/已覆盖”的每条系统设计依据均须为真实、唯一局部锚点的专业设计 `path#fragment`，且该条款的需求—设计映射直接或经准确 AC/专业条款链反向关联当前功能/要求块或同一适用 Trace ID；可由多条有效设计关系共同承担。AC/承接条款使用已有 Trace refs 与精确链接，不要求重复声明或另领全局 ID。`剩余范围` 可以同时记录设计与实现缺口，应分别说清；设计“已覆盖”不要求该字段为“无”，因为实现可能尚未完成。检查器可以拒绝可识别的无效定位或不匹配关联，但语义覆盖是否充分仍须人工按本功能全部适用义务审查，不能把机械通过写成设计/实现/验收已完成。

只修改设计目标也可能破坏未改产品功能的关系。增量 core 检查会对未被产品变更选择器选中的现存产品 PRD，比较 merge-base 与当前快照中的正向设计依据关系；新增的 `invalid-design-evidence` 或 `design-feature-relation-missing` 仍属本次变更的严格失败。删除、重命名设计文件，或改掉局部条款、承接表，不能因引用方未修改而绕过该差分检查。历史已存在的同样失效及未改 PRD 的旧状态字段缺口不因此变成当前 PR 的全仓整改任务；全量历史仍警告，读取与执行错误仍失败。差分只覆盖上述可识别关系错误，不宣称可检测一切语义变更。


推荐在功能条目下使用[状态卡模板](product-documentation-standard.templates.md#feature-status-card)。原根 SC 和系统设计两表继续兼容，也可用单份明确映射承接同一关系，表头/编号/列数只作提示。功能摘要不取代实际验收关系；缺固定卡片不单独失败，已声明关系错误、部分状态缺剩余范围或正向完成声明缺依据按 §10.1 处理。检查器不判定证据真实性或功能完成。只读追踪工具也不自动判定这两项状态。

## 5. 玩法、Agent、经济与涌现

玩法主题必须把“期望体验 → 玩家决策 → 规则约束 → 互动结果 → 观察方式”串起来。持续玩法要区分单次成功、可持续能力、世界自主活跃和玩家可归因影响；回流/离线场景说明玩家回来后能理解什么、哪些承诺仍有效、可以重新决定什么。

间接控制必须区分玩家意图、Agent 自主决定、授权边界、世界规则约束、实际行动和权威回执。目标或 Prompt 只能表达意图，不能直接保证具体世界动作成功；解释须基于真实目标、行动、事件或回执，不能以生成叙事掩盖未发生的结果。

经济主题说明资源来源、用途、持有者、流转、取舍和损失风险。精确上限、公式、分布和结算只由专业 authority 定义。说明性示例、候选参数、正式规则值和观测值必须区分；Tick、现实时间、回放时间和表现时间不能混用。

开放沙盒描述允许的机制、互动范围、不可接受退化和验证办法，不承诺所有玩家走同一路线。确定性世界规则与不确定 Agent 行为分别定义验证口径，具体种子、模型、配置和统计由专业域与 QA 维护。

涉及叙事、视觉或声音时，文档说明体验目的、信息含义、与世界事实的关系、呈现限制和可访问性；不得借背景叙事新增物理规则，或用视觉夸张改变距离、成本、权限和状态。图、原型和截图必须标明是示意、已采纳设计还是当前实现证据，并注明适用状态；图片不能替代行为合同。

## 6. 交互、状态与可访问性

关键交互须说明对象/身份、可见信息、授权范围、主动作、提交前成本与风险、结果和下一步。跨 Viewer、pure API 等入口共享玩家语义，但不要求布局相同；每个入口须取得自身适用证据。

异步、持久化或世界效果须用表或等价结构区分正常、等待、拒绝、失效和恢复，并说明触发、玩家可见含义、允许动作、禁止误读、恢复条件和状态优先级。不得混淆草稿/提交、入口接受/实际应用、应用/永久保存、历史记录/可再次执行授权。

涉及刷新、重连、重复提交、目标切换、未保存草稿、权限变化和不可恢复错误时，失败反馈必须给出真实下一步；没有安全操作时要明确停止和边界。交互主题按实际范围说明键盘/焦点、IME、状态可辨识、文字可读性、窄屏和动效要求，不从“响应式”自动推导跨平台保证。

## 7. 规范性条目与稳定引用

Trace refs: O7-REQ-276983b3-3187-405e-8453-e2785f01c5e6；本节承接[全局要求追踪](cross-layer-requirements-traceability.design.md#global-requirement-trace)的适用写作/引用约定。

叶子要求使用“条件 + 主体 + 一个可观察行为/结果”的形式，每个 `MUST` / `MUST NOT` 能独立判定。理由单独书写。既有根 `SC-*`、专题既有验收 ID 必须保留；新增 `REQ-*` 与 `AC-*` 是文档内局部标识，不是 Product PRD-ID。

跨层追踪遵循[跨层要求与验证映射](cross-layer-requirements-traceability.design.md)。新建或实质修改的跨层要求在拥有该语义的 REQ/SC 原文旁声明一次 `Trace ID: <完整 ID>`；设计和 Task 使用相同 ID 引用，不另发号码。已有根 PRD-ID、SC、专题 REQ/AC、功能 ID 和实际验收关系保留；全局 ID 是增量关联键，不替代这些标识。根 SC 已由叶子要求承接时，按实际独立义务确定声明粒度，不为每个汇总行重复发号。工程-only 要求由专业权威声明，不凭空增加产品承诺。

完整定位引用由“文档路径 + 稳定锚点”组成。要求编号不因润色或插入重用；全局 ID 在路径移动和非语义改名时保持不变，废止不复用，拆分/合并按跨层规范保留前身与后继关系；迁移要记录旧条款到新叶子的映射。一个 AC 可以覆盖多个 REQ，但验证结果仍须区分每一项；根 SC 不得被压成检查器不接受的新根 ID。

首次出现会影响理解的缩写或内部词时，给出简短中文含义或链接术语 authority；至少区分玩家、Agent、节点，接受、应用、结算，以及规则值、示例值、观测值。正常体验和关键取舍先于异常分支与专业引用；可读性不能通过删除权利、损失或结算边界获得。

## 8. 验收、指标与证据

推荐追踪链为：`模块 SC → 专题叶子 REQ → 产品 design/专业合同 → AC 场景 → 权威证据入口`。场景按“给定/当/则”描述可观察行为，至少覆盖正常路径和本主题最高风险的失败、授权、资源、重复或恢复边界。场景没有实际接入并执行前，不得标成自动化已覆盖。

产品指标须写明指标含义、对象、入口、版本/范围、窗口、目标依据和解释方式；无真实基线时标为“基线未验证”，不得编造百分比。规则/能力正确性和玩家体验有效性分开：L4A/L4B/L5 的现有语义保持不变，低层自动化不证明人类愿意继续，Agent 试玩不代替人类体验。

文档采纳只说明设计成为约定；实现完成需要专业验证；体验成立需要适用体验证据；公开发行受根 README 与发行 authority 约束。任何一层不能替代另一层。

### 8.1 真人试玩方案与结论范围

涉及真人理解、决策、挫败或继续意愿的试玩方案，须在原测试计划或专业手册中说明：本次结论对应的目标玩家及需覆盖的经验、操作能力与无障碍需求；招募方式、样本选择和未覆盖群体；代表性任务、初始条件与允许的提示；可观察信号及记录方式，并区分行为记录、参与者自述与评审推断。验收性试玩预先明确判据，探索性试玩明确问题与假设；说明发现问题或规则、内容、交互、支持环境变化后的复测触发。样本数量与结论范围沿原专业合同确定，不将局部样本数推广为统一门槛。

## 9. 未决问题、取舍与迁移

未决问题说明准确问题、受影响 REQ/AC、决策 role、所需信息、解决触发条件、任务引用和临时排除范围。重要取舍记录考虑过的替代方案、选择理由、牺牲和重新评估条件；不要把作者或 Agent 的猜测冒充用户决定。

语义迁移按文件进行：先清点产品、专业、历史和活跃引用，回填到正确产品 authority，再修复导航和回链。源文件仍承担专业真值时保留其 authority，记录剩余语义、接收 owner 和删除条件；只有完整接收且引用修复后才可删除。任务执行状态和 review ledger 只在 Git、PR 与实际 CI 记录。

变更审查至少区分编辑澄清、行为/体验变化、数值/平衡变化、公开承诺变化和重命名/迁移。前四类分别复核行为语义、专业正式值、公开证据和适用范围；重命名或迁移必须保留旧到新的语义映射并修复活跃引用。规范正文只保留理解当前设计所需的已采纳决策摘要，不维护开发日志。

## 10. 质量责任与自动检查边界

`producer_system_designer` 负责产品范围、承诺和组合一致性；`gameplay_designer` 负责玩法决策、循环和专业规则一致性；`game_visual_interaction_designer` 负责信息、反馈、可访问性与异常交互；相关工程 role 负责实现边界；`qa_engineer` 负责验收可判定性和证据适用性；`repository_health_engineer` 负责职责、重复、导航、checker 和迁移完整性；`liveops_community` 在公开说明、玩家承诺或发行范围中负责 claim 边界；`tpm` 负责任务真值与集成，不代替专业结论。

现有检查继续用于结构事实：

```bash
./scripts/doc-governance-check.sh
python3 scripts/product-doc-governance-check.test.py
./scripts/readme-link-check.sh

```

它们可以证明四模块入口、根身份、专题可达性与显式引用关系等已枚举约束；不能自动证明有趣、决策价值、专业语义一致、玩家理解、真实留存或当前实现能力。现有 paired-design backlink 与 `topic-missing` 契约，以及本规范新增的变更范围检查契约，见下文。

已有结构规则与下述内容检查都必须由 `repository_health_engineer` 落实为脚本和回归测试；人工产品质量不由自动检查代签。

<a id="advisory-content-checks"></a>
### 10.1 事实校验与写作提示

自动检查分为可核对的事实错误和写作提示。事实错误包括：路径或锚点失效、已声明 ID 重复或引用无效、已声明的需求/设计/验证关系不成立、四产品模块身份和实际入口不一致，以及正向完成状态缺少其所声称范围的依据。它们在本次受影响范围内使检查非零失败；输入版本、Git 范围、文件读取、依赖、路径安全或检查执行错误始终失败，不能用 `--warn-only` 或 `|| true` 吞掉。

标题关键词、章节编号或次序、固定表头与列数、普遍六字段状态卡、十二段骨架和裁剪模板只产生写作提示。作者可以用清楚的正文、列表或一份需求—设计—验证映射表达同一关系，不必填空章节或重复两张表；旧表格继续兼容。没有采用模板不等于缺陷；已经声明的链接、ID 和关系仍逐项校验，改变表格形式不能隐藏真实断链。语义覆盖、可实施性和体验质量由适用评审核对，提示通过不表示这些义务已完成。

状态按实际已知信息表达。`未核实`、`未设计`、`未实现`可以直接报告未知或缺口，不要求补不存在的设计、Task、证据或日期占位；“部分覆盖/部分实现”说明已完成与剩余范围；“已覆盖”链接准确承接设计，“已实现待验证”保留交付依据及未验证范围，“已验证”保留实际证据、固定基线、适用环境/入口与验收范围。缺少整套状态卡只提示补充可读信息；已经作出的正向声明缺少必要依据、指向不存在条款或与要求不匹配，仍是事实错误。检查不能验证外部证据真伪，也不从 Git 或 CI 绿色自动推导完成状态。

`doc-governance-check.sh` 调用现有产品内容、产品结构、设计追踪与核心内容检查器。普通变更检查新增/实质修改的文档、删除和重命名两端及受影响的反向引用；未触达且未受影响的历史缺口不成为当前 PR 的整改条件。规则、选择器或解析器变化时，运行其适用的完整回归并核对全量适用文档；不能只拿几个改动文件证明规则变化兼容。纯排版识别与固定 base/head/worktree 语义沿 §10.3 保留。

`--full-corpus` 仍表示按需读取当前文档树的全量报告，与已退役的 document-corpus hash 分片不是同一机制。全量报告不能替代变更范围检查或压掉当前失败；历史提示与输入/执行错误分别报告。仓库不再维护 corpus 库存、hash、semantic/evidence 复核绑定或冻结分组机制，原文、历史证据及其专业使用边界继续保留。

模块总览和专题设计按实际职责组织。已有要求—设计—验证关系在改名、合并或迁移后仍须可定位；不因失去某个标题就视为已解除，也不为证明关系而强制恢复固定章节或表格。保留原 ID、准确目标和未覆盖范围即可按实际关系验证。

### 10.2 可作为实现输入的内容条件

产品文档只有在以下条件同时成立时，才可以作为实现工作的产品输入：

1. 产品目标、玩家/使用者情境、范围与 Non-Goals、正常路径、关键选择、代价/风险、失败与恢复、验收场景和证据边界已写在适用的产品文档中；根 PRD 保留既有身份、SC 和真实验收关系，固定六列写法只作参考。
2. 每条可独立失败的产品义务都有稳定的局部 `REQ-*`，并能通过 `AC-*` 场景追踪到可观察结果；根 PRD 可以继续只维护 `SC-*` 汇总义务，不因本条复制专题 REQ/AC。
3. 每个需求、验收场景和关键断言都能追溯到真实的产品、配对 design 或专业 authority；引用目标及其显式 fragment 必须在比较版本和工作树中可解析。
4. 目标要求、已验证事实、设计假设和公开承诺已区分；未决问题写明影响、决策 role、解决触发条件和临时排除范围。
5. 配对 design 可以引用其真实上游 PRD 的 REQ/AC 来承接产品语义，不得为了通过检查复制一份会漂移的需求；design 中若声明本地 REQ/AC，则同样必须满足本地唯一性与可达性。

这些条件是“可以作为实现输入”的最低内容合同，不等同于实现完成、专业规则通过、玩家体验成立或发行承诺。自动检查按 §10.1 核对可机械判定的事实，并独立提供写作提示；趣味性、策略深度是否足够、数值是否合理和玩家是否愿意继续，仍由对应专业 role 与适用证据判断。

跨层映射说明产品或专业要求、相关系统设计和真实验证入口。产品价值、玩家承诺、范围或验收变化时维护对应产品要求；纯工程变化使用专业合同。说明不适用范围和未覆盖风险，不增加 Task、协调 schema、兼容字段或回执准入。全局 ID 的声明和引用可借助[只读追踪工具](../../../scripts/requirement-trace.README.md)检索并人工核对；工具已提供有界索引与诊断，但不推导功能状态，也不构成 checker、CI 或自动验收门禁。

### 10.3 新建与实质变更产品文档的机械检查

作者、CI 和 PR-prep 的规范检查必须接收明确的 `base`、`head` 和工作树路径，并按该比较范围计算变更文件；不能用作者填写的标签、评论或 allowlist 任意绕过。为保持普通本地维护调用兼容，只有在没有任何显式 env 且没有 CI 事件输入时，裸运行 `doc-governance-check.sh` 才可以推导 `base=merge-base(HEAD, main)`、`head=HEAD`；这条便利路径不适用于作者提交、CI 或 PR-prep。显式 env 只提供一半，或存在 CI 事件但其 base/head 缺失、部分或格式错误时，必须失败而不能回退。适用路径是 `doc/product/**/*.prd.md` 与 `doc/product/**/*.design.md`：

- `base` 表示本次集成目标，`head` 表示待集成的源 head；提交范围必须按 `merge-base(base, head)...head`（等价于 merge-base 树到源 head 的单向差异）计算。不得使用会把集成目标独有提交带入结果的双点比较，也不得把 target-only 产品文档变化归因于源变更。worktree 模式在源 head 之上额外纳入 staged、unstaged 和 untracked 产品文档；作者、CI、PR-prep 传入的 base/head/event 缺失、部分或格式错误必须失败，不得静默退回另一个比较范围。
- 新增、复制或重命名的产品文档始终属于检查范围；修改的产品文档在去除空白行、行尾空白和 HTML 注释后仍有内容差异时属于检查范围。仅空白行、行尾空白或 HTML 注释差异按同一机械规则排除；行首缩进变化保留为实质内容变化，因为 Markdown 缩进可能改变列表、代码块或语义结构，除此之外没有“格式调整”豁免。
- 删除文件不生成新的产品内容检查项，但其活跃引用必须由既有链接/结构检查发现并修复；未变更的旧文档不因为本次规范检查被要求全面重写。
- 根 PRD 继续接受身份、SC 与已声明关系检查；章节形式和专题最低内容标记只作提示，语义充分性由作者与评审核对。已经声明的 design/PRD 配对必须能解析到真实目标，可用跨文件链接承接其 REQ/AC；不要求同名文件或重复声明 paired PRD 的需求。
- 先从文档正文移除 fenced code block，再检查 metadata、最低内容标记、真实 authority 路径/fragment、显式 REQ/AC 声明与引用、局部 ID/HTML anchor 唯一性和可达性；fenced block 中的 metadata、路径、REQ/AC 或 trace 示例既不能满足也不能触发这些检查。
- 同一文件中的 `REQ-*`/`AC-*` 引用可以使用稳定局部标识；跨文件引用必须使用带路径和 fragment 的真实 Markdown 链接（例如 design 指向 paired PRD 的 `#req-*` 或 `#ac-*`）。裸的跨文件 token、反引号路径和普通字符串不能替代链接。authority 引用同样必须以真实可解析目标为准。
- REQ/AC 需求块、验收块和追踪表中的 REQ/AC 单元格都是显式关联。每个关联必须解析到同一文件中已声明且有 anchor 的目标，或解析到带路径与 fragment 的跨文件目标；只要某个追踪行出现 `REQ-X → AC-TYPO` 等未声明/拼写错误关联，该文档就产生规范诊断，本次触达范围内阻断 CI，未触达历史只警告，即使其他 ID 在文档别处存在。不能用“文档中出现过同名 token”替代该块或该追踪行的关联。

检查范围与零规范诊断只证明适用机械规则未发现问题，不代替产品、玩法、交互、QA、LiveOps 或专业实现评审。本节产品内容检查适用于其已实现的新建或实质修改产品文档范围；全局 ID 唯一性与跨层完整性不属于本次规范检查的证明范围，未触达的 legacy content 保持在强制迁移范围之外。只读全局 ID 查询工具已有独立脚本与测试，但未因此接入 CI 或 PR-prep 准入；功能状态摘要的形式诊断只作提示；正向声明的依据和已声明关系错误在受影响范围内失败，不自动判定状态所声称的事实。

### 10.4 现行 bounded checker 契约

以上内容检查与下列已有检查共同构成本规范的机械边界：

1. 显式声明的产品 design/PRD 配对必须指向真实有效目标并保留准确 backlink；同名文件继续兼容，也允许非同名的明确配对。普通字符串、反引号中的路径或代码示例不能证明已声明关系成立。
2. active 或迁移中的专题如果由根 PRD 声明但目标文件缺失，必须输出稳定的 `topic-missing` 诊断并指出声明路径与目标路径；不得退化为 `FileNotFoundError` 或无上下文异常。

这些规则由 `repository_health_engineer` 落实为脚本和回归测试；人工产品质量不由它们代签。

## 11. 三类试点与采纳门槛

试点必须同时包含：

1. **Prompt 交互**：保留对象 authority、对话/配置区分、预设/草稿、默认/override、accepted/applied、响应式输入和过期恢复义务，并将其追踪到稳定 REQ/AC。
2. **首局与持续游玩完整主题**：治理覆盖首个工业闭环 walkthrough 的完整玩家语义，包含工厂就绪、配方比较、原料准备、物流抵达、多输入齐套、排程、生产 receipt、交付 receipt、原材料子循环、Starter Industrial Feasibility Gate、失败恢复和 idempotency 边界。
3. **复杂玩法根 SC-31**：根 SC-31 保留组合目标和全部限定词；提交前比较、生产/交付、盈余、缺口/补产、状态变化、重复执行和多入口一致性作为建议叶子主题，由玩法专业权威维护具体接收与验收。

采纳门槛是治理正文与入口一致、三类试点语义无丢失、根结构兼容现有 checker、局部需求可追踪到验收、专业边界仍可达。通过门槛不表示全部产品文档迁移、游戏实现完成或发行就绪。

## 12. 迁移审查清单

1. 是否从具体玩家情境开始，并说明玩家为什么需要它？
2. 正常路径是否包含真实决策、代价、反馈和下一步？
3. 关键失败、授权和恢复是否清楚，且没有凭空保证？
4. 每个叶子 REQ 是否有稳定锚点、上位 SC、专业 authority 和 AC，并能单独引用和判定？
5. 正式规则和参数是否只存在一个专业 authority，且旧附件没有冒充当前事实？
6. 是否区分目标、已验证事实、设计假设、当前实现和公开承诺；每个本次触达功能点是否如实表达设计/实现已知范围，部分结论有剩余范围，正向完成结论有准确证据？
7. 验收是否描述可观察行为，而不是“文档齐全”或“代码合入”？
8. 试玩、自动化或 Agent 证据是否真的支持所声称的体验结论、入口、范围与窗口？
9. ID、anchor、导航、配对 design、authority fragment 和回链是否在变更后仍有效？若是新建或实质变更，是否通过明确 base/head/worktree 的机械检查？
10. 是否删掉了重复和过程记录，而不是删掉重要语义；触达式迁移是否保留了源条款、未迁移部分和删除条件？

上述十项是作者与专业审查者的人工检查提示，不是 subjective quality 自动门禁；自动 checker 只负责本规范第 10.3 节列出的结构事实。

<a id="game-design-applicability"></a>
### 13.2 适用性、范围与最低内容

领域导航须保留全部目录项。具体主题在已有范围/Non-Goals 或要求旁说明受影响领域，允许用简短文字和准确引用，不强制每个 PR 填写全表。

- **适用**：存在该设计义务，标明当前交付或后续范围。后续范围仍是未完成范围，不写成不适用。
- **不适用**：说明哪个入口/阶段/子项不具有该义务及具体理由，并说明什么范围变化会使其重新适用。例如纯 API 不需画面资产，不能据此排除同一产品的 Viewer 美术设计。
- **待决策或未核实**：记录问题、影响、决策主责与触发条件。未找到专门入口、缺预算或尚未实现，都不足以得出不适用；尚未核实也不等于已确认缺失。

每个本次新增或实质改变的适用主题，必须能定位到以下内容：体验目的与玩家决定；正常路径和主要失败/恢复；规则、数值与具体内容；适用交互/视听及素材要求；相关技术约束；可观察的验收方法。每项写清本范围内容，或链接实际承接的条款；无独立义务时说明理由。仅有标题、空表、泛首页、占位链接或无关有效文件，不构成覆盖。

领域视图不改写 §4.2 的系统设计/实现状态及既有追踪表。设计、实际内容/资产和验证分别说明：设计说明已覆盖到哪些义务；素材是占位、部分可用还是适用于所声明范围；验证链接实际版本、入口、环境与结果。资料或资产存在、文档 active、工具能生成素材、PR 合入均不能单独证明内容齐备或体验有效。未完成项按缺设计、缺内容/资产、缺实现、缺验证分别表达，详细执行事实仍引用原 Task/证据。

<a id="player-support-service-boundaries"></a>
#### 13.2.1 玩家支持与服务生命周期

多人、社区或持续服务的适用主题，须在原产品、安全或运营条款中定位玩家反馈/举报的受理入口、处置与升级责任、结果告知及复核方式，区分规则允许的竞争损失与滥用/骚扰。说明所使用数据的用途、范围、访问与保留边界，以及事故和服务结束时玩家可采取的动作、进行中行动和已有资产/数据的处理与恢复限制。未核实或尚未提供的部分保留实际边界，渠道运营样例不能代签全游戏支持能力。

具体机制按已支持的入口与风险适用，不预设聊天、语音、公会或特定举报界面，也不能仅因没有社交界面就排除全部多人滥用风险。数据采集、恢复与补偿沿原授权执行，持久世界仍受[身份与历史连续性](../../product/world-rules-core-gameplay/chartered-conflict-soft-seasons-and-recovery.prd.md#req-wr-cc-002)及[有界恢复](../../product/world-rules-core-gameplay/chartered-conflict-soft-seasons-and-recovery.prd.md#req-wr-cc-003)约束；运营说明不授予删除历史、重写已确认因果或选择性补偿的权限。

### 13.3 按交付阶段核对证据

阶段绑定具体体验、入口和版本范围，不把整个项目所有模块强制置于同一阶段。下表规定设计内容与证据的完成含义，不新增发布权限或独立审批链；实际测试与发布沿用原 authority。

| 所声明的阶段/结果 | 本范围应满足的最低条件 | 结论边界 |
| --- | --- | --- |
| 概念与原型 | 全领域有适用性/未知项去向；核心体验、主要规则及高风险假设有可验证说明，验证主张有相应原型/推演结果 | 可用草图、纸面原型、临时数值/素材；说明验证了什么，尚未证明的生产与体验风险 |
| 可玩切片 | 选定体验的规则、内容、UI/视听、Agent/多人等适用部分形成实际链路；代表性制作流程可执行，试玩与制作风险有记录 | 只证明选定切片；占位项明确排除，不能据此声称该专业的目标品质或生产流程已验证 |

| 正式发行与持续服务 | 承诺范围的设计、实际资产/来源、语言/帮助、渠道材料、质量及运营支持达到相应验收；宣传与交付一致 | 由既有发行与专业证据作结论；开发 CI、领域表完整或局部试玩不代签发行 |

“领域已登记”只表示没有在目录层遗漏；“本范围设计完成”要求所有适用设计义务有实质内容和验收办法；“内容可用”要求相应实际交付物可定位并符合规格；“体验已验证”要求实际证据。可以交付明确范围的设计或工程前置，但须保留后续内容与体验义务，不能在验收失败后缩小名称以改写原目标。

组合验收和发行须按[实际候选的内容组合](doc-structure-standard.design.md#content-candidate-composition)关联被消费的技术、配置、内容与环境。各专业分别通过的结果不能自动证明这一组合通过；已有实际候选记录直接引用，尚未集成的内容如实保留。

<a id="content-scale-evidence"></a>
#### 13.3.1 规模化内容生产的证据

声称具备批量或扩大范围的内容生产能力时，必须在原制作/验收记录中说明选定内容类型、目标数量/变体/品质与入口，样本为何能代表其复杂度和依赖，以及未覆盖范围。区分初次工具/流程建设与后续重复制作的成本，记录适用的制作、等待依赖、集成、验证和返工依据；实测结果、预算和外推估算分别表达，并给出扩大生产的剩余风险与范围取舍。

单个精修切片或一次生成成功只能支持其实际范围。样本数量与验证强度按内容差异和生产风险决定，不固定要求每类做两件、每次变更重复切片或所有模块进入同一阶段。已有试产/生产记录足以覆盖本次范围时直接复用；没有代表性重复制作或相应风险依据时，保留能力未验证，不把估算改写为就绪。

首次采用或实质改变生产流程时，应以实际需要的代表性内容批次检验“制作→转换/导入→集成→目标环境验证”，并核对一次适用的上游规格/依赖变化如何传播到产物和证据；已有变更与运行记录可以承接。记录维护成本、重复信息及未覆盖环节，用于修订原流程。该验证针对受影响生产能力，不是普通 PR 的额外放行材料；静态入口示例和文档模板检查不代签真实生产验收。

<a id="game-design-maintenance-review"></a>
### 13.4 增量维护与评审执行

1. 新增/改变玩家承诺、玩法规则、内容、交互视听、支持入口或阶段范围时，作者用 §13.1 反查受影响领域及直接消费者；在原 authority 补齐本次所需内容，并仅更新变化的导航行。纯工程、排版或文字澄清按实际影响处理，不要求全游戏重新证明。
2. 评审按本次范围检查具体内容、跨域一致性、不适用理由和证据；明确违反本范围适用要求、关键设计决定悬空却宣称可直接实施、或用无效证据声称完成时，作为当前设计缺陷按[既有评审流程](../workflow/source-of-truth.md#evidence-based-review)处理。允许如实提交探索、缺口登记及未完成设计，但不得包装成已完成的实现输入或阶段验收。
3. 声称某范围设计完成、可玩切片完成、对外测试就绪或正式发行时，对该范围全部适用领域集中核对。尚未决定的当前必要义务、缺失的交付物或未验证的必需场景必须保留为未完成；后续范围须有原产品范围依据，不能用临时 N/A 转移。
4. 存量首轮只登记真实来源与已核对边界，未核实保留未知；触达时补受影响义务，阶段评审补该阶段所需完整范围。未触达历史缺口不阻塞无关 PR，详细补齐工作由当前 PR 或有跟踪价值的既有 Task 承接，不强制每个领域开 Issue。
5. 文件/锚点/要求关系和库存继续由 §10 的现有检查执行。本节新增的领域枚举、适用性、内容充分性、素材真实性和阶段判断由作者及适用评审核对；当前 CI 不自动验证这张领域表，也不自动判定游戏设计完整。若扩展机器检查，必须先定义范围、输入与反例测试并同步原入口，不借本节宣称未实现的自动阻断能力。

本规范通过现有范围界定、自检、专业评审和阶段验收执行，不增加每个 PR 的全领域报告、固定角色签字、额外任务身份或重复试玩。变更已有公开承诺、玩法或发布范围，仍须由原主责条款作决定；目录本身不授予扩大范围的权限。
