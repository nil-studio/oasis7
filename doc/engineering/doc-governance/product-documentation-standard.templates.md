# 产品与内容设计模板、交付索引及迁移卡

- 配套规范：[`product-documentation-standard.design.md`](product-documentation-standard.design.md)
- 内容设计与交付组织：[组织规范](doc-structure-standard.design.md#non-code-design-deliverables)；专业承接与验证：[适用边界](system-design-writing-standard.design.md#content-design-applicability)
- 模板性质：可复用写作结构，不是新的任务、数据库 schema 或自动门禁
- 使用边界：保留现有根身份、SC/验收 ID、专业 PRD-ID 和已验证事实；占位符必须替换为真实内容并标明性质

### 变更范围与引用检查约定

根 PRD 沿用固定章节与标题；专题沿用下列核心职责，允许保留可对应的同义标题；适用性裁剪按[核心结构约定](product-documentation-standard.design.md#advisory-content-checks)分别填写非空的理由、范围、风险，并以真实 Markdown 链接映射到本文件已有章节。每个缺失核心组须有独立且标签匹配该组的映射；不同组可以分别指向同一章节，但不能以任意单一链接豁免所有缺组。核心组齐备时仍须至少一条真实映射。合法形式产生非阻断人工复核 notice，不能用空占位符或仅四个关键词替代内容。以下为专业系统设计的可复制形式示例，独立列出五个核心组的映射；实际采用前必须按本次文档范围改写理由、风险、映射与章节内容。产品专题须改用其对应核心组标签：

```markdown
- 结构裁剪：理由：本次仅澄清已有设计的边界说明；范围：不改变行为和验收范围；风险：仍需复核澄清是否遗漏调用方影响；映射：[问题目标](#design-notes)、[上游约束](#design-notes)、[边界结构](#design-notes)、[验证](#design-notes)、[决策风险](#design-notes)

<a id="design-notes"></a>
## 设计说明
本节承接本次澄清涉及的边界、上游约束与验证依据；实际文档应补充准确条款和真实来源。
```

内容规范 finding 的 CI 行为遵循[增量检查边界](product-documentation-standard.design.md#advisory-content-checks)：PR 新增或实质修改的产品/系统设计文档规范问题阻断 CI；未触达历史只警告，纯排版排除遵循下述机械规则；范围/输入/执行异常及来源清单身份唯一性、文件拓扑、安全和库存完整性检查仍可失败。

新建或实质变更产品文档时，把集成目标作为 `base`、待集成源作为 `head`，按 `merge-base(base, head)...head` 计算源变更；集成目标独有的产品文档变化不计入本次源变更。`worktree` 模式在源 head 之上额外纳入 staged、unstaged 和 untracked 产品文档。作者、CI 和 PR-prep 的 `base`、`head` 或事件输入缺失、部分存在或格式错误时必须停止并报错，不得隐式切换比较范围。普通本地裸运行且没有任何 env 或 CI 事件时可保留旧的 HEAD/main 推导便利路径，但它不替代作者提交命令。

只有空白行、行尾空白和 HTML 注释差异可以排除；行首缩进变化是实质内容变化，因为它可能改变 Markdown 列表、代码块或语义结构。检查先剔除 fenced code block，再检查 metadata、authority、REQ/AC、anchor 和 trace；代码块内的示例既不能满足也不能触发诊断。REQ/AC 声明块与追踪表格单元格中的每个关联，都必须解析到本文件已声明的 anchor，或解析到带路径与 fragment 的跨文件 Markdown 链接；`REQ-X → AC-TYPO` 这类未声明关联必须报告规范诊断，本次触达范围内阻断 CI，未触达历史只警告。

## 4. 需求、验收与未决卡

### 4.1 叶子需求卡

Trace refs: O7-REQ-276983b3-3187-405e-8453-e2785f01c5e6；本节承接[全局要求追踪](cross-layer-requirements-traceability.design.md#global-requirement-trace)的适用写作/引用约定。

### 4.2 验收场景卡

```text

### 4.3 未决问题卡

```

### 4.4 语义迁移账目卡（写回 PR 与实际验证记录）

触达式迁移每次只记录本次确实触及的语义；产品目录不新增执行台账。将以下字段写回当前 PR 与实际验证记录，便于下一次触达继续接收：

```text
源条款/旧锚点：旧文件路径与稳定 ID/章节
目标条款/新锚点：产品文档路径与 REQ/AC/SC 或专业 authority fragment
语义分类：产品承诺 / 专业合同 / 历史过程 / 未迁移
已接收语义：本次实际落地的内容
尚未迁移部分：仍留在源 authority 的内容与原因
当前 authority：真实专业或产品权威及职责
接收 owner：负责后续裁定或迁移的真实 role
活跃引用：受影响的路径、fragment 或外部入口
删除条件：何时可删除旧来源或旧引用
验证结果：本次命令、证据窗口与 residual risk
```

旧 `world-rule.md` 或附件只作为背景来源时，`语义分类` 必须写明“历史过程”或“待核对”，并列出当前 authority；不得把未核对的旧名称、路径、资源或规则值填成当前事实。

<a id="feature-status-card"></a>
### 4.5 功能状态摘要卡

本卡消费[双状态规范](product-documentation-standard.design.md#feature-design-implementation-status)，放在现有功能条目或要求块旁，不创建平行台账。不改变根六列追踪、系统设计五列承接与六列验证表。组合功能逐项引用既有要求，不另造声明。

```text
功能点：既有功能 ID / 局部条款及真实链接
Trace refs: 适用要求的完整 ID（要求本身的唯一声明处才使用 Trace ID）
适用范围：入口、阶段、前置条件与验收条款
系统设计状态：未核实 / 未设计 / 部分覆盖 / 已覆盖 / 不适用
系统设计依据：准确 path#fragment；已覆盖及剩余义务，或尚未形成的缺口；确实不适用时填写：理由：具体原因；范围：适用范围
实现状态：未核实 / 未实现 / 部分实现 / 已实现待验证 / 已验证
实现与验证依据：实际 Task/PR、固定提交及测试/验收记录；缺失则明说
核对日期与基线：日期、需求版本、实现版本、环境、入口、验收范围
剩余范围：未覆盖、未交付、未验证或失效证据影响的具体义务
```

“部分覆盖/已覆盖”的系统设计依据须给出专业设计的准确 `path#fragment` 与真实反向承接，可由多个设计共同承担，并按关系规范经准确 AC/专业条款链追溯同一适用要求；产品体验配对 design 或纯模块 overview 链接本身不证明覆盖。只改设计目标导致未改产品 PRD 新增失效关系时，仍按增量差分检查；历史已存在的相同失效不因无关变更升级阻断。剩余范围分别注明设计与实现缺口，设计已覆盖不要求实现缺口为零。

字段可带列表符号或直接逐行填写。两项状态分别核对；缺少依据先用“未核实”并说明实际缺口，不虚构设计、Task 或证据链接。设计状态“不适用”须在系统设计依据中写明无独立技术义务的具体理由和适用范围，不能掩盖缺设计；实现状态不增加“不适用”。“部分”必须明确剩余范围，“已验证”必须有本范围的基线、环境与实际验收证据。要求实质变化后重核，不从文档 active、PR merged 或 Issue closed 自动推导。详细进展和执行日志只在 Task/PR。

## 5. 代表性迁移模式

### 5.1 Prompt 交互

Prompt 主题必须保留：目标 Agent 与控制资格、对话/配置区分、预设与草稿、默认/override、accepted/applied、响应式与输入、控制权丢失优先于值变化、stale 恢复、提交时重新校验和竞态至多一个真实 authority 结果。建议用 `REQ-PROMPT-*` / `AC-PROMPT-*`，并逐项回链配对 design 的状态模型和 `doc/world-simulator` authority。

### 5.2 首局与持续游玩

完整主题至少描述：玩家主目标与动作、工厂就绪、配方比较、原料准备、物流抵达、多输入齐套、排程、生产 receipt、交付 receipt、原材料子循环、Starter Industrial Feasibility Gate、失败恢复、首局/持续能力区分和 Viewer/pure API 入口证据。不要把一条完整 walkthrough 拆成静态任务清单，也不要删掉原文中对顺序、适用性、资源守恒和重复提交的限定。

### 5.3 复杂根 SC

根 SC 保持原组合目标和追踪行。叶子分解可按提交前比较、生产/交付、盈余处置、缺口/补产、状态变化、重复执行、多入口一致性组织，但每条都要回到原条款和 `gameplay` 专业 authority；产品治理 slice 不代替玩法专业迁移。

- [ ] 四模块入口、专题可达、根回链和专业 authority 仍有效。

## 7. 领域覆盖与阶段核对

使用[领域覆盖规范](product-documentation-standard.design.md#game-design-coverage)。全领域导航放在已有产品入口；主题详细说明并入原文，不另建状态台账。以下字段可用等价文字表达，普通 PR 只填写实际受影响范围。

```markdown
### 本主题的适用设计内容
- 范围：〈既有功能/要求、玩家入口、当前交付范围与后续范围〉
- 受影响领域：〈GD 编号及本次改变的义务〉
- 不适用或待决：〈具体子项、理由/问题、范围、主责与重新判断条件〉
- 设计来源：〈精确条款；体验、规则、数值、交互与技术承接〉
- 内容/资产：〈原目录或实际文件、版本、用途、占位/部分可用/适用范围〉
- 验收：〈可观察方法；已有结果链接实际版本、入口、环境与范围〉
- 剩余范围：〈分别说明缺设计、内容/资产、实现和验证〉
```

功能的系统设计/实现状态仍使用[既有状态卡](#feature-status-card)，不在这里复制另一套状态。跨层要求引用同一 Trace ID；GD 编号只表示检查领域。

全游戏导航可使用以下列序；第二列是四模块名称，具体条款与素材链接放在第三列，保持与既有四模块入口表的职责区别：

```markdown
| 领域 | 所属产品模块 | 现有权威条款或素材入口 | 已核对覆盖边界 |
| --- | --- | --- | --- |
| 〈GD 编号与名称〉 | 〈四模块名称；跨域时说明分工〉 | 〈真实来源；未找到时如实说明〉 | 〈已读范围、适用性/未知与剩余内容；不写任务排期〉 |
```

在当前 PR/Task 声明阶段完成时，记录所审版本、体验/入口/阶段范围、全部适用领域的来源、实际结果、未覆盖项与结论。已有等价验收记录直接引用；阶段未通过如实说明，不新建通用证书。音频等条件项可以明确某入口无声音，但不能用“还没做”判不适用；Viewer 静态稿可支持设计评审，实际可用性仍需对应运行验证。

组合验收按[候选内容组合](doc-structure-standard.design.md#content-candidate-composition)引用实际消费版本；声明扩大生产能力时按[规模化生产证据](product-documentation-standard.design.md#content-scale-evidence)核对代表性制作、集成与返工依据。阶段卡只引用原记录，不复制完整资源清单或制作流水。

## 8. 专业内容与表现设计模板

按[组织规则](doc-structure-standard.design.md#non-code-design-deliverables)放在原专业域，先复用已有设计条款；产品体验 design 仍使用 §3。下列模板直接覆盖五个核心内容组，保留现有 `2.1`、`11.1` 追踪标题及列结构，中间章节按内容职责组织，不要求补齐空的 5～10 章。真实技术义务按[适用边界](system-design-writing-standard.design.md#content-design-applicability)由本设计或其他专业设计承接。

```markdown
# 〈主题〉内容与表现设计

- 主责：〈真实专业角色与所属模块入口〉
- 生命周期、适用入口/阶段、审读基线：〈真实范围；active 不表示资产或运行已验收〉
- 上游：〈产品/专业 PRD 的准确条款；沿用其 Trace refs〉

## 1. 问题、目标与范围
〈玩家应理解/感受到什么；本设计拥有的内容/表现义务、非目标和未决范围。〉
〈区分已核实基线、目标、设计假设、参考图与正式内容。〉

## 2. 上游要求与约束
〈产品承诺、世界规则、相邻专业设计及实际消费者；不重复定义数值或权限。〉

### 2.1 需求承接与分配表
| 上游 requirement / product AC / professional acceptance（path#fragment） | 具体 obligation 与适用条件 | 本设计条款（path#anchor） | 外部 owner / dependency | 明确排除或未覆盖范围 |
| --- | --- | --- | --- | --- |
| 〈真实外部上游链接；适用的 Trace refs〉 | 〈内容/表现义务与入口、阶段〉 | 〈本文件准确条款链接〉 | 〈规则、制作或技术依赖及主责〉 | 〈实际剩余范围〉 |

## 3. 内容与表现设计条款
〈按稳定条款组织内容种类、空间/叙事结构、表达规则、状态反馈或视听风格。〉
〈写明与真实世界事实的关系、参考与取舍；适用语言、无障碍和不同入口的差异。〉

## 4. 制作规格与交付物
〈内容规模/变体、品质、格式/尺度/时长等规格，制作方式、输入和依赖；引用原技术合同。〉
〈原内容/资产目录、源文件和导出物的版本定位；占位与缺失项、来源/许可核实边界。〉
〈批量制作、跨团队交接或共用工具时：引用本内容类型的生产流程，明确编辑源与内容模型、转换/导入、协作边界、交接判据及变更传播。〉
〈参与组合验收时：引用既有构建/资源/发布记录，关联该候选实际消费的程序、内容版本、有效生成输入与环境；未集成范围如实保留。〉
〈适用的产能/成本假设及依据；声称可扩大生产时说明代表性批次、初建与重复制作、集成/验证/返工及等待成本，区分实测与估算。未评估项与主责、执行排期继续引用原 PR/Task。〉

## 11. 验证与验收
〈分别说明设计审读、实际素材检查和目标入口验证，保留未执行与未通过范围。〉
〈分配结构/依赖/规格检查、专业审阅与目标环境验证的方法、判据、触发时点、覆盖范围、失败处理主责及结果去向；复用原映射或手册，不另建平行报表。自动化未实现时保留替代检查及覆盖缺口。〉

### 11.1 验证映射表
| 上游 requirement / product AC / professional acceptance（path#fragment） | 本设计条款（path#anchor） | 独立 obligation 与适用条件 | 准确验证方法、test/manual source 或 ID、scenario/layer、candidate/environment 要求或选择规则 | evidence target | 未证明范围 |
| --- | --- | --- | --- | --- | --- |
| 〈同一真实上游及适用 Trace refs〉 | 〈本文件准确条款链接〉 | 〈可独立判断的内容/体验结果〉 | 〈真实测试或专业手册的链接、步骤/判据、场景和候选/环境〉 | 〈实际 PR、原证据或交付物位置；未执行则写计划去向〉 | 〈尚未覆盖的入口、品质、批量生产或运行义务〉 |

## 12. 决策、风险与未决问题
〈方案选择与理由、失效条件；尚未确定事项的影响、主责和解决触发条件。〉
```

使用前必须将占位符替换为真实内容和链接。验收手册可复用既有入口，但必须实际包含本范围的方法与判据；只有泛首页、自引设计或空手册不构成验证。上游或方法尚未形成时如实保留缺口，不为套模板伪造要求、方法或已覆盖结论。模板中的表格属于设计计划；实际结果继续在原 PR/Task 与专业证据中维护。

## 9. 内容与资产交付索引模板

按[交付索引规则](doc-structure-standard.design.md#non-code-deliverable-index)补原目录、配置说明或 manifest。可以使用已有结构化字段或下面的简卡；同规格资产组可共享信息，避免每个文件重复一套资料。

```markdown
### 〈既有内容/资产 ID 或名称〉
- 用途与主责：〈场景、实际消费者、维护者、准确设计条款〉
- 源文件：〈原路径或受控存储的固定版本定位；不可取得/不适用时的理由与编辑限制〉
- 交付版本与导出物：〈实际使用版本、文件位置或可复现输入、入口/语言范围〉
- 规格与依赖：〈原规格、工具/配置版本、字体/关联素材等实际依赖；适用时引用共用生产流程〉
- 实际消费候选：〈参与组合验收或发行时，引用该版本的实际构建/加载/发布记录及环境；尚未集成时保留缺口〉
- 可用边界：〈示意/占位/部分可用/本范围交付的事实与依据，缺失及限制〉
- 来源与权利：〈作者、取得来源、许可/授权/署名与复用限制；未核实项〉
- 验证：〈准确方法及已有结果/候选/环境；未执行时保留计划和缺口〉
```

原格式、提交策略与存储职责保持有效。稳定交付需要可取得的版本；临时本地输出、失效外链或只有生成工具都不能证明实际素材已交付。此索引不复制功能双状态、排期或完成率，也不为资产新增 Trace ID；新增规范性要求仍在其主责条款声明一次。

## 10. 现有入口的组织示例

以下示例说明如何复用真实入口并区分证明范围，不要求迁移示例文件，也不认定全领域素材或运行验收已完成。实际版本和已知限制以所引用来源为准。

| 示例 | 复用的设计与交付入口 | 依规范应区分的内容 |
| --- | --- | --- |
| Viewer 静态设计稿 | [UI/UX 交付说明](../../world-simulator/viewer/viewer-page-module-design-2026-06-18.design.md#detailed-uiux-handoff)、[覆盖目录](../../world-simulator/viewer/assets/ui-ux/full-function/coverage-catalog.json)、[W01 世界目标稿](../../world-simulator/viewer/assets/ui-ux/full-function/world-diagnostics/W01-world-targets.svg)、[W09 窄屏稿](../../world-simulator/viewer/assets/ui-ux/full-function/world-diagnostics/W09-narrow-world.svg) | 原设计拥有交互语义；SVG 是设计目标；派生目录保留来源修订和区域映射，按各项 runtime/test_status 读取未运行边界。静态稿和映射不能证明真实焦点、输入、排版或世界结果，实际验证沿原 QA 方法取证。 |
| 体素资产制作 | [制作工具设计](../../../tools/voxel_asset_pipeline/DESIGN.md#asset-contract)及其输入、导出与输出说明 | 工具拥有六视图、尺度、格式和生成/评估方法；具体资产入口另行定位选定源图、版本、成品及来源/许可。工具文档保留本地预览与评估产物不提交的规则；工具存在或生成成功不能证明正式资产齐备、运行接入或游戏内品质已验收。 |

两例都可沿“真实上游 → 设计条款 → 原内容/素材入口 → 适用方法与证据”追踪。源文件和权利资料未核清时保持未知；小说的版本与文本交付另由 [story 入口](../../../site/story/README.md)说明，可玩事件、任务或对话仍需对应游戏规则与内容明确承接。
