# 跨层要求与验证映射

- 状态：active
- 适用范围：产品文档、系统设计和项目执行记录之间的要求追踪
- 当前入口：[文档治理](README.md)
- 通用规则：[开发流程规范](../workflow/source-of-truth.md)

本文是跨层 Trace ID、声明和引用关系的唯一规范。目标是用同一个稳定 ID 找到一项要求的产品原文、系统设计承接和任务/交付记录。各层仍拥有自己的内容；ID 只关联要求，不表示批准、实现、验证或发布完成，也不是任务准入或完成协议。

### 治理要求：同一要求可跨层追溯

Trace ID: O7-REQ-276983b3-3187-405e-8453-e2785f01c5e6

本规范要求：新增或实质修改的稳定要求，应能通过同一全局 ID 找到其唯一声明、适用系统设计承接和已有任务/交付记录；尚未形成或确实不适用的层级如实说明。下列各节定义分配、引用、维护和人工核对方法。本条属于工程治理要求，产品层不适用，不宣称已经存在一个三层齐备的产品实例；本次规范 PR 引用此 ID 并记录实际文档验证。

## 1. 稳定全局 ID

Trace ID 采用 `O7-REQ-<完整 UUID v4>`，UUID 使用小写、带连字符的完整 36 字符形式，例如 `O7-REQ-7b97fe34-2be1-4b6c-9e8a-54fb03b52c16`（仅作示例，不得复制为真实声明）。使用标准 UUID v4 生成器独立生成，不截断、不从路径/日期/标题派生，也不分配递增序号。全局范围为 oasis7 全仓及其关联 GitHub 记录。并行作者无需争用一个中心计数器；完整 UUID 结合重复声明检查用于全仓唯一性。

- 一项可独立追踪的稳定要求只分配一个 Trace ID，并且只在拥有该要求语义的原文处声明一次。引用可以出现任意多次，不是重复声明。
- 产品要求在产品 PRD 的相应 REQ/SC 条款声明；纯工程、治理或专业要求在已有专业 PRD/design 的相应条款声明，不为凑三层虚构产品要求或新增空产品文档。
- 同一要求在产品、系统设计和 Task 中使用完全相同的 Trace ID。它不代替文档 PRD-ID、功能 ID、局部 REQ/AC/SC、Issue/PR 编号或 commit OID；这些继续承担原有职责。
- 简短名称、标题和局部 `REQ-001` 方便人读，但不是全局键。跨文件定位仍使用真实 Markdown `path#fragment` 链接；固定证据另外保留仓库、提交、测试版本与环境。
- 新声明前全文检索完整 ID，确认未被其他要求声明；评审时区分一处声明和多处引用。若并行变更意外重复声明不同要求，合入前给新要求重新生成 ID 并修正本次引用，不能把两项要求误合为一项。不同 ID 仍可能表达重复语义，应人工核对并记录归一关系；UUID 不能证明语义唯一。

## 2. 三层最小记录

在原有条款、承接表或任务说明中追加信息即可，不要求独立文件、数据库或统一机器 schema。

| 层 | 最少新增信息 | 保留的原有内容 |
| --- | --- | --- |
| 产品或专业要求的声明处 | `Trace ID: <完整 ID>` | 要求正文、适用范围、局部锚点与验收关系 |
| 系统设计的承接处 | `Trace refs: <一个或多个完整 ID>`；逐项链接声明处 | 本设计条款、具体承接义务、验证方法和未覆盖边界 |
| Task 的任务/交付说明 | `Trace refs: <一个或多个完整 ID>`；对应要求和适用设计链接 | 本次范围、实际 PR/commit、测试与评审证据、结果和剩余风险 |

Task 指现有任务说明，可以是 PR 描述、按需使用的 Issue，或已有项目执行记录中的一项工作，不是新的实体或 ID 制度。Project 只展示已有任务。一次 PR 涉及多个要求时列出各 ID 和本次承接范围；一个要求可由多个设计和多个 Task 分阶段交付，一个设计/Task 也可承接多个要求。

产品功能点按[产品双状态规范](product-documentation-standard.design.md#feature-design-implementation-status)保留可回溯摘要，设计和 Task 提供其依据；不把状态编码进 Trace ID，也不让查询工具替代人工判定。

产品 AC 继续通过本地 REQ/SC 与锚点表达验收关系；可以引用所覆盖要求的 Trace ID，不要求每个 AC 另领 ID。同一文档承接多项要求时，引用放在对应条款或表格行，不能只把一串 ID 放在文件头而不说明关系。

尚无系统设计或任务时，说明该层“尚未形成”及影响范围，不用虚假链接补齐。确实不适用时说明具体理由：例如只修正文案不涉及技术义务，或工程-only 没有产品承诺。一个层级的缺失不能被解释为完成。简单编辑可在 PR 写清原因，无需为了获得 ID 新建长期要求。

## 3. 生命周期和迁移

要求措辞澄清、文档改名、路径移动或锚点修正不改变 Trace ID；同步修复活跃链接，保留旧到新定位或 Git/PR 历史。ID 不编码位置、owner、阶段或状态。

要求被废止或被替代后不得复用 ID。原声明保留必要的退役说明和后继定位；确需移走正文时保留可查的旧 ID 与去向，不静默删除唯一声明。内容修订仍是同一义务时沿用 ID，并以 Git/PR 和固定版本区分历史语义；实质产生另一项义务时分配新 ID。

拆分为多个独立要求时给各后继新 ID，在旧条款记下“拆分为”及后继 ID/链接，在新条款反向链接旧 ID。合并产生新的组合要求时给新要求新 ID，并双向记录所有前身和后继；仅重复条款去重时保留一个 canonical ID，其他旧 ID 留作明确的替代关系，不能重指为无关要求。关系使用普通文字与链接，不另建迁移 ledger。

新建或实质修改的跨层要求按本规范补齐本次涉及的声明和引用；仅格式调整、未触达的存量文档和历史证据不要求全仓回填。继承已有要求时先找声明，不为同一语义重复发号。补录 ID 不改写历史证据，也不能声称旧任务原本就带有该 ID。

## 4. 当前检索与有界聚合

当前可用完整 Trace ID 做仓库全文检索，例如 `git grep -n -F 'O7-REQ-<完整 UUID>' -- doc`，找到声明与设计引用；再在 GitHub 的 PR/Issue 中搜索同一完整 ID，搜索范围包含已关闭 Issue 和已合入 PR，或沿已有任务链接读取本次交付和实际证据。

仓库搜索不包含 GitHub PR/Issue 正文，GitHub 搜索也可能受索引时延影响，必要时直接打开已知记录。此方法只能追踪已按本规范记录的关系，零结果不证明该层不存在。权限受限、查询失败或分页未完成时，明确标注检索覆盖不完整，不能断言“未关联”。

人工核对时从声明出发检查设计承接、Task 范围和真实结果；也可从 Task 的 ID 反查原始要求。共享 ID 表示关联，不证明关系完整或验收通过；以正文、真实链接和对应版本的证据判断。

[只读要求追踪 CLI](../../../scripts/requirement-trace.README.md)已提供完整 ID 查询、文档/Task 反查、可重建索引和重复声明等有界诊断（规范由 PR #4680 采纳，工具由 PR #4682 交付）。默认只读本地文档；显式启用 GitHub 时读取其支持范围内的 Issue/PR 正文，并保留分页、权限、缓存新鲜度与已知链接失败边界。它不自动修复来源、不推导功能完成状态，也不是 CI/PR-prep 准入门禁。查询成功或零诊断不能证明全仓唯一性、三层完整或要求验收通过；具体能力与限制以工具 README 为准。

## 5. 内容与流程边界

产品层解释价值、规则和玩家承诺；系统设计说明技术边界、失败行为、兼容与验证；Task 记录本次工作，源码、测试、Git、PR 和真实 CI/评审提供实现与交付事实。新增、删除、重命名和合同变化时检查直接消费者，按真实影响更新引用。

本规范不恢复 loop、ledger、epoch、typed upstream schema、身份传递回执或审批链，不强制创建 Issue，也不改变 workflow 的权限、合入或完成规则。专业运行合同本身需要的版本、receipt 与安全约束继续有效，不与文档追踪键混用。
