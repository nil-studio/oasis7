# parallel-development

规则由[任务拆分与并行开发](../../../doc/engineering/workflow/source-of-truth.md#parallel-task-development)拥有；本方法提供执行步骤和可复用模板，沿用既有授权、验证、评审和交付规则。

Trace refs: O7-REQ-f1388c2b-6f64-4ebd-886e-0b741bfe176c；承接任务拆分、并行派工及整体集成。

## 1. 核对现状，判断拆分

读父目标及验收、适用设计、当前源码、Issue 的原生父子关系与评论、实际会话和在途 PR。确认已有成果、有效认领、暂停与剩余义务；复用现任负责人的分工，不让子任务重复领取整个 Issue。

列出需要交付的结果。未拆分的简单修改可直接开发和交付 PR；强耦合原子改动写明具体依赖后串行。多个结果可以独立推进时继续拆分；已有大任务的阶段 PR 增加，但依赖等待未减少、重复卡在同一边界或缺少整体进展时，重新梳理剩余结果，保留未完成的整体验收。

## 2. 按交付结果建立依赖

给每项父目标验收安排实现任务和最终集成入口，父项保留适用的跨任务组合与长时间观察验收。每个子任务包含实现该结果所需的消费者、测试和文档；保证同一行为正确、安全所需的正常、拒绝与恢复检查随本项交付。合并同一职责内过细的机械步骤。

按[可验证的代码任务](../../../doc/engineering/workflow/source-of-truth.md#verifiable-code-task)把阶段或模块展开为可从实际消费入口验证的行为或接口合同，明确消费入口、本次范围与非目标、实际输入、验证和结束条件。优先安排[关键交付路径](../../../doc/engineering/workflow/source-of-truth.md#delivery-feasibility)；必要前置缺失、合同或约束前提变化、出现独立新结果时，更新受影响拆分后再继续相应实现。

逐项检查内部能否继续拆分。例如“会话生命周期”中的持久恢复、heartbeat 延期、执行到限拒绝和独立停止，能在固定接口上分别正确交付和验证时应各自成项。必须共改才能正确的部分，写清拆开会破坏哪条接口、状态或事务合同；共享模块或状态机本身不足以说明必须合在一起。

逐项写出需要什么输入、由谁产生、采用哪个版本。检查依赖是否成环，找出阻塞整体结果的关键路径。公共类型、协议、错误/恢复语义或资源规则未定时，先安排合同或最小集成骨架；固定前置提交后再派发消费者。无关调研、夹具准备和其他就绪任务可以先行。

按[小而完整的 PR](../../../doc/engineering/workflow/source-of-truth.md#small-complete-pr)同时规划交付边界：可独立构建、验证并保持已有行为的公共前置优先形成小 PR，尽早评审和按授权合入；按独立功能增量持续交付，必须同时修改才能正确的部分保留在同一个 PR 并说明原因。不等整个父目标完成后一次提交，不按 worker 数、文件数或固定行数机械拆分。

前置未合入时，可基于接口稳定且已做适用验证的固定提交堆叠开发；写明依赖 PR/提交、未合入状态与目标分支。前置合入后核对真实合入版本，更新必要的依赖和分支关系，通知依赖方复用；后继验收覆盖实际组合，不重复复制前置实现。

## 3. 维护一份任务安排

计划草拟可先留在当前会话；拆出独立开发任务后，按[原生子 Issue 规则](../../../doc/engineering/workflow/source-of-truth.md#code-task-sub-issues)先核对已有任务，正式派发前创建或复用父 Issue 及每项 `type:code` Issue，建立并回读 [GitHub 原生 parent/sub-issue 关系](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues)。使用当前可用的 GitHub 网页或 API，不假定客户端已有专用命令；工具或权限缺失时如实报告尚未完成的关联，正文链接、清单或 PR 不能代替原生关系。

在父 Issue 放置以下简表作为索引，已有安排补齐子 Issue 关联。完整派工内容和私有工作区路径留在执行会话，公共记录只保留必要且可公开的关联；不另外创建固定任务文件或台账。

```text
父目标及未完成验收：
当前可验证完整结果 / 关键阻断与下一步：
整体集成负责人 / 最终验收入口：
共享文件及其写入负责人：
本轮执行容量与限制：
```

| 子 Issue 及对应验收 | 前置及输入版本 | 写入范围 / 接口边界 | 负责人 / 实际会话 / 工作区 | 验收准备与验证 | 当前结果 / PR 边界及顺序 |
| --- | --- | --- | --- | --- | --- |
| 原生子 Issue 与可观察结果 | 前置编号、提交或合同版本 | 允许修改的路径、非目标及共同接口 | 实际执行关联；待派发则注明 | 输入/夹具、消费入口、独立预期及权威观察点；准备缺口与责任 | 阻塞原因、交付 PR/依赖、补丁/提交、待集成或已集成位置 |

每个子 Issue 承载本项范围、领取与状态、会话、PR 和验收记录；父项保留总体范围、依赖和组合验收。父子关系表达范围归属，不代替前置依赖。任务内部机械步骤和测试用例仍可用清单，已拆出的独立开发结果均使用原生子 Issue；每项未完义务只归属一处。

## 4. 划清写入与运行资源

逐项比较写入范围，把共享协议、`Cargo.toml`、`Cargo.lock`、`lib.rs`/`mod.rs`、生成产物和全局索引交给明确的单一写入者；其他执行者提交所需接口变化。发现新重叠或契约变化时，先调整受影响范围的依赖和所有权。

核对真实工作目录、分支和起始提交；新会话本身不提供隔离。先检查 `git worktree list --porcelain`，需要新增隔离目录时沿用 `scripts/new-task-worktree.sh`，具体入口遵循[日常开发](../../../doc/engineering/workflow/source-of-truth.md#2-日常开发)。

共享工作区只分派文件及生成/运行输出不重叠的任务；Git 暂存、提交、切分支、变基、清理和全局生成由负责人串行处理。会改变其他任务基础的操作，先确认受影响执行者停写并保全成果，完成后通知恢复。worker 不做全仓格式化或提交他人文件。独立 worktree 同样核对端口、测试数据、外部环境和共享构建资源。

## 5. 派发已就绪任务

派发前按[验收条件](../../../doc/engineering/workflow/source-of-truth.md#code-task-acceptance-readiness)核对本项输入/夹具、消费入口、权威结果观察点与运行资源；已有路径做最小启动或基线核验。需在本项补建的入口、夹具或环境准备写入范围；外部前置缺失时明确产出、责任人和解除条件，先推进可执行准备及独立就绪范围，不要求待实现行为预先通过。

核对本轮实际执行范围的前置已满足、输出可检查、共同接口可用、写入及运行资源能隔离。派工指定已回读原生父子关系的具体子 Issue，核对其自身实施条件、领取及暂停事实；父项 ready/active 不代替子项自身状态和领取。在现有授权、工具、构建/CI 和审阅容量内并行分派，优先收尾和解除关键路径阻塞，保留整合与验收容量；所有子任务及后代共享总上限，仍可能写入的会话计入并发。

每次派工给出足以独立执行的上下文，使用下面的简要模板；具体接口值、限制和验收不得仅靠执行者猜测或读取整段聊天。

```text
父 Issue / 具体原生子 Issue / 本项对应验收：
本次可观察结果、范围与非目标 / 适用规范位置：
输入版本 / 已满足前置 / 本项准备范围或待补前置责任 / 共同接口及约定：
实际消费入口 / 权威结果观察点 / 集成去向：
实际工作区、分支、起始提交：
允许写入范围 / 共享文件负责人 / 禁止触碰范围：
执行条件与资源/预算限制 / 需要回报的阻塞：
验证命令或操作 / 输入及夹具准备 / 独立预期与判定依据（含适用的成功、拒绝或恢复）：
需调整或重新拆分的条件：
返回：实际补丁或提交范围、受测版本、已执行命令/操作与真实结果、未覆盖及原因、未完成项、接口偏差。
```

等待依赖且已停写的任务可让出执行名额；待验证、评审或集成的成果仍需安排收尾容量。缺少并行能力时按依赖顺序执行并如实记录；局部阻塞只暂停其依赖链。反复等待、冲突或返工时减少并发、合并过细任务或重划边界。普通派发沿用已有许可，新增外部影响按规范处理。

## 6. 回收、整合与验收

收到结果后读实际 diff，核对约定范围、消费者、共享文件及未完成项。缺失产物或结果不明时先查证，不将会话结束视为完成。

验收失败或迟迟没有可验证结果时，先定位实现缺陷、夹具或判定依据问题、依赖/环境缺口或过大的任务边界，再按原因修复、补准备或重拆受影响范围；未执行与未覆盖项如实保留。

按依赖顺序及时整合，记录提交或补丁进入了哪个分支及版本。已具备独立交付条件的小 PR 及时送审并在授权内推进合入，不为等待其他分支而积压；把可用接口和实际版本交给依赖方。对应子 Issue 区分“已返回、待集成”和“已集成”，父项索引同步必要摘要；修复优先续接原执行者，边界变化先更新分工。

让执行者承担局部验证，集成者对已形成且可验证的组合及时执行跨边界验证，并保留父目标最终验收及现有必要检查。mock、各分支绿色及旧父分支结果只证明各自范围；验证记录写明实际受测组合，不让每个 worker 重复全仓测试。

按[验证与评审](../../../doc/engineering/workflow/source-of-truth.md#3-验证与评审)检查必要结果，按[交付与状态](../../../doc/engineering/workflow/source-of-truth.md#5-交付状态与清理)核实实际合入。PR 使用 `Refs` 关联对应子 Issue，阶段交付同时保留父项关联；本项验收及交付义务完成后才按授权关闭子项，原目标及适用部署、真实环境验收全部满足后再关闭父项。

## 7. 中断后恢复

从父项索引及对应子 Issue 核对实际会话、分支/补丁、已整合结果和剩余依赖，继续尚未完成的范围。结果未知先查询；确认旧执行停止并保全成果后再换人，避免两个执行者继续写同一范围。

父项暂停传递到受影响子项；局部阻塞保留其他就绪工作。按原验收核对剩余义务，缩减目标需有相应用户决定，不能通过拆任务遗漏困难部分。清理沿用通用规范。
