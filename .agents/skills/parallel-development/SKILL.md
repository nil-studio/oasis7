# parallel-development

规则由[任务拆分与并行开发](../../../doc/engineering/workflow/source-of-truth.md#parallel-task-development)拥有；本方法提供执行步骤和可复用模板，沿用既有授权、验证、评审和交付规则。

Trace refs: O7-REQ-f1388c2b-6f64-4ebd-886e-0b741bfe176c；承接任务拆分、并行派工及整体集成。

## 1. 核对现状，判断拆分

读父目标及验收、适用设计、当前源码、Issue 的原生父子关系与评论、实际会话和在途 PR。确认已有成果、有效认领、暂停与剩余义务；复用现任负责人的分工，不让子任务重复领取整个 Issue。

按[项目拆解](../../../doc/engineering/workflow/source-of-truth.md#project-decomposition)将完整目标组织为实际消费者可用的模块增量，先识别关键依赖、整体验收及其负责人，再细化当前和近期批次。后续范围保留目标、前置和解除动作；决定当前方案可行性的未知先验证。模块分组写在父项现有正文，不增加必建的中间 Issue。简单修改直接交付，已有任务与成果继续复用。

## 2. 按交付结果建立依赖

给全部父目标验收安排归属和最终集成入口；当前批次明确实现任务，后续范围保留在父项或已有子项，适用的组合与长时间观察义务保持可见。每个子任务包含实现该结果所需的消费者、测试和文档，必要的成功、拒绝与恢复随本项完成。reader、预算、owner、来源和回执若共同服务同一业务行为，作为该任务内部步骤连续实现。

按[可验证的代码任务](../../../doc/engineering/workflow/source-of-truth.md#verifiable-code-task)把阶段或模块展开为可从实际消费入口验证的行为或接口合同，明确消费入口、本次范围与非目标、实际输入、验证和结束条件。优先安排[关键交付路径](../../../doc/engineering/workflow/source-of-truth.md#delivery-feasibility)；必要前置缺失、合同或约束前提变化、出现独立新结果时，更新受影响拆分后再继续相应实现。

用以下问题走读拟派发子项，复用已有说明，不把通用规则重复写入每项正文：

| 核对问题 | 判断方法与例子 |
| --- | --- |
| 本次范围能否确定？ | 从正文或固定来源确定实际 profile、消费者及条件。例如“统一服务资格”要能定位本次覆盖的 profile 和读写入口；未定部分明确补齐动作及影响。 |
| 拆分能更快形成什么可用结果？ | 核对解除下游阻塞、利用独立容量、隔离风险或提前交付的收益。CLI 的完整启动与独立报告若能分别消费并减少等待，可以分项；若主要增加接口协调、重复构建和验收，则在同一任务内连续完成。独立可测试不自动要求继续细拆。 |
| 验收是否保留合同条件？ | 对照主责条款核对关键预期。例如区分可释放的并发占用和不返还的窗口消耗，释放事件以原合同为准；改变约定先修订主责设计。 |

必须共改才能正确的部分保留原子性；其余范围按实际拆分收益决定，共享模块本身不证明必须合并。本行为必需的真实适配器、权限或恢复验证随本项完成，不以模块完整为由纳入无关新能力。

为当前批次写出所需输入、生产者和版本，核对循环依赖与关键路径。共享接口按[接口前置交付](../../../doc/engineering/workflow/source-of-truth.md#interface-prerequisite-delivery)由单一写入者收口；大量并行实现前，整合负责人先将真实消费方接入同一组合做定向检查。固定已就绪前置后派发消费者，接口变化先更新组合并同步消费方；其他就绪工作可以继续。

按[小而完整的 PR](../../../doc/engineering/workflow/source-of-truth.md#small-complete-pr)同时规划交付边界：可独立构建、验证并保持已有行为的公共前置优先形成小 PR，尽早评审和按授权合入；按独立功能增量持续交付，必须同时修改才能正确的部分保留在同一个 PR 并说明原因。不等整个父目标完成后一次提交，不按会话数、文件数或固定行数机械拆分。

前置未合入时，可基于接口稳定且已做适用验证的固定提交堆叠开发；写明依赖 PR/提交、未合入状态与目标分支。前置合入后核对真实合入版本，更新必要的依赖和分支关系，通知依赖方复用；后继验收覆盖实际组合，不重复复制前置实现。

## 3. 维护一份任务安排

计划草拟可先留在当前会话；拆出独立开发任务后，按[原生子 Issue 规则](../../../doc/engineering/workflow/source-of-truth.md#code-task-sub-issues)先核对已有任务，正式派发前创建或复用父 Issue 及每项 `type:code` Issue，建立并回读 [GitHub 原生 parent/sub-issue 关系](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/adding-sub-issues)。使用当前可用的 GitHub 网页或 API，不假定客户端已有专用命令；工具或权限缺失时如实报告尚未完成的关联，正文链接、清单或 PR 不能代替原生关系。

在父 Issue 放置以下简表作为索引，已有安排补齐子 Issue 关联。完整派工内容和私有工作区路径留在执行会话，公共记录只保留必要且可公开的关联；不另外创建固定任务文件或台账。

```text
父目标及未完成验收：
已验证模块增量 / 待集成或待验收成果 / 关键阻断：
当前批次 / 后续范围及前置 / 下一步解除动作：
整体集成负责人 / 最终验收入口：
共享文件及其写入负责人：
本轮执行容量与限制：
```

| 子 Issue 及对应结果 / 验收 | 前置及当前阻塞 | 负责人 / 实际会话 | 当前成果 / PR / 下一步 |
| --- | --- | --- | --- |
| 原生子 Issue 与可观察结果 | 输入来源及未满足条件；详细版本在子项维护 | 实际执行关联；待派发则注明 | 已交付范围、交付顺序与承接或核实动作 |

每个子 Issue 承载本项范围、输入版本、写入和接口边界、领取与状态、会话、PR 和验收记录；父项保留总体范围、依赖和组合验收，索引引用子项，不复制整份任务内容。父子关系表达范围归属，不代替前置依赖。任务内部机械步骤和测试用例仍可用清单，已拆出的独立开发结果均使用原生子 Issue；每项未完义务只归属一处。

本次仅要求拆分时，按[仅拆分时的交付](../../../doc/engineering/workflow/source-of-truth.md#task-decomposition-delivery)在此交付安排，区分建议优先项、已核验的派发条件和实际领取／执行。尚未承接的责任或未核实的条件写明下一步；后续实施沿用已有授权，相关范围就绪后再进入派发步骤。

## 4. 划清写入与运行资源

逐项比较写入范围，把共享协议、`Cargo.toml`、`Cargo.lock`、`lib.rs`/`mod.rs`、生成产物和全局索引交给明确的单一写入者；其他执行者提交所需接口变化。发现新重叠或契约变化时，先调整受影响范围的依赖和所有权。

核对真实工作目录、分支和起始提交；新会话本身不提供隔离。先检查 `git worktree list --porcelain`，需要新增隔离目录时沿用 `scripts/new-task-worktree.sh`，具体入口遵循[日常开发](../../../doc/engineering/workflow/source-of-truth.md#2-日常开发)。

共享工作区只分派文件及生成/运行输出不重叠的任务；Git 暂存、提交、切分支、变基、清理和全局生成由负责人串行处理。会改变其他任务基础的操作，先确认受影响执行者停写并保全成果，完成后通知恢复。各开发会话不做全仓格式化或提交他人文件。独立 worktree 同样核对端口、测试数据、外部环境和共享构建资源。

## 5. 在独立会话中推进就绪任务

按[独立开发会话](../../../doc/engineering/workflow/source-of-truth.md#independent-development-sessions)由用户直接打开会话，或在选择 TPM 协调时使用已获准的会话管理能力。每个会话领取具体代码任务，负责实现、自测、PR/CI 和同范围修复；优先续接已有会话，不默认转派给 subagent。用户或已有负责人承担整合，不为本方法增加必经协调会话。

启动前按[验收条件](../../../doc/engineering/workflow/source-of-truth.md#code-task-acceptance-readiness)核对本项输入/夹具、消费入口、权威结果观察点与运行资源；已有路径做最小启动或基线核验。需在本项补建的入口、夹具或环境准备写入范围；外部前置缺失时明确产出、责任人和解除条件，先推进可执行准备及独立就绪范围，不要求待实现行为预先通过。

核对本轮实际执行范围的前置已满足、输出可检查、共同接口可用、写入及运行资源能隔离。派工指定已回读原生父子关系的具体子 Issue，核对其自身实施条件、领取及暂停事实；父项 ready/active 不代替子项自身状态和领取。采用代码队列时按[领取与状态维护](../../../doc/engineering/workflow/source-of-truth.md#coding-agent-task-claim)更新本项标签。在现有授权、工具、构建/CI 和审阅容量内并行推进，优先收尾和解除关键路径阻塞，保留整合与验收容量；所有相关开发和评审会话共享总上限，仍可能写入的会话计入并发。

交接直接引用当前子 Issue、设计版本和 PR，补充本轮目标、工作区、允许写入范围、共享文件负责人及执行预算即可；已有范围、依赖、验收入口、夹具与独立预期不重复抄写。接手会话须读取这些来源，缺少内容时先补齐，不能靠猜测或整段聊天恢复合同。私有环境信息留在获准会话，公开记录只保存必要关联。

返回实际补丁或提交范围、受测版本、已执行命令/操作与结果、未覆盖及原因、未完成项和接口偏差。CI、评审与验收反馈优先由原会话在同一任务内修复，不为每轮反馈新开会话。

等待依赖且已停写的任务可让出执行名额；待验证、评审或集成的成果仍需安排收尾容量。整合负责人持续推进当前完整消费路径；同一接口返工或待集成成果积压时，先整合、验证并减少并发，再扩大派工。缺少并行能力时按依赖顺序推进，局部阻塞只暂停其依赖链。普通派发沿用已有许可，新增外部影响按规范处理。

## 6. 回收、整合与验收

收到结果后读实际 diff，核对约定范围、消费者、共享文件及未完成项。缺失产物或结果不明时先查证，不将会话结束视为完成。

验收失败或迟迟没有可验证结果时，先定位实现缺陷、夹具或判定依据问题、依赖/环境缺口，以及任务过大或拆分过细的成本，再修复、补准备或调整受影响范围；未执行与未覆盖项如实保留。

按依赖顺序及时整合，记录提交或补丁进入了哪个分支及版本。已具备独立交付条件的小 PR 及时送审并在授权内推进合入，不为等待其他分支而积压；把可用接口和实际版本交给依赖方。对应子 Issue 区分“已返回、待集成”和“已集成”，父项索引同步必要摘要；修复优先续接原执行者，边界变化先更新分工。

让执行者承担局部验证，集成者对已形成且可验证的组合及时执行跨边界验证，并保留父目标最终验收及现有必要检查。mock、各分支绿色及旧父分支结果只证明各自范围；验证记录写明实际受测组合，不让每个开发会话重复全仓测试。

按[验证与评审](../../../doc/engineering/workflow/source-of-truth.md#3-验证与评审)检查必要结果，按[交付与状态](../../../doc/engineering/workflow/source-of-truth.md#5-交付状态与清理)核实实际合入。各开发会话随 PR 完成适用单元测试和无外部条件的集成测试；子项所需 PR 均已合入且自身仍承担复杂测试时，才沿用该子 Issue 按[测试分工与转换规则](../../../doc/engineering/workflow/source-of-truth.md#issue-lifecycle)交接，由测试执行者按[测试接收规则](../../../doc/engineering/workflow/source-of-truth.md#test-task-acceptance)确认认领。父项的整体复杂测试不复制给每个子项；无此剩余的子项按自身义务结项。PR 使用 `Refs` 关联对应子 Issue，阶段交付同时保留父项关联；本项验收及交付义务完成后才按授权关闭子项，原目标及适用部署、真实环境验收全部满足后再关闭父项。

## 7. 中断后恢复

从父项索引及对应子 Issue 核对实际会话、分支/补丁、已整合结果和剩余依赖，继续尚未完成的范围。结果未知先查询；确认旧执行停止并保全成果后再换人，避免两个执行者继续写同一范围。

父项暂停传递到受影响子项；局部阻塞保留其他就绪工作。按原验收核对剩余义务，缩减目标需有相应用户决定，不能通过拆任务遗漏困难部分。清理沿用通用规范。
