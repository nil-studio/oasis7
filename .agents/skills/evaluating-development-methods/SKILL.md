# evaluating-development-methods

通用规则见[开发流程规范](../../../doc/engineering/workflow/source-of-truth.md)。本方法帮助比较开发方法的效果，不新增任务准入、固定角色、每 PR 试验、付费 CI 或合入条件。

## 确定试验问题

先用实际失败、返工或待验证的 Skill 改动提出一个可证伪的问题，例如“先核对消费者能否减少漏测”。区分产品缺陷、环境故障与开发方法问题；普通 bug 仍使用 [systematic-debugging](../systematic-debugging/SKILL.md)。

说明适用任务、预期收益、可能退化及最小试验。保留现行方法作为 H0；H0 是合法结论，不为证明有进展而强造修改。一次只改变一个可解释的方法因素，避免同时更换模型、预算、工具和角色数。

先核对已有来源、环境、工具、授权及预算。缺少可比较基线、必要隔离或执行许可时，说明哪些试验未执行及具体缺口，完成可执行的静态分析；不因此阻塞其他已授权开发，也不把缺前置记成方法效果差。

可以优化上下文加载、工具指导、任务拆分和调试顺序。用户授权、凭据边界、必要验证和独立评审要求仍按现行规范执行，候选方法不能自改判据、自授权限或批准自己。

## 准备同条件输入

使用可核对的固定输入，区分真实历史任务与合成合同 fixture。回放历史任务时提供当时源码、原任务描述和可见输入，记录来源及范围；历史 PR 修复和后续讨论留在评估侧。脱敏、删去凭据，不把当前 main 或内置 fixture 假称历史快照。

先选 pilot 样本探索方法，冻结候选后再用未参与调优的 holdout 样本检查。内置 holdout 是公开合同 fixture，不具有保密性；执行者已见答案或用其调优后，不再将该样本计作有效留出证明。

使用 [trial-format.md](references/trial-format.md) 中的入口导出任务包、固定样本与重复次数的 `plan.json` 和结果模板。执行前在当前 PR 或已有 Task 固定计划与 H0/候选方法版本。`prepare` 不导出 `expected` 或 `provenance`，但也不创建源码沙箱或阻断 Git 历史和网页答案。

真实对照要在同等隔离环境中仅提供任务包、所需固定源码和方法；阻断答案文件、修复提交及无关网络来源。隔离不足或执行者已见答案时如实注明，不把该样本计作有效留出证明。

固定模型与推理配置、工具版本、源码/输入摘要、环境、初始 memory、cache 状态和资源上限。使用隔离会话的同一 memory 快照或相同关闭设置，不清空用户日常记忆；缓存采用同等冷/热条件，不混淆预热收益与方法收益。

## 执行有限对照

H0 与候选使用相同任务、重复次数、最大时间、工具/模型预算和重试策略。先定次数再执行，不只保留各自最好一次；交错或平衡执行顺序，记录影响比较的外部变化。

全部基线、候选、子任务及重试共享事先明确的总预算。已有许可覆盖时直接继续，超出许可或缺少必要条件时停止依赖动作；使用本 Skill 本身不授予调用外部 Codex、GPT Work、付费服务或持续调度的权限。

记录每次真实输出、命令/操作、耗时、token/费用及人工介入。保留失败和未完成尝试，未知成本保持未知；不能把重复运行到成功包装为一次成功。

候选期间出现权限越界、重复副作用、判据泄漏或预算耗尽时停止新增执行，保存已发生事实。方法调整后作为新候选重新比较，旧失败不改写。

## 判定结果

用预先固定的期望行为、回归检查和原始事实判断结果。执行者的“完成”标签、报告长度、角色数量和自评分不代替验收。需要专业判断时按实际风险安排独立审阅。

先确认结果来自真实执行且输入可比，再运行 `compare`。脚本只核对合同 fixture 的指定答案字段并汇总配对结果，报告 `evaluation_scope=contract_fixture`、`evidence_verified=false`、`adoption=not_decided`；不启动模型、网络、Git 或编译，也不验证所填证据真实存在。

同时看正确性、边界违反、误报/漏项、返工或人工介入、墙钟时间和成本。双方均未通过不算平局，超预算或缺少耗时/token 记录的配对为不确定；成本覆盖不全时不声称总成本更低。CI 等待与 Agent 工作时间分别解释，不把并行任务耗时相加当用户等待。

候选出现关键正确性或安全退化时保留 H0。覆盖或可比性不足、差异不清、成本未知时说明限制；只有收益得到支持且代价可接受，才提出采用候选的具体范围。

比较程序成功退出只表示输入和比较流程可处理，不代表候选优于 H0、经验已采用或 PR 可合入。有限样本结论只覆盖所测任务，不宣传整体提升比例。

## 沉淀与交付

在当前 PR 或已有 Task 说明问题、H0/候选差异、固定版本、样本范围、实际结果、成本和限制；复用现有记录，不新增统一试验账本、证书或每 PR 表单。

把可复用结论写成“适用信号 → 有效做法 → 证据 → 不适用/失效条件”，按职责更新原 Skill、manual 或主责设计。一次失败不升级为所有任务的全局规则；没有收益可以删除候选或保留 H0。没有充分可迁移证据时记 `NO_ENTRY`，表示本轮不形成长期经验，不是脚本状态码或开发阻塞。

原始逐次运行、失败和比较输出按[信息归属](../../../doc/engineering/workflow/source-of-truth.md#information-record-placement)留在适用原始证据和 PR/Task，清理按通用规范执行；长期方法只保留稳定约定与必要来源。

涉及方法修改时按现行评审和授权边界提交，不能由工具自动修改规则、发 PR、合入或放宽权限。说明本轮完成的是静态检查、真实方法试验还是经验采用，不互相代称。

## Supporting Files

- `references/trial-format.md`：执行导出、填写结果或解释比较报告时读取，含格式与证明边界。
- `scripts/trial.py`：离线列出样本、导出不含答案的任务包、比较已取得的结果。

## Verification

修改本 Skill 后运行 `./scripts/lint-skills.sh`、适用文档检查和 `git diff --check`。验证脚本/样本时使用确定性 fixture，明确其只证明工具行为；真实方法效果需要另外取得受控执行证据。

## Known Failure Modes

- 当前规则和历史源码混用、初始记忆不同或一侧缓存已预热，会产生不可归因的差异。
- 给执行者评估答案、修复 diff 或完整研究对话，会把答案复述误当方法改进。
- 用同一批样本调优与验收、丢弃失败或追加无限重试，会夸大收益。
- 用删除必要检查、增加未授权预算或新增强制材料换取高分，不属于可采用的方法改进。
