# 汇报方式

项目汇报与交接文字遵循[语言与写作要求](../../doc/engineering/workflow/source-of-truth.md#language-and-writing)。

默认使用中文，先结论后依据；代码标识保留原名，PR 标题和 commit message 按仓库要求使用英文。汇报服务于用户判断，不重复粘贴日志或生成另一套任务账本。

## 工作过程中

开始复杂任务时用一两句说明目标和范围。出现有价值的阶段结果、具体阻塞或需要决定的事项时及时更新；没有实际进展不机械播报。不要用“正在处理”代替已经获得的结论。

缺信息时说明具体未知、它影响什么，以及本轮已完成什么。不能把未接入显示成零、把请求已发出显示成成功、把 CI 运行中显示成通过。

## 项目简报

项目总览复用 [指挥看板 Skill](../../skills/oasis7-command-center/SKILL.md) 的口径，可按以下顺序压缩成几段：

```text
当前判断：项目目前处于什么状态，最值得关注的是什么。
目标与变化：本次范围内的目标、真实交付和仍未满足的部分。
需要决定：具体问题、影响与推荐；没有则省略。
下一步：最小的有效行动及必要依赖。
来源与限制：查询时间/时区、仓库版本、PR/CI/文档及未覆盖范围。
```

按用户指定时间窗读取最近工作，区分事件发生时间与查询时间。搜索、分页或权限只覆盖部分数据时明确范围，不把“未查到”说成“不存在”。

事实、推断、建议分别表达。完成率只有在分母和判据明确时使用；不按 PR 数量或描述长度计算项目进度。待审、已合入、已部署和已验收直接用自然语言说明，不建立新的强制状态机。

## 例行任务汇报

空巡检保持安静；subagent 不可用时如实显示“等待执行者，20 分钟后重试”，同一未变化的等待或调度异常不每轮重复通知，不宣称已停止。增量 Issue 整理只汇报实质转换、关闭/归并、新阻塞、恢复或待用户决定；无变化和相同等待不通知用户，内部保留真实覆盖与待办。每日 CI 回顾完成后汇报一次；即使没有明显卡点也给出简短结论、统计日期和覆盖范围，数据不足必须明说。补跑报告同时标注计划日期与实际执行时间，不把积压日报当成今天的新发现。

主 Agent 汇总 subagent 的真实结果，保留子任务与报告引用。报告区分“CI 明确阻塞合入”“疑似 CI 瓶颈”“非 CI 等待”，不将耗时最长的 job 自动定为合入卡点。CI 报告附新建/复用的 Issue 链接及原因，整理报告附关闭、去重、合并与保留项的链接和依据；摘要数量只计回读确认的操作，不把草稿或未确认写入算已完成。

通知去重与执行成功分别记录；报告已经生成且必要 Issue 操作已核实、只有通知失败时只补发，不重跑分析或重复写 Issue。分析完成但 Issue 写入失败/结果未知时分别报告，并保留待协调操作，不宣称完整成功。

### Sites 内容 review

无变化且健康时保持安静；有实质内容更新、新失败、过期/缺证据影响扩大、恢复或需用户决定时，按同一 Site、来源范围、输入版本和异常类别去重汇报。未变化的失败、等待执行者或同一摘要请求不每 20 分钟重复提醒；必要的时效变化应说明实际影响。成功的常规更新可合并简报，阻塞和重要变化及时说明。

报告分开说明计划触发、实际检查、来源发布、摘要请求和摘要回读结果；“任务启用”“任务运行中”“摘要已更新”不是同一事实。给出 Site/来源链接、计划槽或合并范围、实际检查时间与时区、输入/输出版本和覆盖，明确保留的 last-good、stale/失败/未知部分及下一步。通知失败仅补通知，摘要提交响应未知先核对原回执，不能再次归纳或换标识重写。

## 评审与方案

评审问题应包含位置、实际风险、证据和修复建议。按阻断程度排序，不把风格偏好升级为安全问题；未发现问题不等于证明没有问题。

方案写最终建议、改动范围、验证方式和关键取舍，不夹带已淘汰的讨论编号。已确认的用户决策直接体现在方案里；需要新增决定时，说明原因。

## PR 交付

```text
结果：PR 链接，以及当前是待评审、已合入还是其他实际状态。
改动：主要文件与它们解决的问题。
验证：实际执行的检查、对应版本和结果。
限制：未运行的验证、未接入的能力及仍需用户判断的事项。
```

CI 尚未结束时说明“运行中”，不预告将通过。没有真实独立评审不宣称“已通过专家 review”。文件保存、配置读取、行为试用分别报告；没有真实 dot 任务试用时，只能说文件和静态检查已完成。

## 原 Issue 的实质反馈

用户采用[可选的 dot 开发交接](../../doc/engineering/workflow/source-of-truth.md#coding-agent-issue-handoff)时，部署、测试、修复反馈和整体结果继续写回同一原 Issue；沿用现有实质反馈，不为指挥中心另建摘要 Issue、台账或独立汇报评论。反馈有新结果、限制或下一步变化时，用自然语言包含以下要点，便于用户和指挥中心回溯同一交付：

```text
交付结果：解决了什么，实际完成到哪里，对原目标有什么影响。
验证与版本：实际受测 source/build、环境或入口、执行的验证及结果；未测试的明确说明。
仍未满足：尚未达到的原验收条件、失败或未知范围；没有新增缺口时直说。
下一步：已有任务范围内的具体行动、必要依赖或待决定事项。
依据：原 Issue、关联 PR、准确提交、检查/运行记录或正式条款的可访问链接。
```

区分代码合入、部署、测试与整体验收；原版本失败和未覆盖范围不被后来的成功改写。没有实质变化不重复评论，写入结果未知时先回读协调。公开反馈不携带凭据、私有路径或用户对话；汇报和后续模型归纳都不授予新权限，也不自动关闭仍有义务的 Issue。普通 PR 未采用此交接方式时仍可直接承载交付说明，不强制创建 Issue 或经过 TPM。

规则版本可在首次采用、发生变化或排查问题时报告，不必每条回答重复完整清单。引用优先给可访问的仓库路径或 PR/提交链接，不暴露私有机器路径、凭据或敏感日志。
