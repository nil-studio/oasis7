# 前一日 CI 耗时与合入卡点回顾

此任务由时间表指定的 subagent 执行。目标是回答：前一自然日的 CI 是否形成明显的合入等待，主要卡在哪里，以及最小可行的改进是什么。发现有证据的合入卡点时创建或关联 Issue，不自动修复代码或操作 CI；通用规则以[开发流程规范](../../../doc/engineering/workflow/source-of-truth.md)为准。

## 输入与日期

使用主 Agent 提供的计划日期 D、时区、实例键和规则提交。默认时区为 `Asia/Shanghai`，主统计窗口是 `[D-1 00:00, D 00:00)`；补跑也使用这个窗口，不取“现在之前 24 小时”。记录查询时刻和当前 GitHub 状态，窗口之后发生的完成/合入只作后续状态，不混入昨日指标。

范围为 `eng-cc/oasis7` 的 PR 相关 CI，优先 required checks 及其必要上游；非必需 workflow 单列为资源开销或疑似共享资源竞争，不直接称为合入阻塞。读取当前规则用于导航，但没有历史证据时，不将当前分支保护设置冒充昨日配置。

## 读取实际来源

读取窗口内创建的相关 workflow runs，同时从当日曾等待 CI 的 PR/checks 补查更早启动、跨窗执行和窗内重跑的记录。不能只筛“昨天创建的 runs”就漏掉跨天卡住的 PR。比较基线为主窗口之前的 7 个完整自然日，使用相同 workflow、runner 类别和测试范围；无法完整覆盖时在报告说明。

按 `run_id + run_attempt` 区分尝试，按 job ID 去重，并保留 PR、source HEAD、测试对象/merge SHA、workflow、job 和最终检查的关联。读取全部必要分页和 attempts，不能只分析默认首页/最新 attempt；GitHub 查询返回达到上限时拆分时间窗口继续读取，仍无法完整取得则标记覆盖不足。无需下载无关产物或在当前环境编译项目。

读取当时 workflow 的依赖关系、检查/作业时间戳、必要的脱敏日志和 PR 时间线，确定 required-gate 的必要上游。权限不足、日志过期、取消和仍在运行都单独记载；没有看到的结果不能计作成功或零耗时。API 字段和分页入口以 GitHub 的 [workflow runs](https://docs.github.com/en/rest/actions/workflow-runs) 与 [workflow jobs](https://docs.github.com/en/rest/actions/workflow-jobs) 文档为准。

## 耗时口径

| 指标 | 计算与边界 |
| --- | --- |
| 任务墙钟耗时 | 单 job 的 `completed_at - started_at`；按 workflow/runner/实际测试范围分组 |
| 首次启动延迟 | run 创建到第一个 job 启动的间隔；不能直接等同 runner 排队，可能含并发控制或审批 |
| runner 排队 | 仅在可核实 job 已具备执行条件的时间时计算；只有创建时间时标为等待上界/代理值，不能把依赖等待算排队 |
| 候选 CI 就绪耗时 | 固定 source HEAD 的相关触发到所需检查全部满足的墙钟区间；核对上游和测试对象，不把并行 jobs 耗时相加 |
| 关键路径 | 根据实际依赖和时间戳找拖住最终检查的链；缺依赖信息只报告观测等待，不能伪称完整 DAG 分析 |
| 重跑与无效开销 | 同一 source HEAD 的 attempts、重复 runs、失败后重试和被更新取消分别统计；不能把正常新提交验证当重复开销 |
| 实际合入阻塞 | 结合 PR 就绪/评审、冲突、检查与合入时间线判断；“CI 很慢”和“CI 是实际合入卡点”分别下结论 |

以窗口内首次触发的候选/作业作为耗时 cohort，完成耗时只使用完整可观测样本，跨日未完成单列并给出截至窗口结束的等待下界。更早开始且在窗口内等待的实例单列 carry-in；资源消耗按与窗口交集计算，不能把全长重复记入两天。失败/取消不当成功，窗口后的新信息只更新后续状态。

报告样本数、P50、最大值；样本数不少于 20 时报告 P95（排序后取 `ceil(0.95*n)` 项），不足时说明小样本而非给出稳定趋势。失败率、重跑率写清分子与分母。runner-minutes 作为资源成本单列，不等同用户等待时长。

## 明显卡点的初版筛选

以下数字是本任务的初始筛查阈值，不是仓库 SLA、已有性能事实或新的 CI 门禁；命中只进入调查，不能直接确认因果。

| 候选信号 | 进一步核对 |
| --- | --- |
| 某个 PR 的必要 CI 墙钟等待超过 45 分钟 | 是否真正阻止该候选合入，还是同时仍在开发、待评审或有冲突 |
| 可核实的 runner 排队超过 10 分钟 | 是否资源不足；只有代理值时标疑似，不确定性不可省略 |
| 同一 source HEAD 为满足必要检查发生至少 3 次尝试 | 区分基础设施故障、flaky、重复触发、合理手动诊断及被替代构建 |
| 可比组 P95 比前 7 日基线上升至少 50%，且增加至少 10 分钟 | 两边样本是否足够，是否测试范围/runner/缓存条件已变；不满足可比性就不下退化结论 |
| 多个 PR 被同一个必要检查、串行链或错误门禁卡住 | 是否有同源证据；没有足够时间数据也可作为高影响疑似问题报告 |

按影响的 PR 数、可证明的等待及是否仍在发生排列前 3 个问题。明确区分“已确认 CI 合入卡点”“疑似瓶颈”“非 CI 等待”；最后一次 CI 变绿到 merge 的间隔不是 CI 阻塞时间。不能建议通过删除必要检查、放宽汇总成功条件或伪造状态来提速。

## 卡点必须有 Issue 承接

沿用 [WORKFLOW 的问题闭环](../WORKFLOW.md#confirmed-problem-followthrough)；以下保留本任务的卡点判据、证据字段与执行者分工，不扩大写入或持续执行授权。

每个有证据的合入卡点都由本 subagent 在 `eng-cc/oasis7` 创建或关联 Issue，不能仅在报告中建议建单。已观测到阻塞但根因尚不明确时可以建立“待定位”的卡点 Issue，区分事实和假设；单独命中筛查阈值、数据不足或没有实际问题不制造 Issue。报告重点展示前 3 项，其余已确认卡点保留 Issue 索引，不因摘要上限丢失跟踪。

写入按 [HEARTBEAT.md](../HEARTBEAT.md) 的 Issue 协调与结果核实执行。先检索并读取相关 open/closed Issue，按必要检查、症状/根因和影响范围查重，不只按标题或当日日期判断。同一卡点跨日期复用同一未解决 Issue，只补充新的 PR/run 证据；只有关闭记录且存在新复发证据时新建关联复发项，不擅自重新打开历史 Issue。主 Agent 不代写。

新 Issue 包含问题与影响、统计窗口、PR/source HEAD、run/job 链接、可核实等待、已知原因与待定位部分、最小改进建议及验证/关闭判据。复用项以增量评论补充，保留原始需求；没有新证据不每天重复评论。Issue 不包含凭据、私人机器地址或原始敏感日志。

将不含日期的同源问题标识、Issue ID 和已执行操作保留在私有运行状态，供补跑和重试查重。创建/评论结果未知先查询已存在结果，不重复提交；无法核实则保留待协调状态。缺写权限时返回可用分析及待建 Issue 内容，明确建单未完成，不代称完整成功。

## 返回给主 Agent

```text
结论：有明显卡点 / 有疑似瓶颈 / 在已覆盖范围内未发现明显卡点 / 数据不足。
统计：计划日期、主窗口与时区、查询时刻、覆盖的 PR/runs/attempts、缺失范围。
耗时：必要 CI 和关键作业的样本数、P50/P95/最大值、可核实排队、失败和重跑情况。
卡点：最多 3 项；每项含 PR/HEAD、run/job 链接、可证明的等待、根因证据及置信边界。
建议：按收益排序的最小改动与验证办法；可合并处理的问题优先一个 PR，不直接实施。
Issue：每个卡点的新建/复用链接、已补充证据，以及未完成或结果未知的写入。
后续：窗口结束仍未完成的项截至查询时刻是否缓解，单列且不回填昨日耗时。
结果：完整完成 / 部分完成 / 失败，附可读取的报告与来源。
```

数据充分但无异常也返回简报；数据缺失不输出“无卡点”。遵守派工预算和 60 分钟执行上限，不能无限拉取历史；达到上限即说明真实覆盖和未完成部分。除本任务的卡点 Issue 创建/增量评论外，不写仓库代码、PR 或日志服务，不重跑/取消 CI、不合入或部署。向主 Agent 返回已脱敏报告及真实 Issue 结果。
