# Rust CodeQL 告警分诊与修复跟进

本任务由 dot 的时间表 subagent 执行，dot 对持续分诊、修复承接和结果核实负责。范围为 `nil-studio/oasis7` 主干 `oasis7/rust-repo/default` 的原生告警与其未完成修复；先处理新增、重开或风险变化，同时逐步清理存量。目标是推进真实问题解决，不能只汇总告警数量或停在“建议建单”。

时间、每日实例键及补跑规则只由 [SCHEDULE](../SCHEDULE.md) 定义，协调与跨轮状态沿用 [HEARTBEAT](../HEARTBEAT.md#codeql-告警与修复的接续)。授权见 [AUTONOMY](../AUTONOMY.md#时间表任务的授权范围)，代码实施沿用 [Issue 开发交接](../../../doc/engineering/workflow/source-of-truth.md#coding-agent-issue-handoff)：dot 准备和跟进，Coding Agent 负责 Rust 实现、验证与 PR/CI。此任务不新增运行器或自动消费开发队列。

遵守[当前 Rust 日频目标](../../../doc/testing/ci/codeql-integration.design.md#rust-daily-baseline-goal)：保持主干每日 default baseline，不为每个 PR 开启 Rust 扫描，不改变其他语言现有 observe。分诊复用正常扫描结果，不修改查询、覆盖、频率或预算。

## 读取范围与扫描身份

接收计划日期、实际检查时间、规则提交、实例键、上次完整读取水位、未完成分页、告警处置依据、修复 Issue/PR 和实际执行者。先协调原有未知写入、在途修复与暂停，再读取新增来源；补跑保留计划日期，告警状态标注实际读取时刻，不伪造历史日快照。

读取可信 main 的最近生产扫描及原生 Security 数据，按[运营手册](../../../doc/testing/ci/codeql-operations.md)核对 `run_id/run_attempt`、job、source SHA/ref、category、官方 SARIF ID 与唯一 analysis 的关联、错误和警告。既有采证结果只在身份和读取范围仍适用时复用。扫描成功、平台接收和告警结论分别记录；运行中、失败、缺权限、上传未确认或采证不完整不能解释成零告警。

完整读取本项所需分页，并对已跟踪告警补查当前状态及适用的 instances。记录读取范围、分页结束依据、截断/预算和未覆盖部分；只处理了首页或部分返回时不能推进完整覆盖水位。collector 的 `most_recent_instance` 匹配结果是读取时的现存开放告警，不等于该次扫描新增，也不能证明历史完整或零告警。已跟踪告警不再出现在某次列表中时，必须核对实际状态及原因，不能自行记为已修复。

扫描尚未完成或当前数据不可读时，继续可独立推进的既有修复和证据核对，保留当日覆盖未知。正常日频结果没有覆盖修复提交时标注“已合入，待扫描确认”，不为刷新结果额外触发重型扫描。已确认的调度、上传或采证故障沿现有问题承接方法查重跟进，不能把扫描基础设施故障当成业务漏洞。

## 分诊与优先级

以 `仓库 + alert ID` 关联历史，记录规则、位置、受影响版本、状态、来源与修复项。先看生产可达、高影响和边界变化，再处理其余未核实存量；同一根因可成组分析，但每条告警保留适用依据。规则名称、测试标签、测试目录或固定值本身都不能直接证明可利用或误报。

结合当前源码与告警所指版本核对输入来源、调用路径、日志接收者、凭据用途和权限边界。历史探针或旧版本结论仅在前提仍成立时复用；源码、配置、调用者或信任边界变化后重新判断。

| 结论 | 后续动作 |
| --- | --- |
| 确认存在需修复问题 | 写清实际风险、影响与验证判据，查重并进入下述修复交接 |
| 已修复，等待扫描或原生状态确认 | 核对实际合入提交、相关源码与扫描覆盖；保留原修复项，不重复开工 |
| 有具体证据的误报或接受的风险 | 记录逐条依据和适用边界；仅在已有授权覆盖时按运营手册处理精确 ID 并回读，否则保留建议和开放状态 |
| 证据不足 | 保留待核实事项、缺少的来源和下一步，不把未知转为误报或安全结论 |

不以批量 dismissal、整类忽略、删查询、扩大排除路径或改变 SARIF/category 消除噪声。查询或模型确有独立缺陷时，先记录证据与受影响范围，按既有设计和实现流程另行承接；本日任务不直接修改扫描配置。告警下降区分代码修复、检测模型修正、扫描范围变化和人工处置。

## 修复交接与持续推进

1. 检索并读取相关 open/closed Issue、在途 PR、实际认领及暂停，按根因和验收范围查重。同源问题优先继续原 Issue/PR；只有新证据或状态变化才更新，不能每个日期、analysis 或 alert 重建同一修复。
2. 对根因未知但风险已确认的问题，建立或补充 `type:defect`，记录事实与待定位内容。设计充分或属于明确实现 bug 时，按五类合同直接建立代码任务或在原 ID 转为唯一 `type:code`，写清目标、范围、证据、最小修复方向、回归验证、依赖和交付终点；有设计缺口先补受影响设计。
3. 交接条件、执行授权和依赖具备后，可在本专项授权内为尚未领取的具体代码任务设置 `implementation:ready`，通过已有获准的交接入口核实真实执行者接收。已有 active/paused 或同范围执行者时保留原关联，不重复 ready、派工或解除暂停。没有执行者或入口时记录“待承接”及具体缺口，跨日保留；标签不是开工证明，不能把无人领取说成修复已开始。
4. Coding Agent 连续负责小而完整的修复、必要回归、适用评审与 PR/CI，按该代码任务已有授权和正常保护条件推进交付。dot 核对实际 diff、source HEAD、CI、冲突及阻断问题；需要返修时把直接相关的新证据补到原 Issue，必要时在原修复 PR 反馈，继续原执行者，不另开同目标开发任务。
5. 合入后核对修复提交及随后覆盖该提交的日频扫描、相关原生告警状态和适用验证。PR 已合入、扫描自然关闭和人工 dismissal 分别记载；旧扫描仍 open 不能推翻新修复，也不能以 PR 合入代签扫描确认或全部验收。只有原 Issue 的全部义务完成且具备关闭授权时才结项。

本任务的持续责任不在 ready 或 owner 接收时结束。有可执行待办时，在现有预算内推进分诊、交接、返修反馈或结果确认；保留尚未完成的修复，下一轮继续。外部开发服务、费用或环境超出已有授权时，只暂停相关执行并说明具体解除条件，不把日常修复委托扩展为任意 Codex/GPT Work 调用。

## 本轮结果与接续

每轮保存实际扫描身份、告警读取覆盖、已核实结论、完成的写入、修复 Issue/PR、实际执行者、待扫描确认项及剩余待办。沿用运行器私有状态和原 Issue/PR，不新增公共台账，也不每轮提交仓库文件。

本轮状态按 HEARTBEAT 记录：取得完整的本轮读取范围、推进可执行的优先事项并保存待办，不要求在一次日任务内修完全部存量。分页、关键数据或所需写入未完成时保留 partial/blocked，报告不能代替写入核验；每日实例完成不等于关联漏洞全部修复。

中文报告说明新增/重开/复核的告警范围、确认风险、实际修复进展、PR/CI 链接、扫描确认与未完事项。无实质变化时不重复通知；新风险、修复交付、阻塞变化或待决定事项按既有报告规则汇报。通知失败只补通知，写入未知先回读，重试只推进剩余动作。

## 行为核对

以下场景用于静态评审及接入后的实际核对，不代表任务已运行：

| 场景 | 期望结果 |
| --- | --- |
| 初次读取大量存量，其中部分带测试标签 | 按风险分批核对，保留未分诊项，不整类关闭或把全部结果称为漏洞 |
| 当日扫描未完成、上传失败或分页截断 | 明确覆盖未知，接续已有修复，不报零告警或额外重跑扫描 |
| 跨日或补跑再次看到同一告警/根因 | 复用原证据、Issue/PR 与执行者，只推进新变化和未完动作 |
| 确认问题可以交接，但无可用开发执行者 | 保留可领取的具体任务与待承接事实，不报告已开始修复 |
| 修复 PR 合入，最近扫描仍为旧 SHA | 记录已合入待扫描确认，不重复修复、不宣称原生告警关闭 |
| 相同 alert 曾判误报，但调用或权限边界变化 | 重新分诊；平台处置仅在有效授权内执行并回读 |
| Issue/PR 评论或告警处置响应丢失 | 在同仓库写入互斥内查询真实结果，避免重复写入 |
