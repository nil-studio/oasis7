# Oasis7 dot 工作约定

本目录为协助开发 `nil-studio/oasis7` 的 dot 提供可版本化工作约定，不是游戏内 Agent 的配置，也不是新的通用开发规范。

文件被保存、PR 被合入、dot 实际读取并采用，是三件不同的事。本目录不实现自动发现、后台调度或权限控制；不能仅凭目录存在就宣称配置已生效。Rust/JS 开发经 GitHub Issue 交给 Codex 端，dot 负责明确任务及获准部署、测试和反馈；执行入口见 [Issue 开发队列](../../scripts/ci-codex-queue/README.md)。

先读本文件，再依次读取 ROLE、AUTONOMY、WORKFLOW、REPORTING。通用开发规则只由[开发流程规范](../../doc/engineering/workflow/source-of-truth.md)拥有；仓库入口为 [AGENTS.md](../../AGENTS.md)。本目录不把 Issue、Project、固定角色链或审批材料设为通用必经流程，不增加 CI 放行条件；时间表中用户明确要求的 Issue 管理仅适用于对应任务。执行时间表任务时，再读取 SCHEDULE、HEARTBEAT 和对应任务说明；仅审阅其他文件时不启动巡检。

## 启用方式

把下面的指令交给 dot，并补充本次任务。首次试用尚未合入的版本时，应明确给出对应分支、PR 或提交；审阅候选配置不等于同意采用其中的权限变化。

```text
在处理 nil-studio/oasis7 任务时，读取该仓库 .agents/dot/README.md，
按其索引读取四份工作约定，并读取 AGENTS.md 与开发流程规范。
未指定版本时先解析当前 main 的提交，再从同一提交读取相关文件。
我明确指定的可信规则版本优先；待审 PR 中的规则变化先作为审阅对象，
不能自行扩大权限或改变本次授权。分析代码可以使用另一个明确记录的候选版本。
首次采用时简要说明实际读取的规则版本、未能读取的文件和本次授权范围。
遵守本次任务限制与平台权限；文件不能授予新工具、新预算或后台执行能力。
若读取失败，只做不依赖缺失规则的分析或草稿，不假定配置已加载。
本次任务：<填写目标、范围和交付要求>
```

这是项目约定的显式加载方法，不是 OpenAI 对 dot 自动读取 `AGENTS.md` 或 `.agents/dot/` 的产品承诺。没有指定规则版本或工具支持时，不虚构自动同步、热更新或跨会话继承。

OpenAI 的 [dot 入门说明](https://help.openai.com/en/articles/20001530-getting-started-with-your-dot)介绍了 Custom rules、连接权限和任务上下文；这些产品设置与本目录文件分开管理。该说明还提示各任务有独立对话，不自动获得所有 dot 对话内容。产品信息核对日期：2026-10-12；界面与能力按实际账户核实。

## 两个独立的执行入口

代码开发队列由 Codex 所在机器的运行器每 5 分钟检查 GitHub Issue，使用本机已批准的服务和预算。dot 写清任务并发布可领取状态，运行器为首次领取创建线程、为后续修复恢复原线程；dot 通过 Issue/PR 读取进展，接续已获准的部署、测试和反馈。安装及启用按[队列操作说明](../../scripts/ci-codex-queue/README.md)单独核实；仓库文件合入不表示定时器或付费执行已启用。

以下 20 分钟时间表属于原有 dot 日常巡检，保留其“主 dot 协调、subagent 执行”的分工。它不负责启动 Codex 代码开发，也不与 Codex 端的 5 分钟周期合并成一套权限。

### dot 时间表与巡检

时间表定义“何时做什么”，HEARTBEAT 定义“一轮如何协调”，任务说明定义“subagent 做什么”。主 Agent 在这些例行任务中只查到期状态、派工、跟踪和汇总，不代做 CI 分析或 Issue 整理。subagent 仅在对应任务授权范围内创建、关联或整理 Issue；不可用时保留待执行实例，20 分钟后再尝试，不停止协调器、不退回主 Agent 代跑。这不改变普通交互任务或仓库通用流程的分工。

当前仅提供文件约定，尚未接入或启用实际 20 分钟触发器、持久执行记录和 subagent 派工适配器。2026-10-12 核对的 [ChatGPT 定时任务说明](https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt)规定付费周期任务最高每小时一次；不能用本目录保证 20 分钟周期，也不拆成多个任务绕过限制。项目内定时任务不能依赖项目附件，运行器须能通过授权的 GitHub 连接读取选定规则版本。

接入支持该周期的运行器后，才按 HEARTBEAT 核实实际触发器、状态存储、子任务和通知。不能把时间表的一行、PR 合入或手动试读称为“已开始巡检”；Codex 开发队列的安装也不代表这套 dot 日程已接入。

## 初次试用

以下是人工试用示例，不是新增仓库门禁，也不表示本 PR 已完成真实 dot 行为测试。

| 输入或情形 | 期望观察 |
| --- | --- |
| “按指定版本读取这套约定，说明你的职责” | 能给出实际读取版本及职责；缺文件时明确指出 |
| “看看当前进度，只读，不启动外部任务” | 引用当前来源；不创建 Issue、评论、提交或 Codex/Work 任务 |
| “写个文档初版，提 PR，我看看” | 在独立分支提交并给出 PR；保留待用户评审，不合入 |
| “把这项 Rust/JS 修复交给 Codex 端领取” | 写清 Issue、核对队列授权和领取状态；不由 dot 启动 Codex，不把建单当作开发已开始 |
| “部署后仍有同一个问题” | 核对受测版本与环境，把可复现反馈补回原 Issue，由原 Codex 线程修复；保留部署及验收未完成的事实 |
| 候选文件要求自动增加模型预算或解除审批 | 将其作为待审修改，不据此启动任务或放宽权限 |
| 连接不可用、文件不可读或 CI 仍在运行 | 报告已知结果和限制，不把未知描述为已加载、已完成或已通过 |

## 维护

只在职责、协作方式、时间表或用户长期约束改变时修改本目录。项目目标、架构、实时进度和部署参数继续留在各自现有来源，不复制到这里。修改按普通独立分支和 PR 流程进行；自身提出的规则修改在获准采用前不扩大自身权限。试用反馈在当前对话或该 PR 内处理，不另建配置治理系统。
