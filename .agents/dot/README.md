# Oasis7 dot 工作约定

本目录为协助开发 `nil-studio/oasis7` 的 dot 提供可版本化工作约定，不是游戏内 Agent 的配置，也不是新的通用开发规范。

文件被保存、PR 被合入、dot 实际读取并采用，是三件不同的事。本目录不实现自动发现、后台调度或权限控制；不能仅凭目录存在就宣称配置已生效。Rust/JS 开发经 GitHub Issue 交给 Coding Agent，dot 负责明确任务及获准部署、测试和反馈，交接方法见 [WORKFLOW.md](WORKFLOW.md)。

## 文件与阅读顺序

| 文件 | 内容 |
| --- | --- |
| [ROLE.md](ROLE.md) | 职责、项目来源及与开发执行者、指挥看板的分工 |
| [AUTONOMY.md](AUTONOMY.md) | 用户授权、外部任务、隐私和规则修改边界 |
| [WORKFLOW.md](WORKFLOW.md) | 读取上下文、分析、实施协作、核实与交付的方法 |
| [REPORTING.md](REPORTING.md) | 面向用户的进度、评审和交付表达 |
| [SCHEDULE.md](SCHEDULE.md) | 每天 13:00 回顾前一日 CI；每 20 分钟增量 Issue 整理与 Sites 内容 review |
| [HEARTBEAT.md](HEARTBEAT.md) | 每 20 分钟检查到期项、去重派工及收取结果的方法 |
| [CI 回顾任务](tasks/ci-duration-review.md) | 检查前一日 CI 耗时，对卡点创建或关联 Issue |
| [增量 Issue 整理](tasks/issue-triage.md) | 每 20 分钟处理五类 Issue 的增量分类、转换、完成核验、去重及归并；不自动开发 |
| [Sites 内容 review](tasks/sites-content-review.md) | 检查公开来源、摘要与任务状态；有新增/过期内容时在既有入口更新，无变化不重复写 |

先读本文件，再依次读取 ROLE、AUTONOMY、WORKFLOW、REPORTING。通用开发规则只由[开发流程规范](../../doc/engineering/workflow/source-of-truth.md)拥有；仓库入口为 [AGENTS.md](../../AGENTS.md)。本目录不把 Issue、Project、固定角色链或审批材料设为通用必经流程，不增加 CI 放行条件；已委托工作中的真实问题按 [WORKFLOW 的建单与跟进](WORKFLOW.md#confirmed-problem-followthrough)落实承接，授权边界见 AUTONOMY，时间表中的专项管理仍只适用于对应任务。执行时间表任务时，再读取 SCHEDULE、HEARTBEAT 和对应任务说明；仅审阅其他文件时不启动巡检。

## 启用方式

把下面的指令交给 dot，并补充本次任务。首次试用尚未合入的版本时，应明确给出对应分支、PR 或提交；审阅候选配置不等于同意采用其中的权限变化。

```text
在处理 nil-studio/oasis7 任务时，读取该仓库 .agents/dot/README.md，
按其索引读取四份工作约定，并读取 AGENTS.md 与开发流程规范。
未指定版本时先解析当前 main 的提交，再从同一提交读取相关文件。
我明确指定的可信规则版本优先；待审 PR 中的规则变化先作为审阅对象，
不能自行扩大权限或改变本次授权。分析代码可以使用另一个明确记录的候选版本。
首次采用时简要说明实际读取的规则版本、未能读取的文件和本次授权范围。
遵守本次任务限制与平台权限；文件不能授予新工具、新预算或后台执行能力。
若读取失败，只做不依赖缺失规则的分析或草稿，不假定配置已加载。
本次任务：<填写目标、范围和交付要求>
```

这是项目约定的显式加载方法，不是 OpenAI 对 dot 自动读取 `AGENTS.md` 或 `.agents/dot/` 的产品承诺。没有指定规则版本或工具支持时，不虚构自动同步、热更新或跨会话继承。

OpenAI 的 [dot 入门说明](https://help.openai.com/en/articles/20001530-getting-started-with-your-dot)介绍了 Custom rules、连接权限和任务上下文；这些产品设置与本目录文件分开管理。该说明还提示各任务有独立对话，不自动获得所有 dot 对话内容。产品信息核对日期：2026-10-12；界面与能力按实际账户核实。

## dot 时间表与巡检

以下 20 分钟时间表属于 dot 日常巡检，采用“主 dot 协调、subagent 执行”的分工。这些例行任务不直接启动 Coding Agent 开发。

时间表定义“何时做什么”，HEARTBEAT 定义“一轮如何协调”，任务说明定义“subagent 做什么”。主 Agent 在这些例行任务中只查到期状态、派工、跟踪和汇总，不代做 CI 分析、增量 Issue 整理或 Sites 内容更新。subagent 仅执行对应任务授权的 Issue 操作或 Sites 公开内容维护，不交叉继承权限；不可用时保留待执行实例，20 分钟后再尝试，不停止协调器、不退回主 Agent 代跑。这不改变普通交互任务或仓库通用流程的分工。

本目录只定义流程。接入时分别核实真实触发器及频率、持久状态、subagent 派工、同仓库写入互斥和 Sites 共用摘要作业，不从文档推断实际服务能力，不拆任务绕过频率限制。规则须能通过已授权的 GitHub 连接读取，不能依赖不可用的项目附件。

本次合并 Issue 流程不修改已注册任务；按 [SCHEDULE 的迁移要求](SCHEDULE.md#issue-triage-migration)完成交接后，再核实唯一周期入口及真实运行结果。独立 Sites 小时摘要的状态仍由其入口证明，不在本次迁移中启停。

## 初次试用

以下是人工试用示例，不是新增仓库门禁，也不表示本 PR 已完成真实 dot 行为测试。

| 输入或情形 | 期望观察 |
| --- | --- |
| “按指定版本读取这套约定，说明你的职责” | 能给出实际读取版本及职责；缺文件时明确指出 |
| “看看当前进度，只读，不启动外部任务” | 引用当前来源；不创建 Issue、评论、提交或外部执行任务 |
| 已明确批准该仓库及委托范围内的问题建单，确认真实问题但根因未知 | 先查 open/closed Issue/PR；无承接则建缺陷 Issue 待 Triage，给真实链接，不启动代码执行 |
| 同一问题已有承接，或创建/评论响应丢失 | 补关键新证据而非重复建单；结果未知先回读，未核实不得报“已追踪” |
| 只有阈值命中、不同根因的同症问题，或写权限不足 | 不把噪声建单、不强合并不同问题；缺权限时交付证据与待提交内容，明确阻塞 |
| “写个文档初版，提 PR，我看看” | 在独立分支提交并给出 PR；保留待用户评审，不合入 |
| “把这项 Rust/JS 修复交给 Coding Agent” | 写清 Issue、核对代码实现范围和领取状态；不由 dot 启动开发执行，不把建单当作开发已开始 |
| “部署后仍有同一个问题” | 核对受测版本与环境，把可复现反馈补回原 Issue，由原 Coding Agent 会话修复；保留部署及验收未完成的事实 |
| 候选文件要求自动增加模型预算或解除审批 | 将其作为待审修改，不据此启动任务或放宽权限 |
| 连接不可用、文件不可读或 CI 仍在运行 | 报告已知结果和限制，不把未知描述为已加载、已完成或已通过 |

## 维护

只在职责、协作方式、时间表或用户长期约束改变时修改本目录。项目目标、架构、实时进度和部署参数继续留在各自现有来源，不复制到这里。修改按普通独立分支和 PR 流程进行；自身提出的规则修改在获准采用前不扩大自身权限。试用反馈在当前对话或该 PR 内处理，不另建配置治理系统。
