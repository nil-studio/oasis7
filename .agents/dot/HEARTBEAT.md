# 时间表巡检与协调

本文件是每轮巡检的执行约定，不是 OpenAI 自动识别的心跳配置或已经部署的程序。时间点只在 [SCHEDULE.md](SCHEDULE.md) 维护，权限沿用 [AUTONOMY.md](AUTONOMY.md)。主 Agent 只协调，所有时间表事项交给真实 subagent。

## 接入前核实

运行器须接入实际 20 分钟周期、授权的 GitHub 连接、跨轮持久状态、原子防重复派工、subagent 派工/查询及通知接口；Issue 操作还须有对应写权限；Sites 项另须核实准确 Site/项目/环境、受限来源与摘要入口、既有小时任务的真实标识和共用作业去重，不继承 Issue 写权限。记录真实触发器 ID、采用的规则版本、时区、状态后端和激活时间，分别说明协调器、子任务接口及写权限的实际接入情况，未接入不宣称已运行。

subagent 当前不可用不要求停止已启用的协调器：到期实例进入等待，每 20 分钟再尝试调用；其他巡检、在途跟踪和通知继续。等待策略不能凭空补出触发器或持久状态，也不能绕过模型服务、费用与用户授权。

当前 ChatGPT 内置周期任务最高每小时一次，不能直接承载此处的 20 分钟要求；不拆多个小时任务绕过频率限制，不用循环等待假装常驻。接入新的外部运行器/模型服务须另行核对能力和授权。本目录只定义约定，不实现或部署运行器；本次文档变更不产生新的真实任务 ID 或执行记录，也不改变已有独立 Sites 小时摘要任务。

## 一轮只做这些事

1. 读取当前时间和已经采用的规则版本。从同一提交读时间表、任务说明及权限边界；不得因 main 或待审 PR 多了一项就自动扩大任务范围。版本读取失败时不派新任务，可继续核对已经明确授权且有完整快照的在途任务。
2. 读取持久状态，先核对在途子任务、保存已返回的报告和待发通知。无法读取状态时不能把它当成“尚未执行”，只暂停依赖该状态的新派工并报告原因，不终结全部任务。
3. 按时间表展开从激活日到现在的每日实例；各周期项（缺陷 Triage、Sites）按自身激活时间展开并合并遗漏槽，保留覆盖范围和水位，不逐槽补跑。筛选 `scheduled_at <= now` 的事项。未到期不派；到期实例须同时满足尚未成功/终结、无在途任务、未暂停、`next_retry_at` 已到或为空，以及仍在授权范围内。
4. 可派的每日积压按到期时间从早到晚优先，各周期项（缺陷 Triage、Sites）各最多保留一项待派；在共同上限内原子认领；持久保存派工意图后才启动 subagent。执行者不可用且已确认没有创建任务时，保存 `waiting_executor` 和 `next_retry_at = 本次检查时间 + 20 分钟`，释放名额后继续本轮其他协调，不阻塞整个队列。
5. 给 subagent 明确的任务包，确认真实子任务标识后记录运行中及执行尝试。本轮不原地等待分析或执行者恢复；由运行器回调或后续真实巡检收结果、重试，不能以一句“继续后台处理”代替这些能力。空巡检直接结束，不派子任务判断是否需要派任务。
6. 主 Agent 核对报告日期、来源、范围及操作结果，保存真实结果后更新状态，并按 [REPORTING.md](REPORTING.md) 汇总。主 Agent 不代做 CI 数据采集、统计、根因分析、Issue 整理、缺陷 Triage 或 Sites 内容维护及其写入。

## 持久状态与防重复

复用实际运行器的私有持久存储，不使用聊天记忆、临时沙箱文件或 Git 提交充当执行账本。至少保存：`occurrence_key`、计划时间/时区、采用的配置提交、状态、执行尝试次数、`next_retry_at`、派工幂等键、子任务 ID、更新时间、报告引用、最近错误及通知状态。首次初始化须能区别于存储丢失；状态不明时先恢复记录，不从空库重新派完全部任务。

`occurrence_key` 按 SCHEDULE 区分：每日事项为 `仓库 / 稳定 ID / 计划本地日期`，各周期项（缺陷 Triage、Sites）包含计划本地日期、时分和时区。周期合并范围及处理水位另存；已有 pending/waiting_executor 的承接键、尝试次数和 next_retry_at 不随新槽改变，在途或未知结果的原实例身份也保持不变。同一实例同一时刻只能有一个认领者；并发巡检须使用唯一约束、事务或 compare-and-set，不能只靠先读后写的提示词。运行器若不能提供该保证，就不启用自动派工。重试复用实例身份，已确认可重试的执行尝试才在该实例内生成下一次派工标识。

| 状态 | 下一轮处理 |
| --- | --- |
| `pending` | 到期且有名额时认领 |
| `waiting_executor` | `now >= next_retry_at` 时再尝试调用 subagent；仍不可用就再延后 20 分钟，不终结实例 |
| `dispatching` | 先按已保存的幂等键核对是否已创建；结果不明时不重复启动 |
| `running` | 查询原有子任务；仍在执行就继续跟踪，不重派 |
| `succeeded` | 已保存完整报告，所需 Issue/Sites 操作或无变化结论已核实；同一实例不再执行，仅处理未完成通知 |
| `partial` | 已交付带限制的报告；保留未完成操作/事项，不当成完整成功，不自动重做已完成分析 |
| `failed` | 已确认原任务结束，且属于可重试故障时按执行上限重试；其他情况保留失败 |
| `blocked` | 授权、状态或操作结果待核实；只暂停相关不安全动作，前置恢复后先协调已有结果 |
| `cancelled` | 用户停止或事项已撤销；不自动重新启动 |
| `coalesced` | 仅用于周期项未执行的过期槽；由一个恢复 review 覆盖，保留范围和承接实例，不计逐槽成功 |

创建子任务的返回丢失时，先按幂等键查询真实结果；无法证明未创建则继续协调原派工，不得把它当成“subagent 不可用”重新发起。只有确认任务未创建，才适用等待执行者策略。提交版本变化或主 Agent 重启不生成另一个实例。

只有 subagent 真正结束并返回可读取的报告，才可标记 succeeded/partial；“已派出”“模型说完成”或只有健康检查不够。保存报告、Issue/Sites 操作和结果状态要可恢复；通知与任务执行分别去重，通知失败只补通知。发送结果未知时先核对已有消息，不无限补发。

## 并发、重试与停止

初版最多同时运行 2 个子任务，每次巡检最多新派 2 个，每实例最多 2 次已确认创建的子任务执行尝试（含首次）；子任务不再递归派工。执行者不可用且未创建任务不计入这 2 次，也不计入子任务的 60 分钟执行上限，不因等待次数或跨日而失败/停止。同一不可用执行入口每轮只探测一次，等待项不占在途名额。

等待执行者的实例持续保留，在 `next_retry_at` 到期后的首轮真实巡检再次尝试；成功获得执行者时清除等待时间。协调器不 sleep 20 分钟、不忙轮询、不创建一串新定时任务；不阻止其他可执行事项、在途查询或结果通知。没有真实运行器时只能保留配置意图，不能承诺稍后自动调用。

子任务已开始后的临时执行故障，须确认原任务结束才按剩余执行次数重试；权限/数据不足交付 partial 或 blocked，不每轮重做分析。设置每次执行上限 60 分钟，但到时先查询/停止原任务并确认终止，不能因超时或租约过期直接启动第二份。需要新服务或新增费用时按 AUTONOMY 核对授权，不以等待重试自动扩大预算。

暂停时间表项或收到停止要求后，不派新任务、不重试；按实际能力停止在途子任务并核对结果。无法确认已停止时保留真实在途状态并报告，不伪记 cancelled。清理或恢复不得删除防重复记录；配置变化不提升权限、并发或费用上限。

## Issue 写入的协调

分析可以并行，所有涉及 Issue 的时间表任务（含缺陷 Triage）的写入须经运行器的同仓库写入互斥串行执行；写入前的查重/状态核对、实际操作及回读处于同一受控段。主 Agent 只分配写入资源和传递已有结果，具体判断与操作仍由 subagent 完成。未取得写入资源时保留待处理动作，不绕过互斥，也不阻塞其他只读工作。

私有状态保存同源问题到主 Issue 的关联，以及每项创建、增量评论、要求迁移、关闭操作的目标、依据和已确认/未确认结果。跨日、重试、缺陷周期、06:00 补跑与 13:00 任务相遇时复用这些记录，不因实例日期不同重新建单。每次写入前重新读取当前 Issue，保留他人新增内容；运行器互斥不等于锁住人工或其他客户端的修改。

结果未知先查服务器；评论已写就不再追加，要求已迁移就不重复复制，Issue 已按同一依据关闭就不重复关闭。出现并发新意见时重新判断受影响操作；不能证明目标状态和未完成义务时保留原 Issue，只报告该项限制。报告与 Issue 写入分别记录，报告生成不代签写入成功。

## Sites 更新的协调

Sites 项沿 [任务说明](tasks/sites-content-review.md) 使用现有有界来源入口和独立摘要作业；它是时间表 subagent 的受限操作，不由该 subagent 再派一个分析子任务。模型执行仍归原摘要任务入口，其运行状态与有限预算单独核对，不转成主 Agent 代跑或新开发派工。

以准确 Site/项目/环境/公开来源范围为隔离键，共用发布互斥与带版本条件的写入。20 分钟 review 和小时触发先核对同一输入指纹已有的运行、结果或未知提交：已有成功结果就复用；已有运行就跟踪；未知就查原回执。不能只按不同时间表实例键各自生成摘要。任务入口无法提供共同认领/去重及状态查询时，暂停新的自动写入，只检查和报告，不靠提示词假称互斥。

持久记录来源 revision/内容摘要/coverage、预期摘要 revision、作业/提交幂等键、真实运行标识、已确认回执、last-good 和未完成动作。CAS 冲突先读取新输入与当前结果，不覆盖更新内容；请求受理不算发布成功。已完成来源更新而摘要失败时只协调剩余摘要，不重放整轮来源写入；报告和通知也各自去重。保留所有在途/未知操作后才推进周期合并水位。

## 子任务说明模板

```text
你是时间表任务的执行 subagent，主 Agent 只负责协调。
仓库：eng-cc/oasis7；实例键：<occurrence_key>。
计划时间及任务日期：<scheduled_at / timezone / local_date>。
统计窗口：<window_start_inclusive, window_end_exclusive>；不要按实际补跑日重算。
采用的工作约定：<config_commit>；任务说明：<该提交内的任务文件>。
读取所需 GitHub 来源，记录实际查询时间、版本、分页及未覆盖范围。
允许的 Issue 操作：<仅本任务已授权的创建/增量评论，或分类转换/迁移/去重/关闭范围>。
既有操作与待协调结果：<运行器提供的私有记录及同仓库写入互斥入口>。
不修改代码/CI/分支保护，不发 PR 评论、创建 PR、合入、部署、删除 Issue 或再派工。
遵守已批准模型/预算和 60 分钟执行上限；缺关键条件如实交付限制，不伪造完成。
返回中文报告、来源和 Issue 链接、真实操作结果、覆盖范围及完成/部分/失败结论。
```

任务创建时由运行器注入已有授权、实际执行限制与必要文件内容/可读取引用；模板中的占位符不视为已经完成派工。

Sites 项用同一模板结构，但仓库读取目标核对为 `nil-studio/oasis7`，输入替换为准确 Site/项目/环境、周期槽/合并范围、来源与摘要版本、任务实际配置和共享作业入口；允许动作仅为任务说明内的公开来源/摘要缓存维护，Issue 操作为“无”。返回来源与摘要的分别结果、回读证据及未知范围，不要求 GitHub 写入。任务包不得携带服务密钥、个人记录或用户对话。

## 行为试用场景

以下是接入后的验收案例，不是当前已经通过的运行记录，也不是仓库合入新门禁。

| 场景 | 期望 |
| --- | --- |
| 同一天 05:40 / 06:00 / 06:20 / 13:00 巡检 | 两个每日事项分别到期派一次，06:20 不重派原整理任务；缺陷 Triage 与 Sites 分别按周期槽独立认领/合并，未到期项不派 |
| 13:00 漏触发，13:20 才恢复 | 补派同一天 CI 实例，不漏执行 |
| 两轮同时发现同一到期项 | 只有一个原子认领成功，不重复启动 |
| 任务跨越多个巡检间隔 | 保持同一子任务，不因未完成重复派工 |
| 派工响应丢失 / 主 Agent 重启 | 协调真实子任务，不套用等待执行者逻辑盲目重派 |
| 每日事项前一天未执行，跨日恢复 | 按旧计划日期补跑，各统计窗口不变；新日期实例独立去重 |
| 每日或周期项的承接 subagent 连续三轮不可用，第四轮恢复 | 每次延后 20 分钟；仍为同一实例，执行尝试未耗尽，恢复后派一次 |
| subagent 等待期间另有在途任务完成 | 正常收取和汇报，不停止协调器或阻塞其他事项 |
| 缺状态存储或写权限 | 只暂停依赖该条件的动作，不伪造执行或写入成功 |
| 两任务遇到同一卡点 / 写入响应丢失 | Issue 写入串行查重并核实结果，不重复建单、评论或关闭 |
| 已有报告且 Issue 操作完成，但通知失败 | 只补通知，不再次分析或写 Issue |
| 时间表改文案、暂停或用户停止 | 不重跑已完成项；暂停/停止阻止新派工并核对在途状态 |
| Sites 停机一天后恢复，且每日事项积压 | 周期遗漏合并为一项最新 review，记录覆盖槽而非 72 次摘要；每日事项仍逐日补跑且优先 |
| Sites 20 分钟项与小时摘要同时发现相同输入 | 共用作业只归纳/发布一次，分别记录计划触发与共享结果 |
| 摘要运行期间来源变化、CAS 冲突或提交回执丢失 | 保留 last-good，先协调原作业/回执，不让旧结果覆盖新输入，不盲目重写 |
| 摘要任务停用、共用互斥不支持或来源缺证据 | 不擅自启用/新增任务，显示真实限制；缺证据不改成成功或空结果 |
